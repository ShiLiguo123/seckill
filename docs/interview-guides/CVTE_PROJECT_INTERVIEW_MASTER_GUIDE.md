## 0. 如何使用这份文档

这不是普通项目说明，而是一份面向 AI 应用工程师、大模型应用工程师和后端工程岗位的项目答辩底稿。建议按以下顺序复习：

1. 先背熟 30 秒、2 分钟和 5 分钟介绍；

3. 掌握从初版动态 Rubric 到最终预构建 Rubric 的架构演进；
4. 掌握知识点分组、证据溯源、结构化输出、缓存和降级；
5. 最后使用高频问题、压力追问和数字口径卡进行三层追问演练。

面试中的主线始终是：

> 传统听评课依赖教研员经验，评价口径不统一，结论又难以追溯到课堂原始证据。直接让 LLM 自由评分会进一步引入标准漂移、上下文干扰和无依据结论。因此我没有把模型当作自由裁判，而是把教育评价建模为“知识点驱动、Rubric 约束、证据绑定、可信度校验”的确定性工作流：先构建评价参照，再让模型匹配证据判级，最后由代码校验和阻断不可信结果。

### 0.1 项目记忆钩子

只记一句话：

> **模型负责理解课堂，Rubric 负责限定标准，证据链负责证明结论，代码负责最终放行。**

### 0.2 面试时不要混淆的四组概念

| 容易混淆的概念 | 正确区分 |
| --- | --- |
| 课堂素养与知识点 | 素养是长期能力目标，知识点是本节课可观察的载体 |
| 观察点与等级 | 3×3 产生 9 个观察点；每个观察点再按 C/B/A/S 四级描述 |
| 引用真实与评价正确 | evidence_id 真实只证明引用未伪造，不等于判级语义一定正确 |
| 工作流与 Agent | 本项目最终采用显式工作流；LLM 只在规定节点完成语义任务，不拥有自由规划权 |

## 1. 项目定位

### 1.1 一句话定位

这是一个面向新课标课堂素养评价的 Rubric-constrained LLM Evaluation Engine：系统把希沃课堂问答与互动数据按知识点聚合，映射到学科素养和 3×3 能力要素框架，再让 LLM 依据预定义 C/B/A/S 行为标准完成证据匹配、判级和教学建议，并通过 evidence_id、5 级引文匹配、trust_score、缓存和审计机制保证结果可追溯、可复现。

### 1.2 30 秒介绍

```text
这个项目主要解决传统听评课依赖教研员经验、评价标准不统一、结论缺少课堂证据的问题。我的核心思路是不让 LLM 直接自由评分，而是先把知识点、学科素养和 3×3 能力要素建模为可观察的 Rubric，再让模型在 C/B/A/S 四级行为标准中完成受约束匹配。工程上我把初版运行时生成评价框架重构为“预构建评分框架 + 知识点分组评估”，减少约 40% LLM 调用；同时通过 evidence_id、5 级引文匹配和 trust_score 阻断无效引用。基于 400 节人工标注课程迭代 Prompt 和规则，在 100 节独立验证集上与人工标准一致率达到 85%+，关键维度准确率达到 90%+。
```

### 1.3 两分钟介绍

```text
这个项目面向新课标下的课堂核心素养评估。传统听评课主要依赖教研员经验，存在三个问题：第一，不同教研员的评价口径不一致；第二，结论往往只有“好或不好”，但无法追溯到课堂中的具体问答和互动；第三，素养是长期、抽象的能力目标，不能直接拿一段课堂对话让大模型打分。

我的第一个核心工作是评价问题建模。我把“知识是能力的载体、能力是素养的外显”转化为三层映射：知识点先映射到学科核心素养，再落到学习理解、实践应用、迁移创新三个维度，每个维度设置三个可观察能力要素，共 9 个课堂观察点；每个观察点再按 C/B/A/S 分成达标、良好、优秀、卓越四级行为标准。这样就把开放式评分转化为基于 Rubric 的受约束选择问题。

初版方案会在运行时让 LLM 为每个知识点生成 9 条候选期望表，然后总结课堂案例、标注证据、查表判级。这个方案验证了“先有标准、再判级”的可行性，但也暴露出调用链长、上下文膨胀和评价标准可能波动的问题。因此我进一步重构为“知识点驱动 + 预构建评分框架 + 分组评估”：先把课堂问答按知识点和时间密度聚合成教学案例，只注入当前知识点相关的素养、Rubric 和证据；每组最多 3 个知识点，减少无关上下文，LLM 调用量降低约 40%。

可信度方面，每条判级必须绑定原始课堂对话的 evidence_id。后处理依次执行 Schema 校验、5 级引文匹配、trust_score 计算和审计落盘，trust_score 低于 0.9 时自动阻断。28 次真实运行共生成 178 条引用，没有发现伪造 evidence_id；在更严格的语义匹配口径下，无效引用率控制在 2% 以内。

评测方面，构建了 400 节人工标注评估集，其中 300 节作为开发集迭代 Prompt 和评价规则，100 节作为独立验证集。最终与人工标准一致率达到 85%+，专家标记的关键评价维度准确率达到 90%+。工程上使用 design_targets 确定性缓存、24 小时 LLM 响应缓存和 SHA-256 增量证据构建，相同输入重评由 2-5 分钟降低到 2 秒以内，并设计了模型失败、Schema 错误和章节 API 失败等多级降级路径。
```

### 1.4 五分钟介绍结构

五分钟介绍不要从 Prompt 或缓存开始，按以下顺序讲：

1. 传统听评课的业务问题；
2. 为什么“直接把课堂对话交给 LLM 打分”不可靠；
3. 知识点 → 素养 → 3×3 能力要素 → C/B/A/S 的评价建模；
4. 初版动态 Rubric 的问题与最终预构建 Rubric 的演进；
5. 用“认识周长”案例串起知识点聚合、证据匹配、判级和建议；
6. 用 400 节数据、85%+ 一致率、40% 调用下降和 <2% 无效引用率收尾。

### 1.5 项目最准确的技术标签

推荐标签：

- Rubric-based Evaluation；
- LLM-as-Judge，但需要强调模型受预定义 Rubric 约束；
- Evidence-grounded Generation；
- Structured Output / Schema Validation；
- Context Engineering；
- Deterministic Workflow；
- Education AI / Classroom Analytics。

不建议把项目包装成：

- 自主 Agent 系统；
- 普通 RAG 问答；
- 从零训练教育大模型；
- 仅靠 Prompt 消除幻觉。

## 2. 业务问题、系统目标与边界

### 2.1 输入是什么

系统的主要输入包括：

- `course_id`、`chapter_id`、学科、年级等课程元数据；
- 教学目标与课前目标；
- 希沃课堂问答记录和师生互动数据；
- 课堂对话轮次、时间戳和角色信息；
- 可选的其他课堂行为文本描述；
- 当前学科课标、素养定义和能力要素表；
- 预构建的学科 Rubric 与评分指导。

### 2.2 输出是什么

系统最终回答“3+2”类问题：

1. 本节课应该发展哪些核心素养；
2. 实际达到了什么能力维度和行为等级；
3. 结论由哪些课堂证据支持；
4. 当前表现与下一等级之间差在哪里；
5. 教师下一次可以如何改进。

典型结构化输出包含：

- 知识点与素养映射；
- 评价维度和观察点；
- C/B/A/S 等级；
- `good_points`；
- `gaps`；
- `improvement_hint`；
- 绑定课堂轮次的 evidence_id；
- 三层递进教学建议；
- trust_score 和审计信息。

### 2.3 为什么直接 LLM 评分不够

#### 问题一：评价标准会漂移

如果只给模型一句“请评价这节课的核心素养达成度”，模型会根据自身语言先验临时创造评价标准。同一节课换 Prompt、换模型或重复运行，等级边界可能发生变化。

#### 问题二：开放式生成容易出现“语言正确、证据不足”

模型很擅长生成听起来专业的教学建议，但建议不一定来自课堂真实行为。教育评价需要回答“这句话是根据哪一轮师生对话得出的”。

#### 问题三：完整课堂对话上下文过长

一节课可能包含多个知识点、大量对话和互动记录。如果把完整课堂、全部课标和全部评分表一次性放入上下文，会出现：

- Token 成本高；
- Lost in the Middle；
- 模型注意力被无关知识点分散；
- 长任务干扰知识点提取等短而重要的任务；
- 输出格式更容易失控。

#### 问题四：抽象素养不能直接从一节课得出

核心素养具有长期性。一节课只能观察到素养在特定知识点和能力要素上的局部表现，不能把单节课判级等价为教师长期素养水平。

### 2.4 系统目标

系统目标不是替代教研员，而是：

- 统一评价参照；
- 将抽象素养转化为可观察行为；
- 让每个判级都能回到课堂原始证据；
- 为教研员提供可复核的初步诊断；
- 为教师提供具体、分层、可执行的改进建议；
- 在相同输入下得到尽可能稳定、可复现的结果；
- 在模型或外部 API 失败时受控降级。

### 2.5 系统边界

面试中必须主动说明：

- 系统只使用已有课堂过程数据，不分析完整课堂视频；
- 板书、动作、表情等视觉证据当前不完整；
- 一节课只能反映局部教学表现，不能直接评价教师长期能力；
- 自动结果用于辅助教研，不替代高风险或正式考核中的专家判断；
- 引文真实不等于教育评价在科学性上绝对正确；
- 评价框架仍需教育专家持续校准。

### 2.6 项目的核心业务价值

| 传统方式 | 系统化方式 |
| --- | --- |
| 依赖教研员个人经验 | 使用统一 Rubric 形成共同尺度 |
| 结论难追溯 | 判级绑定原始课堂轮次 |
| 只能给总体印象 | 按知识点、素养、维度和观察点诊断 |
| 建议较抽象 | 对照下一等级差距生成递进建议 |
| 重复评价成本高 | 缓存与增量构建支持低成本重评 |

## 3. 教育评价理论与 3×3×4 建模

### 3.1 三层映射理论

项目的根本理论是：

```text
知识是能力的载体
        ↓
能力是素养的外显
        ↓
素养通过“知识 × 能力”的课堂行为被观察
```

落到系统中：

```text
知识点
  ↓ 映射
学科核心素养
  ↓ 分解
3 个能力维度 × 每维 3 个观察点
  ↓ 分级
C/B/A/S 四级教师与学生行为描述
  ↓ 匹配
课堂实际行为 + 原始证据
```

### 3.2 三个能力维度

通用表达为：

1. **学习理解**：学生是否理解概念、识别对象、复述关系和建立初步表征；
2. **实践应用**：学生是否能够在任务、练习或真实情境中使用知识；
3. **迁移创新**：学生是否能够跨情境迁移、提出问题、解释新现象或自主探究。

不同学科的具体能力要素并不完全相同，因此项目使用学科专属标签和描述，而不是一套词表覆盖全部学科。

### 3.3 为什么是 3×3

每个大维度继续拆成 3 个可观察点，共 9 个交叉格。这样做的目的是：

- 避免只给“学习理解较好”这种粗粒度结论；
- 让每个观察点能够绑定具体教学行为；
- 支持从当前观察点向下一观察点生成发展建议；
- 控制 Rubric 规模，避免评价表无限膨胀。

### 3.4 C/B/A/S 四级的含义

| 等级 | 名称 | 核心差异 |
| --- | --- | --- |
| C | 达标 | 教师主导，学生旁观或模仿 |
| B | 良好 | 教师引导，学生参与练习 |
| A | 优秀 | 学生主动建构，教师适时点拨 |
| S | 卓越 | 学生自主探究，课堂具有研究与迁移价值 |

等级不是简单按“说得多、互动多”判断，而要同时观察：

- 教师做了什么；
- 学生是否产生对应行为；
- 行为是否和当前知识点相关；
- 是否存在可定位的课堂证据；
- 是否真正达到该等级的关键差异。

### 3.5 观察点编码与等级编码不要混淆

技术文档可能使用 A1/A2/A3、B1/B2/B3、C1/C2/C3 表示 9 个观察点，同时又使用 C/B/A/S 表示行为等级。面试时应明确：

- 前一组是“维度与观察点坐标”；
- 后一组是“行为水平等级”；
- 两者是两个正交轴，不是同一个 A/B/C。

更清晰的数据结构可以分别使用：

```text
dimension = learning_understanding
observation_index = 1
level = B
```

### 3.6 表现期望如何设计

表现期望采用三步法：

1. **观察分析**：从教学设计、课堂教学和练习反馈中提炼典型行为；
2. **初拟描述**：描述教师和学生“做了什么”，避免只描述“说了什么”；
3. **专家校验**：对照课程标准、教师专业标准和真实课堂案例修订模糊或不可观察的描述。

一条合格的 Rubric 描述必须同时具备：

- 知识点关联；
- 能力维度关联；
- 教师行为；
- 学生行为；
- 可观察证据；
- 相邻等级的差异。

### 3.7 为什么 Rubric 比自由 Prompt 更可靠

Rubric 的作用不是让模型绝对正确，而是缩小模型的决策空间：

```text
自由评分：模型自己决定“评什么、怎么评、评几级”
Rubric评分：系统先固定“评什么、等级差异是什么”，模型只做证据匹配
```

这相当于把开放式生成问题改造成受约束的分类与证据对齐问题。

## 4. 架构演进：从动态 Rubric 到预构建 Rubric

### 4.1 初版方案解决了什么

初版的核心思想已经正确：不让 LLM 直接给评价结论，而是：

1. 知识点映射到素养；
2. 为当前知识点生成 9 条候选期望；
3. 每条期望包含 C/B/A/S 四级行为描述；
4. 总结课堂案例并标注证据；
5. 从候选表唯一匹配一个观察点和等级；
6. 输出优点、差距和三层建议。

它首先验证了“先生成评价参照，再匹配判级”是可行的。

### 4.2 初版的三个主要问题

#### 问题一：运行时生成 Rubric，标准可能波动

同一知识点重复运行时，9 条候选期望的措辞和等级边界可能变化，影响复现性。

#### 问题二：调用链过长

知识点映射、候选表生成、案例总结、查表判级和教学建议都可能触发模型调用，知识点越多，调用数越高。

#### 问题三：上下文膨胀

完整课堂对话、多个知识点、9 条候选表和四级描述同时进入上下文，容易达到模型的灰度容量区间，即虽然未超过硬限制，但注意力和格式稳定性明显下降。

### 4.3 最终方案如何重构

最终方案采用：

> **知识点驱动 + 预构建评分框架 + 分组评估 + 证据后处理**

关键变化：

| 维度 | 初版 | 最终方案 |
| --- | --- | --- |
| Rubric | 运行时由 LLM 生成 | 预构建、版本化、按学科读取 |
| 输入组织 | 完整案例与大表同时输入 | 按知识点聚合并裁剪无关内容 |
| 评估单位 | 多阶段、多次调用 | 每个知识点组一次结构化评估 |
| 结果约束 | 候选表唯一匹配 | 只能在预定义行为表中判级 |
| 证据验证 | 基础证据标注 | 5 级引文匹配 + trust_score |
| 复现能力 | 受动态生成影响 | design_targets 和响应缓存 |
| 失败处理 | 流程失败风险较高 | Schema 修正、重试和多级降级 |

### 4.4 为什么不在简历里写“方案一/方案二”

简历只呈现最终系统和一次关键架构演进：

> 针对初版实时生成评价框架导致的调用链长、上下文膨胀和结果波动，重构为“预构建评分框架 + 知识点分组评估”

面试官继续追问时，再展开初版和最终方案的差异。这样既体现最终架构完整度，也展示技术判断力。

### 4.5 为什么选择 Workflow 而不是 Agent

本项目最终使用工作流，原因是：

- 评价步骤固定，没必要让模型自由规划；
- 中间结果必须逐阶段审计；
- Agent 黑盒决策不利于定位评分错误；
- 课堂数据和 Rubric 已占用大量上下文；
- Agent 循环会增加时延和成本；
- 教育评价要求同输入尽可能同输出。

统一回答：

> 这个项目的难点不是“下一步该调用什么工具”，而是“每一步必须按照统一尺度产出可审计结果”。因此我选择显式工作流，把 LLM 放在知识点提取、语义匹配和 Rubric 判级等有限节点中，而不是让它拥有自由规划权。

### 4.6 总体架构

```text
希沃课堂数据 + 课程元数据
        ↓
输入校验与课堂数据解析
        ↓
教学目标 → 知识点提取
        ↓
知识点 → 核心素养与目标档级
        ↓
按知识点进行语义检索、时间切分与案例聚合
        ↓
读取学科专属 3×3×4 预构建 Rubric
        ↓
每组 ≤3 个知识点进行结构化 LLM 评估
        ↓
Schema 校验与自动修正
        ↓
evidence_id 绑定 + 5级引文匹配 + trust_score
        ↓
判级、good_points、gaps、三层递进建议
        ↓
缓存、审计日志与 data/runs/ 持久化
```

### 4.7 项目的四个核心创新点

1. **评价问题结构化**：把抽象素养转为 9 个观察点和四级行为 Rubric；
2. **受约束 LLM 判级**：模型只能依据预定义标准和课堂证据完成匹配；
3. **知识点级 Context Engineering**：按知识点聚合、裁剪和分组，控制上下文与调用成本；
4. **证据可信度闭环**：引用绑定、语义匹配、trust_score、缓存和审计共同保证可追溯与复现。

## 5. 技术栈与工程组件

技术栈不要为了显得复杂而虚构框架。面试中优先讲清楚组件职责：

| 层 | 技术或机制 | 作用 |
| --- | --- | --- |
| 数据接入 | 课程/章节 API、课堂问答与互动记录 | 获取课程元数据和原始证据 |
| 流程编排 | 显式 Workflow / Pipeline | 固定阶段、错误边界和中间产物 |
| LLM 调用 | Structured Output、低温生成 | 知识点提取、语义匹配和 Rubric 判级 |
| 数据契约 | JSON Schema | 约束映射、评估结果、引用和建议格式 |
| 评价框架 | 学科专属 3×3×4 Rubric | 提供统一、可版本化的评价参照 |
| 上下文工程 | 知识点聚合、案例裁剪、每组≤3点 | 降低 Token、调用和注意力干扰 |
| 证据校验 | evidence_id、5级引文匹配、trust_score | 检查引用存在性和语义有效性 |
| 可复现 | design_targets 缓存、LLM 响应缓存 | 相同输入复用确定性中间结果 |
| 增量构建 | SHA-256 内容指纹 | 无变化时跳过证据层重建 |
| 并发与稳定性 | 异步线程、最多重试2次、多级降级 | 降低阻塞并控制外部服务故障 |
| 审计 | 运行日志、Prompt/模型/Rubric版本、`data/runs/` | 支持问题定位和结果复盘 |
| 测试 | 单元测试、链路测试、离线验证集 | 覆盖结构、证据、缓存和降级路径 |

### 5.1 为什么需要 JSON Schema

自然语言输出容易出现字段缺失、类型不一致、枚举漂移和额外解释。Schema 把模型输出限制为系统可消费的数据，例如：

```json
{
  "knowledge_point": "周长",
  "competency": "量感",
  "dimension": "学习理解",
  "observation_point": "LU-1",
  "level": "B",
  "evidence_ids": ["turn_12", "turn_15"],
  "good_points": [],
  "gaps": [],
  "improvement_hint": ""
}
```

Schema 的价值包括：

- 后续程序可以确定性消费；
- 枚举字段可做白名单检查；
- 缺失证据可在进入建议阶段前阻断；
- 便于做批量评测和错误分类；
- 便于缓存、审计和版本迁移。

### 5.2 为什么需要低温和确定性缓存

教育评价追求稳定，不追求语言创造性。低温可以减少随机表达差异，但不能保证事实正确；确定性缓存可以直接复用已经验证的中间结果。两者解决不同问题：

- 低温降低采样随机性；
- Rubric 限制决策空间；
- 缓存降低重复调用和重复波动；
- 证据校验负责阻断不可信输出。

### 5.3 为什么不把项目说成 RAG

项目包含语义检索：将课堂片段匹配到知识点，但核心不是“检索文档再回答问题”。核心是：

- 对课堂行为进行评价建模；
- 使用 Rubric 完成受约束判级；
- 将结论绑定课堂原始证据。

因此更准确的说法是“Rubric 约束的证据化评估引擎”，而不是普通 RAG。

## 6. 核心数据结构

下面的数据结构是理解整条链路的关键。名称可以与真实代码不同，但字段语义必须一致。

### 6.1 CourseContext

```json
{
  "course_id": "course_001",
  "chapter_id": "chapter_03",
  "subject": "数学",
  "grade": "三年级",
  "teaching_objectives": ["理解周长含义", "能够测量简单图形周长"],
  "rubric_version": "math_2022_v3"
}
```

作用：保存课程、学科、年级、教学目标和 Rubric 版本，是后续知识点提取与缓存键的一部分。

### 6.2 KnowledgePointTarget

```json
{
  "knowledge_point_id": "kp_math_perimeter",
  "name": "周长",
  "source": "teaching_objective",
  "competencies": [
    {
      "name": "量感",
      "target_level": "B",
      "confidence": 0.90
    }
  ]
}
```

作用：表示“本节课为什么需要评这个素养”。`source` 必须可追溯到教学目标或开放发现模式。

### 6.3 DialogueTurn

```json
{
  "evidence_id": "turn_015",
  "timestamp": "00:18:32",
  "speaker": "teacher",
  "text": "请你找一找教室里哪些物体有一周的长度",
  "interaction_type": "question"
}
```

作用：这是最小原始证据单元。模型不能自己创建 ID，只能引用输入中存在的 evidence_id。

### 6.4 TeachingCase

```json
{

  "knowledge_point_id": "kp_math_perimeter",
```

作用：把散落的课堂轮次聚合为围绕一个知识点的完整教学案例。

```json
}
```

作用：定义模型可以选择的有限评价空间。


### 6.9 AuditRun

建议至少保存：

- run_id、course_id、输入指纹；
- 模型版本、Prompt 版本、Rubric 版本；
- 知识点分组；
- 原始结构化输出；

- 降级路径；

## 7. 端到端执行流程

### 7.1 Prepare：输入校验

主要检查：

- 课程和章节信息是否存在；
- 教学目标是否可用；
- 对话轮次是否有唯一 evidence_id；
- 时间戳和角色是否合法；
- 学科、年级和 Rubric 版本是否匹配；
- 相同课堂是否已经存在可复用缓存。

为什么先校验：如果 evidence_id 重复、角色缺失或课程版本错误，后面的模型判断再准确也无法形成可靠证据链。

### 7.2 获取教学目标与知识点

正常链路：

```text
course_id → chapter_id + 年级 → 教学目标 → 知识点
```

需要注意：

- 教学目标提取和复杂评价不要放在同一次模型调用中；
- 知识点必须规范化，避免“周长”“认识周长”“物体一周长度”被当作三个点；
- API 失败时进入开放发现模式，但结果置信度和审计状态必须标记。

### 7.3 知识点映射到素养与目标

对每个知识点，从学科受控素养空间中选择 1-3 个最相关目标，并给出来源与置信度。最终方案不允许模型自由创造不存在的素养名称。

输入：

- 学科；
- 年级；
- 教学目标；
- 规范化知识点；
- 当前学科允许的素养与能力要素列表。

输出：

- 素养名称；
- 目标档级；
- 映射理由；
- 置信度；
- Rubric 版本。

### 7.4 课堂数据解析与提纯

原始课堂数据可能包含：

- 教师讲解；
- 教师提问；
- 学生回答；
- 师生追问；
- 互动事件；
- 无关寒暄；
- 重复转写和语音识别噪声。

解析阶段完成角色标准化、文本清洗、重复合并、时间排序和 evidence_id 固化。

### 7.5 知识点语义检索

每个课堂轮次与知识点进行语义匹配。不能只用关键词，因为：

- 教师可能不直接说出知识点名称；
- 同义表达和例子可能体现同一概念；
- 关键词可能出现在无关回顾或过渡语句中。

语义检索的输出不是最终评价，而是知识点案例的候选证据。

### 7.6 密度与时间段切分

仅按单句相似度会把同一教学活动切碎。因此系统同时考虑：

- 知识点匹配分数；
- 相邻轮次的时间距离；
- 连续命中密度；
- 问答对完整性；
- 教师问题和学生回答的依赖关系。

目标是形成包含“引入—讲解—练习—反馈”的相对完整教学案例。

### 7.7 读取预构建 Rubric

根据学科、素养和版本读取：

1. 三维度档级说明表；
2. 当前素养相关的教学行为描述表；
3. 评分指导和必要证据要求。

只读取本次需要的 Rubric，而不是把全学科评价表注入模型。

### 7.8 知识点分组

每组最多 3 个知识点。分组时优先考虑：

- 同一教学时间段；
- 素养维度相近；
- 案例证据有重叠；
- 总 Token 预算不超过安全区间。

为什么是 3：这是基于项目上下文容量与稳定性做出的工程工作点，不是普适常数。面试时应强调“最多 3 个”和“按 Token 预算动态控制”，而不是机械每 3 个一组。

### 7.9 结构化评估

每组输入只包含五类信息：

1. 这是什么课；
2. 评价哪些知识点和素养；
3. 课堂中发生了什么；
4. 允许使用的评分表；
5. 评价原则与输出 Schema。

模型必须完成：

- 选择唯一观察点；
- 选择 C/B/A/S 等级；
- 为等级绑定 evidence_id；
- 输出 good_points 和 gaps；
- 给出具体 improvement_hint。

### 7.10 后处理与可信度校验

```text
结构化输出
  ↓
JSON Schema 校验
  ↓
枚举与 Rubric ID 校验
  ↓
evidence_id 存在性检查
  ↓
5级引文匹配
  ↓
trust_score 计算
  ↓
低于0.9阻断 / 修正 / 重试
  ↓
证据标注与审计落盘
```

### 7.11 教学发展建议

建议不是泛化模板，而是根据当前等级到下一目标之间的差距生成：

- tier_1：同维度、同观察点内提升一级；
- tier_2：同维度推进到下一观察点；
- tier_3：推进到下一大维度。

每条建议遵循：

```text
Before：当时的教学场景和做法
Problem：当前证据显示的不足
After：建议替换或新增的具体动作
Why：为什么该动作能够弥补目标差距
```

### 7.12 Finalize：结果持久化

最终结果写入 `data/runs/` 或等价审计存储，保存评价结果、证据、版本、耗时、缓存命中和降级路径，确保同一结果可复盘。

## 8. 核心模块详细设计

### 8.1 知识点规范化

知识点规范化需要处理：

- 同义词；
- 上下位概念；
- 教材章节名与课堂口语差异；
- 一个目标包含多个知识点；
- 复习内容与本节主目标的区分。

可以采用“受控词表优先、规则归一、LLM 兜底”的思路，但如果真实代码没有完整三级架构，面试时不要主动宣称具体命中比例。

### 8.2 知识点—素养映射

映射不是纯关键词分类。模型需要同时读取：

- 知识点定义；
- 教学目标上下文；
- 学科素养定义；
- 能力要素描述；
- 年级和学段约束。

输出必须从受控候选中选择，避免自由生成“创新思维能力”等不在当前课标版本中的标签。

### 8.3 案例聚合

案例聚合是项目中容易被忽视但很重要的模块。它解决的是：

> 如何把一整节课的碎片化对话，重组为围绕某个知识点、能够独立评价的教学过程。

如果聚合错误，后面可能出现：

- 把另一个知识点的学生回答当作当前证据；
- 只截取教师问题，没有学生反馈；
- 把课堂导入与核心教学阶段混在一起；
- 因证据不完整而错误降级。

### 8.4 预构建 Rubric

Rubric 建议按以下层次管理：

```text
学科
  └─ 核心素养
       └─ 能力维度
            └─ 观察点
                 └─ C/B/A/S 行为描述
```

每次变更需要：

- 版本号；
- 修改人和依据；
- 专家审核状态；
- 生效时间；
- 受影响的学科和评测集；
- 回归结果。

### 8.5 评分指导与权重

技术方案二中给出了学习理解、实践应用、迁移创新的加权评分思路，其中高阶迁移权重更高。但文档也明确该评分规则仍需教育专家调整。因此面试中应把它描述为：

> 项目探索过加权总分用于课程级汇总，但最终核心判级仍优先使用 Rubric 的行为等级与证据匹配；权重只作为辅助统计，不替代专家校准。

不要把 1、1.5、2 的权重包装成已经得到教育科学证明的标准。

### 8.6 证据绑定

模型输入中每条课堂轮次提前分配 evidence_id。模型输出只能引用已有 ID。后处理重新从原始证据表取回文本，不能信任模型回写的 quote。

推荐流程：

```text
模型输出 evidence_id
  ↓
程序按 ID 查询原始对话
  ↓
比较模型 quote 与原文
  ↓
检查引用上下文和角色
  ↓
判断证据是否支持当前 Claim
```

### 8.7 trust_score

trust_score 不是模型自报置信度，而是证据完整性和匹配质量的综合分数。可包含：

- evidence_id 是否存在；
- quote 与原文是否匹配；
- 引用是否属于当前知识点案例；
- 引用角色和时间范围是否正确；
- 引用是否语义支持当前判级理由；
- 必要证据槽位是否齐全。

阈值低于 0.9 时阻断，意味着该结果不能进入正式输出，需要重试、修正或人工复核。

### 8.8 缓存设计

#### design_targets 缓存

缓存知识点、素养目标和 Rubric 选择等相对确定的中间结果，避免同一课程反复映射。

#### LLM 响应缓存

对相同输入指纹、Prompt 版本、模型版本和 Rubric 版本的调用结果缓存 24 小时。

#### SHA-256 增量证据构建

对课堂原始数据计算内容指纹。内容未变化时跳过证据层重建；内容变化时只重建受影响部分。

缓存键必须包含版本，否则 Rubric 或 Prompt 更新后可能错误复用旧评价。

### 8.9 降级保护

| 失败场景 | 降级策略 |
| --- | --- |
| 章节 API 失败 | 进入开放发现模式，并标记目标来源 |
| 任一评估模型失败 | 降级为可用单模型结果 |
| 仲裁模型失败 | 使用 conservative_min 保守等级 |
| 结构化评估失败 | 回退到受控单次 LLM 评估 |
| Schema 错误 | 自动修正并记录审计日志 |
| 引文校验失败 | 阻断当前结果，不生成正式判级 |
| 缓存不可用 | 回源执行，不影响正确性 |

### 8.10 为什么使用 conservative_min

当两个模型或两个评价结果不一致且仲裁不可用时，取较保守等级可以降低虚高评价风险。它不是永远正确，而是在教育质量评价中体现风险偏好：宁可暂时低估并等待复核，也不应无证据地给出更高等级。

## 9. Prompt、结构化输出与证据校验

### 9.1 Prompt 的职责分离

不要把所有任务塞进一个 Prompt。推荐拆分为：

1. 知识点提取；
2. 知识点—素养映射；
3. 课堂案例归纳；
4. Rubric 判级与证据绑定；
5. 教学建议生成；
6. 必要时的结构修正或复核。

拆分的原则不是越多越好，而是：

- 短而重要的任务不被长文本干扰；
- 中间结果可缓存；
- 每一阶段可以单独评测；
- 失败时只重试受影响节点。

### 9.2 一个合格评估 Prompt 的组成

```text
角色与任务边界
  + 当前课程、学科、年级
  + 当前知识点与目标素养
  + 允许使用的 Rubric
  + 按 evidence_id 编号的课堂案例
  + 判级规则与禁止事项
  + JSON Schema
  + 正反例或边界例
```

### 9.3 必须写入 Prompt 的禁止事项

- 不得创建输入中不存在的 evidence_id；
- 不得选择 Rubric 中不存在的等级或观察点；
- 不得仅根据教学目标推断课堂实际达成；
- 不得把教师说过等同于学生已经掌握；
- 不得在证据缺失时补写合理课堂行为；
- 不得把一节课扩大为长期教师能力结论；
- 输出必须符合 Schema，不添加额外解释。

### 9.4 五级引文匹配

技术方案使用“5级引文匹配”。面试时可以按以下工程口径解释，具体字段应与真实实现一致：

1. **ID 存在性**：evidence_id 是否真实存在；
2. **原文匹配**：去除空格和标点后，quote 是否与原文一致；
3. **模糊匹配**：处理转写轻微差异、同义替换或截断；
4. **上下文一致性**：引用是否属于当前案例、角色和时间范围；
5. **语义支持**：引用是否真的支持当前 good_point、gap 或等级理由。

前两级主要防止伪造，后三极主要防止“引用真实但与结论无关”。

### 9.5 为什么 0% 伪造 ID 不等于 0% 幻觉

28 次真实运行、178 条引用中没有出现模型编造 evidence_id，这证明 ID 约束和存在性校验有效。但仍可能存在：

- 引用真实但断章取义；
- 引用只支持“教师提问”，却被解释成“学生已经掌握”；
- 引用来自另一个知识点；
- 等级边界判断错误；
- 建议与差距不对应。

因此简历使用更严格的“无效引用率 <2%”，并把“伪造 ID 率”和“语义无效引用率”分开统计。

### 9.6 Schema 错误如何处理

处理顺序：

1. 严格解析；
2. 校验必填字段和枚举；
3. 对轻微格式问题做确定性修正；
4. 必要时带错误信息受控重试；
5. 仍失败则进入降级路径；
6. 所有修正写入审计日志。

不能把无法解析的自由文本继续传给后续节点，否则错误会在流水线中扩散。

### 9.7 如何降低长上下文干扰

- 先聚合案例，不直接注入全部课堂对话；
- 只选择当前知识点相关 Rubric；
- 每组最多 3 个知识点；
- 把确定性元数据保存在结构字段中；
- 教学目标提取与长文本评估分开；
- 对证据保留原文 ID，摘要只用于模型理解；
- 监控每阶段输入 Token 和输出 Token。

### 9.8 为什么不能暴力截断

直接截断可能刚好删除学生回答、教师反馈或等级判断的关键证据。项目优先通过知识点选择、时间切分、案例摘要和 Rubric 裁剪降低上下文，而不是从末尾粗暴删除。

## 10. 四个完整案例

### 10.1 案例一：三年级数学“认识周长”

#### 输入背景

- 学科：数学；
- 年级：三年级；
- 教学目标：理解周长含义，能够识别生活中的周长；
- 知识点：周长；
- 目标素养：量感；
- 素养映射置信度：0.90。

#### 案例聚合

系统从完整课堂中提取围绕“周长”的问答片段，例如：

```text
turn_012 教师：请大家摸一摸课桌边缘的一周
turn_013 学生：就是沿着桌面边走一圈
turn_015 教师：再找一找教室里哪些物体也有一周的长度
turn_016 学生：黑板、书本和窗户
turn_019 教师：同桌互相说一说为什么这些物体有周长
```

#### Rubric 匹配

系统读取“量感—学习理解—观察点1”的 C/B/A/S 描述。模型选择 B 级“良好”，理由是：

- 教师使用真实物体引导；
- 学生参与识别与讨论；
- 证据显示学生能够列举实例；
- 但没有充分证据证明学生能够自主归纳周长本质或迁移到复杂情境。

#### 结构化输出

```text
rubric_id：math_quantity_LU_1
level：B（良好）
evidence_ids：turn_012、turn_013、turn_015、turn_016、turn_019
good_points：真实情境引入、学生参与识别、组织同伴表达
gap：缺少学生自主归纳和反例辨析
```

#### 三层建议

- tier_1：让学生自行归纳“封闭图形一周长度”的共同特征；
- tier_2：加入不规则图形测量任务，推进到下一观察点；
- tier_3：在实际情境中比较不同方案，向实践应用维度发展。

#### 运行结果

- 1 个知识点；
- 1 条知识点—素养映射；
- 9 个候选观察点；
- 5 条证据标注；
- trust_score=1.0；
- 未发现伪造引用。

#### 案例体现什么

- 抽象素养被落到知识点和观察行为；
- 判级不是直接生成，而是 Rubric 匹配；
- 等级和建议都能回到具体课堂轮次；
- 系统能够说明“为什么是 B，而不是 A”。

### 10.2 案例二：一节课包含多个知识点

#### 问题

一节课同时包含概念引入、公式推导、例题应用和拓展讨论。如果把全部课堂对话和全部 Rubric 一次性输入，模型容易：

- 混淆不同知识点的证据；
- 使用后半节课的学生表现评价前半节知识点；
- 输出过长导致字段丢失；
- 把不同素养的行为描述混在一起。

#### 处理流程

1. 从教学目标提取多个知识点；
2. 对课堂轮次做知识点语义匹配；
3. 结合命中密度和时间段切分案例；
4. 按证据重叠和 Token 预算分组；
5. 每组最多 3 个知识点；
6. 只加载该组涉及的素养与 Rubric；
7. 每组独立结构化评估；
8. 最后按课程维度汇总，但保留知识点级结果。

#### 为什么不直接做课堂摘要

单一摘要会损失对话轮次、角色和细节，且摘要模型可能提前加入评价。项目使用“案例归纳 + 原始 evidence_id”双轨：摘要帮助模型理解，原始轮次负责证明结论。

#### 结果

相较初版动态评价表和长上下文链路，最终方案的 LLM 调用量降低约 40%，同时使每次调用的任务边界更清晰。

### 10.3 案例三：引用 ID 真实，但语义不支持结论

#### 模型候选输出

```text
结论：学生已经能够自主迁移周长知识解决新问题
引用：turn_016 “黑板、书本和窗户”
```

#### 校验结果

- evidence_id 存在；
- quote 与原文一致；
- 引用属于当前知识点；
- 但该证据只支持“学生能够列举实例”；
- 无法支持“自主迁移并解决新问题”。

#### 系统处理

语义支持层不通过，trust_score 低于 0.9，当前 A/S 级判定被阻断。系统可以：

- 回退为更保守等级；
- 要求模型基于已有证据重新判级；
- 输出缺失证据；
- 记录到审计日志供人工复核。

#### 价值

这个案例说明 evidence_id 白名单只能解决“引用是否伪造”，5 级匹配和语义校验才解决“引用是否真的支持结论”。

### 10.4 案例四：相同课堂重复评估

#### 初始情况

一次完整冷启动评估需要完成目标解析、知识点映射、证据构建和 LLM 判级，耗时约 2-5 分钟。

#### 第二次请求

系统依次检查：

1. 课堂原始数据 SHA-256 是否变化；
2. design_targets 是否命中；
3. 模型、Prompt 和 Rubric 版本是否一致；
4. 24 小时 LLM 响应缓存是否有效。

#### 缓存命中

- 证据层无变化，跳过重建；
- design_targets 直接复用；
- LLM 结果直接返回；
- 相同输入重评耗时降低到 2 秒以内。

#### 注意

`<2s` 只适用于缓存命中，不是冷启动端到端延迟。面试时必须主动说明这一点。

## 11. 数据集、评测体系与 A/B

### 11.1 数据集口径

项目构建 400 节人工标注课堂评估集：

| 数据划分 | 数量 | 用途 |
| --- | ---: | --- |
| 开发集 | 300 节 | Prompt、Rubric、规则和错误类型迭代 |
| 验证集 | 100 节 | 独立评估最终一致率和关键维度准确率 |
| 合计 | 400 节 | 教育评价离线开发与验证 |

为什么叫开发集而不是训练集：项目主要使用这 300 节做 Prompt 和规则迭代，没有证据表明完成了模型参数微调。使用“训练集”容易让面试官误以为做了 SFT。

### 11.2 标注单元

一节课可以产生多个评价单元。建议统一为：

```text
评价单元 = 知识点 × 目标素养 × 能力观察点
```

每个单元标注：

- 目标素养；
- 观察点；
- C/B/A/S 等级；
- 支持证据；
- good_points；
- gaps；
- 可接受的改进方向；
- 是否属于关键评价维度。

### 11.3 标注流程

推荐面试口径：

1. 系统根据教学目标生成知识点候选；
2. 标注人员确认知识点和目标素养；
3. 依据统一 Rubric 标注观察点和等级；
4. 绑定课堂原始 evidence_id；
5. 标记关键维度和可接受建议；
6. 分歧样本由更高资历专家仲裁；
7. 最终形成开发集和独立验证集。

如果真实项目只有单专家标注，不要声称双人标注和 Kappa；可以说“专家标注 + 抽样复核”。

### 11.4 核心指标定义

#### 与人工标准一致率 85%+

推荐定义：在 100 节独立验证课程产生的评价单元上，系统输出的观察点与 C/B/A/S 等级与专家标准完全一致的比例。

```text
一致率 = 完全匹配的评价单元数 / 全部有效评价单元数
```

如果实际统计按课程级主等级计算，应使用真实口径，不要混用。

#### 关键维度准确率 90%+

推荐定义：对每节课由专家指定的核心素养主目标或关键观察点，系统判级与专家一致的比例。

关键维度准确率高于总体一致率是合理的，因为系统对主教学目标的证据通常更完整，对边缘或弱证据维度更容易出现分歧。

#### 无效引用率 <2%

```text
无效引用率 = 无法通过证据校验的引用数 / 全部生成引用数
```

无效包括：

- evidence_id 不存在；
- quote 与原文不匹配；
- 引用超出当前知识点案例；
- 引用语义不能支持结论。

#### 伪造 evidence_id 率

28 次真实运行、178 条引用中，模型没有生成不存在的 evidence_id，因此该样本范围内的伪造 ID 率为 0%。这不是整体评价幻觉率。

#### LLM 调用量下降约 40%

```text
下降比例 =（初版平均调用数 - 最终版平均调用数）/ 初版平均调用数
```

A/B 必须使用同一批课程、同一模型、同一超时配置，并统计冷启动调用。缓存命中不应混入该指标。

### 11.5 A/B 方案定义

#### A 组：初版动态 Rubric

- 运行时生成 9 条候选期望表；
- 多阶段分别调用 LLM；
- 多知识点上下文较长；
- 证据校验和缓存能力较弱。

#### B 组：最终方案

- 预构建学科 Rubric；
- 按知识点聚合与分组；
- 每组最多 3 个知识点；
- 结构化评估与后处理；
- evidence_id + 5 级匹配 + trust_score；
- design_targets、响应缓存和增量构建。

### 11.6 核心结果

| 指标 | 结果 | 正确解释 |
| --- | ---: | --- |
| 数据集规模 | 400 节 | 300 开发 + 100 验证 |
| 与人工标准一致率 | 85%+ | 独立验证集上的评价一致性 |
| 关键维度准确率 | 90%+ | 主素养/关键观察点判级 |
| LLM 调用量 | 降低约 40% | 最终方案相对初版冷启动调用 |
| 无效引用率 | <2% | 严格证据校验口径 |
| 伪造 evidence_id | 0/178 | 28 次真实运行的窄口径结果 |
| 相同输入重评 | 2-5min → <2s | 缓存命中场景 |
| 无变化证据构建 | ~10s → <1s | SHA-256 检测无变化 |
| 测试 | 164 项通过 | 初版链路与关键规则测试 |

### 11.7 分层评测指标

#### 知识点提取

- 知识点 Precision/Recall；
- 同义知识点归一准确率；
- 主知识点命中率；
- 多知识点漏检率。

#### 素养映射

- 素养 Top-1/Top-3 命中率；
- 不存在标签生成率；
- 学科与学段约束违反率；
- 映射置信度校准情况。

#### 案例聚合

- 对话轮次覆盖率；
- 无关轮次混入率；
- 问答对完整率；
- 跨知识点污染率。

#### Rubric 判级

- 观察点准确率；
- C/B/A/S 等级准确率；
- 相邻等级误差率；
- 关键维度准确率；
- 与专家一致率。

#### 证据质量

- evidence_id 存在率；
- quote 匹配率；
- 语义支持率；
- 无效引用率；
- trust_score 阻断召回率和误阻断率。

#### 工程指标

- 平均 LLM 调用数；
- 输入/输出 Token；
- 冷启动和缓存命中耗时；
- P50/P95；
- 缓存命中率；
- Schema 修正率；
- 降级率和失败率。

### 11.8 消融实验如何设计

建议至少比较：

| 消融项 | 主要观察指标 |
| --- | --- |
| 去掉预构建 Rubric，恢复动态生成 | 复现一致性、调用量、Token |
| 去掉知识点分组 | 长上下文错误率、Schema 合法率 |
| 去掉语义级引文校验 | 无效引用率 |
| 去掉 trust_score 阻断 | 错误结论漏放率 |
| 去掉案例聚合，只用全文摘要 | 证据覆盖和跨知识点污染 |
| 去掉缓存 | 重评耗时和成本 |

没有真实消融数字时，面试中只讲实验设计和观察结论，不要临时编具体百分点。

### 11.9 如何保证评测可信

- 开发集与验证集隔离；
- 不根据验证集持续调 Prompt；
- 固定模型、Prompt、Rubric 和数据版本；
- 同一课堂的重复或相邻切片不要跨集合；
- 保存每个评价单元的原始证据和系统 Trace；
- 按学科、年级、知识点数和证据密度分层分析；
- 同时报告准确率、拒绝/阻断和覆盖率，避免只挑优势指标。

## 12. 工程化、缓存与稳定性

### 12.1 模块化边界

```text
Course Data Adapter
  ├─ Objective/Knowledge Extractor
  ├─ Competency Mapper
  ├─ Case Aggregator
  ├─ Rubric Registry
  ├─ Structured Evaluator
  ├─ Citation Validator
  ├─ Advice Generator
  ├─ Cache Manager
  └─ Audit Store
```

即使部署为单体，也应保持模块和数据契约分离，便于单独测试和替换模型。

### 12.2 缓存键设计

#### design_targets

```text
course_id
+ teaching_objective_hash
+ subject/grade
+ competency_mapping_version
+ rubric_version
```

#### LLM response

```text
normalized_input_hash
+ model_version
+ prompt_version
+ schema_version
+ rubric_version
```

#### evidence layer

```text
raw_classroom_data_SHA256
+ parser_version
+ aggregation_version
```

### 12.3 缓存失效

以下任一变化都应失效相关缓存：

- 原始课堂数据变化；
- 教学目标修正；
- Prompt 版本变化；
- 模型版本变化；
- Rubric 或课标版本变化；
- 证据聚合算法变化；
- Schema 变化。

### 12.4 为什么使用 SHA-256

SHA-256 在这里不是用于安全加密，而是作为稳定内容指纹：

- 同一内容生成相同指纹；
- 输入变化能够快速检测；
- 可作为缓存和审计的可复现锚点；
- 避免逐字段深度比较大体量课堂数据。

### 12.5 并发策略

可以并行的任务包括：

- 不同知识点组的评估；
- 不同模型的共识评估；
- 独立的证据匹配；
- 部分后处理和审计写入。

不能盲目并行的部分：

- 知识点提取依赖教学目标；
- Rubric 选择依赖素养映射；
- 教学建议依赖最终判级和 gaps；
- trust_score 必须在引用解析后计算。

### 12.6 超时与重试

- LLM API 临时故障自动重试最多 2 次；
- 重试应复用幂等请求 ID；
- Schema 错误和网络错误应分类处理；
- 网络错误可退避重试；
- 语义不合格不应无限重复同一 Prompt；
- 总超时必须限制，避免单节课评估无上限等待。

### 12.7 可观测性

每次运行至少记录：

- 各阶段耗时；
- 输入输出 Token；
- LLM 调用数；
- 缓存命中与失效原因；
- 知识点分组情况；
- Schema 错误；
- trust_score 分布；
- 阻断和降级 reason code；
- 模型、Prompt、Rubric 版本；
- 最终人工复核反馈。

### 12.8 失败模式与处理

| 失败模式 | 可能后果 | 处理方式 |
| --- | --- | --- |
| 章节 API 不可用 | 无法获得课前目标 | 开放发现模式并降低目标可信度 |
| 知识点提取错误 | 后续评价对象错误 | 受控候选、人工修正、审计来源 |
| 案例聚合混入无关对话 | 证据污染 | 时间/密度切分与跨知识点检查 |
| 上下文过长 | 格式漂移和漏证据 | 分组、裁剪、摘要+原始ID |
| LLM 输出非法 JSON | 后续无法解析 | Schema 修正、重试、降级 |
| 引用不存在 | 伪造证据 | 直接阻断 |
| 引用不支持结论 | 虚高判级 | 语义匹配、降级或人工复核 |
| 双模型结果冲突 | 判级不稳定 | 仲裁或 conservative_min |
| 缓存版本污染 | 返回旧评价 | 版本化缓存键与主动失效 |
| 专家 Rubric 不完善 | 评价体系偏差 | 版本管理、专家迭代和回归集 |

### 12.9 冷启动与缓存命中必须分开报告

推荐口径：

```text
冷启动：完整执行知识点、证据和 LLM 评估，约2-5分钟
缓存命中：相同输入、相同模型/Prompt/Rubric版本，<2秒
```

不要把缓存命中耗时包装成系统每次评估耗时。

### 12.10 双模型共识

方案支持双模型并行评估，约 3 分钟完成。它的价值是发现不稳定样本，而不是简单多数投票：

- 结果一致时提高稳定性信号；
- 结果相邻等级时可采用保守等级或仲裁；
- 差异过大时标记人工复核；
- 任一模型失败则降级为单模型；
- 仲裁失败时采用 conservative_min。

## 13. 项目高频面试问题与标准回答

### Q1：这个项目到底解决什么问题？

把依赖教研员经验的听评课，转换为有统一 Rubric、有课堂证据、可复现和可审计的自动化辅助评价。核心不是生成一段评价文字，而是让每个判级都能说明“依据什么标准、来自哪段课堂证据、为什么不是更高一级”。

### Q2：为什么不能直接让 LLM 对课堂打分？

直接评分时，模型同时决定评价维度、等级边界和结论，容易出现标准漂移和无依据解释。项目先固定 Rubric，再让模型在有限候选中匹配证据，把开放生成转化为受约束判级。

### Q3：为什么不直接用规则引擎？

规则可以检查 evidence_id、等级枚举和阈值，但无法仅靠关键词理解复杂课堂语义，例如学生是在机械复述还是主动解释。LLM 负责语义理解，规则负责边界和放行，两者结合。

### Q4：为什么最终选 Workflow，不选 Agent？

流程阶段和教育评价标准基本固定，Agent 的自由规划没有明显收益，反而增加黑盒、时延、成本和复现难度。工作流更适合逐阶段评测、缓存和审计。

### Q5：3×3×4 是什么？

3 个能力维度，每个维度 3 个观察点，共 9 个评价位置；每个位置再按 C/B/A/S 描述达标、良好、优秀、卓越四级课堂行为。

### Q6：为什么是 C/B/A/S，不是 1-4 分？

字母等级背后对应可观察的教师与学生行为差异，比单一分数更容易解释。分数可以做汇总，但最终判级必须回到行为描述。

### Q7：如何判断 B 而不是 A？

不是看语言感觉，而是对比 B 和 A 的关键行为差异。例如 B 可能是教师引导下参与练习，A 要求学生主动建构和解释。如果证据只有参与和列举，没有自主归纳，就不能升到 A。

### Q8：知识点和素养怎么映射？

模型读取教学目标、知识点定义和当前学科受控素养列表，从候选中选择 1-3 个最相关素养，并输出置信度和来源。模型不能自由创造素养标签。

### Q9：如果知识点提取错了怎么办？

知识点是整个评价链路的入口，因此要保留教学目标来源、规范化结果和人工修正入口；低置信度或开放发现模式结果进入审计，不能当作完全确定目标。

### Q10：案例聚合为什么重要？

课堂对话是碎片化的，单句不足以评价完整教学行为。案例聚合把相邻问答、学生反馈和教师追问按知识点组织起来，同时保留原始 evidence_id，减少证据断裂和跨知识点污染。

### Q11：为什么每组最多 3 个知识点？

初版在多知识点时容易出现上下文膨胀和注意力分散。3 是项目根据 Token 预算和稳定性选择的工作点，真正实现还会根据案例长度动态调整，不是普适常数。

### Q12：为什么预构建 Rubric 比运行时生成好？

预构建 Rubric 可以经过专家审核、版本化和回归测试，同一知识点使用统一等级边界；运行时生成更灵活，但容易波动、调用多且无法保证复现。

### Q13：预构建 Rubric 会不会失去灵活性？

会牺牲一部分开放性，因此 Rubric 按学科、素养、年级和版本管理，并允许专家迭代。项目优先选择“可解释和稳定”，而不是让模型临时创造更灵活的标准。

### Q14：evidence_id 是怎么防幻觉的？

每条原始课堂轮次预先分配 ID，模型只能引用已有 ID；程序按 ID 回查原文。它能防止伪造引用，但还需要 quote、上下文和语义支持检查，才能避免真实引用被错误解释。

### Q15：5级引文匹配是什么？

从 ID 存在、原文匹配、模糊匹配、上下文一致到语义支持逐层检查。前两层防伪造，后面三层防断章取义和证据—结论错配。

### Q16：trust_score 怎么得到？

它是证据完整性分数，不是 LLM 自报 confidence。综合 ID、quote、案例范围、角色时间和语义支持等检查，低于 0.9 时阻断正式输出。

### Q17：为什么阈值是 0.9？

这是在验证集上平衡错误漏放和误阻断选择的保守工作点。面试中不要说是通用阈值；模型、匹配算法或业务风险变化后需要重新标定。

### Q18：0% 幻觉率怎么解释？

准确说法是在 28 次真实运行、178 条引用中没有发现伪造 evidence_id。它是窄口径引用完整性结果，不等于判级、解释和建议在所有维度零幻觉。

### Q19：无效引用率 <2% 和 0/178 冲突吗？

不冲突。0/178 统计的是“ID 是否伪造”；<2% 使用更严格口径，还包括 quote 不匹配、上下文不一致和语义不支持。

### Q20：400 节数据是怎么用的？

300 节作为开发集，用于 Prompt、Rubric 和规则迭代；100 节独立验证，不参与持续调参，用来计算与人工标准一致率和关键维度准确率。

### Q21：为什么不说 300 节训练集？

因为项目主要进行 Prompt 和规则优化，不是模型参数训练。使用“开发集”更准确。

### Q22：85%+ 一致率怎么计算？

在验证集产生的有效评价单元上，系统的观察点和 C/B/A/S 等级与专家标准完全一致的比例。必须能说清统计单元和分母。

### Q23：关键维度准确率 90%+ 为什么高于总体一致率？

主教学目标通常证据更集中、Rubric 更明确；边缘维度和弱证据知识点更容易产生分歧。因此关键维度准确率高于全量评价单元是合理的。

### Q24：LLM 调用为什么能降低 40%？

主要来自三点：Rubric 从运行时生成改为预构建；多个知识点按组一次评估；确定性中间结果和重复请求通过缓存复用。40% 指同一批课程冷启动链路的平均调用数下降。

### Q25：相同输入为什么能从分钟级降到 2 秒内？

因为输入指纹、模型、Prompt 和 Rubric 版本都一致时，可以命中 design_targets 和 LLM 响应缓存，同时 SHA-256 判断证据层未变化。该指标不代表冷启动。

### Q26：如果 Rubric 更新，缓存怎么办？

缓存键包含 Rubric 版本；新版本发布后旧缓存自然失配，也可以主动批量失效。审计中同时保存旧版本，便于解释历史结果。

### Q27：模型输出非法 JSON 怎么办？

先做确定性轻量修正，再携带错误信息受控重试；仍失败则进入单次评估或保守降级。不能把自由文本直接传入下游。

### Q28：为什么教学建议分三层？

只给“提高课堂互动”过于空泛。三层建议分别对应当前观察点升一级、同维度下一观察点和下一大维度，能够直接对齐 Rubric 中的差距。

### Q29：项目最大的技术难点是什么？

不是调用 LLM，而是把抽象、主观的教育评价转换成可计算、可证据化、可复现的工程问题：既要保留模型对课堂语义的理解，又要限制它不能自由创造标准和证据。

### Q30：如果重新做一次，会改什么？

第一，扩大视觉、板书和课堂行为证据来源；第二，完善由专家撰写而非模型生成的 Rubric；第三，增加跨学科和跨年级验证；第四，引入更严格的多专家一致性指标；第五，持续分析 15% 左右的不一致样本并迭代聚合与等级边界。

## 14. Rubric、LLM-as-Judge 与评测八股

### 14.1 什么是 Rubric

Rubric 是带有明确评价维度、等级和行为锚点的评分规程。它不仅规定“评哪些方面”，还规定每个等级具体表现为什么。

本项目的 Rubric 包含：

- 学科核心素养；
- 能力维度；
- 观察点；
- C/B/A/S 等级；
- 教师行为；
- 学生行为；
- 必要课堂证据；
- 相邻等级差异。

### 14.2 Analytic Rubric 与 Holistic Rubric

- Holistic Rubric：对整节课给一个总体等级，速度快但难解释；
- Analytic Rubric：按多个维度分别评价，能定位优点和差距；
- 本项目以 Analytic Rubric 为主，最后可以汇总课程级结果。

### 14.3 什么是行为锚定

行为锚定是用可观察行为描述等级，而不是使用“很好、较好、一般”等抽象形容词。例如：

```text
弱锚定：学生理解较好
强锚定：学生能够独立举例并解释为什么该对象具有周长
```

强锚定更容易被模型、专家和教师共同理解。

### 14.4 什么是 LLM-as-Judge

LLM-as-Judge 使用 LLM 对另一个输出、案例或行为进行评价。典型风险包括：

- position bias：偏好先出现或后出现的答案；
- verbosity bias：偏好更长、更华丽的答案；
- self-enhancement bias：偏好与自身风格相似的输出；
- rubric ambiguity：评分标准含糊；
- reference leakage：参考答案暗示最终等级；
- stochasticity：重复运行结果波动。

本项目通过预构建 Rubric、结构化输出、低温、证据绑定和人工验证降低这些问题。

### 14.5 本项目为什么不是普通 LLM-as-Judge

普通 Judge 可能直接阅读课堂并给分。本项目增加了三个约束：

1. 评价对象按知识点聚合；
2. 判级只能在预定义 Rubric 中完成；
3. 每个理由必须绑定原始课堂证据。

因此更准确地说是“Evidence-grounded Rubric Judge”。

### 14.6 Pairwise、Pointwise 和 Listwise 评价

- Pointwise：单独对一个案例打分；
- Pairwise：比较两个课堂表现谁更符合标准；
- Listwise：对多个候选整体排序。

本项目线上主要是 Pointwise Rubric 判级；构建 Rubric 或验证等级边界时，可以使用 Pairwise 案例帮助专家确认 A 与 B 的差异。

### 14.7 Exact Match 与相邻等级容忍

严格一致率要求系统等级与专家完全相同。教育评价中 B 与 A 的分歧通常比 C 与 S 的分歧轻，因此还可以补充：

- Exact Match；
- ±1 等级容忍准确率；
- Mean Absolute Grade Error；
- 严重跨级错误率。

简历中的 85%+ 应保持一个固定口径，不要在面试中临时切换到更宽松指标。

### 14.8 混淆矩阵怎么看

四级判级可以构造 4×4 混淆矩阵。重点分析：

- 是否普遍高估；
- 是否把 B 大量判成 A；
- 是否存在 C 与 S 的严重跨级；
- 哪个学科或观察点最容易混淆。

### 14.9 Cohen's Kappa

Kappa 用于衡量两个评价者在扣除随机一致后的 agreement：

```text
κ = (p_o - p_e) / (1 - p_e)
```

- `p_o`：观察到的一致率；
- `p_e`：按双方等级分布随机情况下的预期一致率。

如果等级有顺序，可以使用 weighted Kappa，让相邻等级分歧惩罚小于跨级分歧。

如果项目没有计算 Kappa，面试时可以说这是下一步更严格的评测方式，不要伪装已有结果。

### 14.10 多专家分歧怎么处理

教育评价本身存在主观性。合理流程是：

- 先统一 Rubric 和标注指南；
- 标注一批校准样本；
- 统计分歧类型；
- 对边界样本仲裁；
- 必要时保留分布标签，而不是强行单标签；
- 系统准确率上限要考虑专家自身一致性。

### 14.11 Macro 与 Micro Accuracy

- Micro：把所有评价单元放在一起计算，样本多的学科权重大；
- Macro：先按学科、维度或类别计算，再平均，更能体现小类效果；
- 项目应同时看总体一致率和各学科/维度分层结果。

### 14.12 Precision、Recall、F1 在本项目中的用途

对于知识点、素养或关键证据识别：

```text
Precision = TP / (TP + FP)
Recall    = TP / (TP + FN)
F1        = 2PR / (P + R)
```

例如素养映射过多会提高 Recall 但降低 Precision，并让后续评估无意义地膨胀。

### 14.13 什么是校准

如果系统给出 0.9 置信度的样本中约 90% 确实正确，才说明概率经过良好校准。模型自报 confidence 通常不满足这个性质。

trust_score 更偏证据完整性分数，不应直接解释为“评价正确概率”。

### 14.14 如何评估教学建议

教学建议没有唯一标准，可以按以下维度评估：

- 是否对应当前 gap；
- 是否具体到课堂动作；
- 是否符合学科和年级；
- 是否能够在下一节课实施；
- 是否包含可观察的学生反馈；
- 是否错误引用课堂事实；
- 专家可接受率。

### 14.15 为什么准确率不能说明全部价值

即使最终等级准确率相同，一个能提供证据、差距和建议的系统，也比只输出等级更可用。项目应同时报告：

- 判级一致性；
- 证据有效性；
- 结果复现性；
- 建议可操作性；
- 成本和时延；
- 阻断与人工复核能力。

## 15. LLM、Prompt 与上下文工程八股

### 15.1 Temperature 的影响

Temperature 越低，输出分布越集中，重复运行更稳定。结构化评价通常使用低温或关闭采样，但低温只减少随机性，不能保证事实正确。

### 15.2 Top-k 与 Top-p

- Top-k：只在概率最高的 k 个 Token 中采样；
- Top-p：选择累计概率达到 p 的最小 Token 集合；
- 结构化判级通常不需要高随机采样。

### 15.3 System Prompt 与 User Prompt

System Prompt 定义模型角色、不可绕过的规则和输出契约；User Prompt 提供当前课程、案例和 Rubric。用户数据不能覆盖系统中的证据白名单和 Schema 规则。

### 15.4 Few-shot 的作用

Few-shot 示例可以帮助模型理解：

- B 与 A 的边界；
- 如何引用 evidence_id；
- 证据不足时如何降级；
- JSON 输出格式。

但示例过多会增加 Token，并可能引入样例偏置。应选择具有代表性的边界样本。

### 15.5 Chain-of-Thought 是否需要保存

线上不需要保存自由长 CoT。项目更适合保存：

- 选中的 Rubric ID；
- 证据 ID；
- good_points 与 gaps；
- reason code；
- 结构化修正日志。

这些信息足以审计，又比自由推理更稳定。

### 15.6 什么是 Structured Output

Structured Output 要求模型按照预定义 Schema 返回 JSON。它提高可解析性，但不能保证字段语义正确，因此仍需业务校验。

### 15.7 Constrained Decoding 与后验校验

- Constrained Decoding：生成过程中只允许合法 JSON Token 或枚举；
- 后验校验：生成后再检查 Schema 和业务规则；
- 最佳实践是两者结合：前者减少格式错误，后者发现语义错误。

### 15.8 Lost in the Middle

长上下文模型可能更关注开头和结尾，对中间信息利用较差。课堂证据很多时，关键学生回答可能被埋在中间。知识点切分和相关证据选择比单纯扩大上下文窗口更有效。

### 15.9 为什么更大上下文不等于更好

更大窗口只提高硬容量，不保证模型能够稳定关注所有信息，还会增加 Token 成本和推理时延。项目使用 Select、Compress、Isolate 思路：

- Select：选择当前知识点相关证据；
- Compress：生成教学行为摘要；
- Isolate：不同知识点组独立评估；
- Preserve：原始 evidence_id 不因摘要丢失。

### 15.10 什么是 Prompt Versioning

Prompt 作为系统配置必须版本化：

- 版本号；
- 修改内容；
- 适用模型；
- Rubric/Schema 依赖；
- 回归集结果；
- 发布时间和回滚点。

缓存键和审计日志必须包含 Prompt 版本。

### 15.11 Prompt Injection 是否存在

课堂对话本身可能出现类似“忽略之前指令”的文本。系统必须把课堂内容作为数据字段，而不是直接拼接成高权限指令；Rubric、工具和输出限制由系统层和代码控制。

### 15.12 为什么不能只靠 Prompt 说“不要幻觉”

Prompt 是软约束，模型仍可能违反。项目使用：

- evidence_id 白名单；
- Rubric 枚举；
- Schema；
- 引文回查；
- trust_score 阻断；
- 降级与审计。

这些是可执行约束，而不是语言提醒。

### 15.13 什么是幂等 LLM 请求

同一输入指纹、模型、Prompt、Rubric 和 Schema 版本对应同一个请求键。重复请求优先返回缓存结果，避免重复扣费和结果波动。

### 15.14 如何定位 Prompt 问题

按错误类型分层：

- 知识点错：目标提取 Prompt 或词表；
- 素养错：候选集合或定义不清；
- 等级偏高：Rubric 边界或示例偏置；
- 引用错：证据格式或语义校验不足；
- JSON 错：Schema 太复杂或输出约束不足；
- 建议空泛：gap 与建议生成未强绑定。

### 15.15 Prompt 优化为什么不能只看几个案例

对单个失败样本不断加规则，容易过拟合和产生 Prompt spaghetti。正确方式是：

- 维护错误分类；
- 用开发集迭代；
- 固定验证集；
- 每次修改跑完整回归；
- 记录对不同学科和等级的影响。

## 16. Workflow、缓存与可靠性八股

### 16.1 Workflow 与 Agent 的区别

- Workflow：节点与路径主要预定义；
- Agent：模型运行时决定下一步动作；
- 本项目的评价路径固定，因此 Workflow 更合适。

### 16.2 状态机的关键要素

状态、节点、条件、转移、终止和错误路径。即使没有使用特定状态机框架，工作流也应明确每阶段输入、输出和失败处理。

### 16.3 什么是幂等

同一操作执行一次或多次，最终效果一致。评估接口通常通过输入指纹和 run_id 保证幂等，避免重复创建审计记录或重复扣费。

### 16.4 为什么重试要分类

- 网络超时、限流：可退避重试；
- 非法 JSON：可带错误反馈重试；
- 证据语义不支持：不应原样无限重试；
- 权限或参数错误：应直接失败；
- 非幂等写操作：必须有请求 ID 防重。

### 16.5 指数退避与 jitter

指数退避逐步延长等待，避免持续打满故障服务；jitter 加随机扰动，避免多个请求同时重试形成惊群。

### 16.6 熔断器

- Closed：正常请求；
- Open：错误率过高时快速失败；
- Half-open：少量探测，成功后恢复。

LLM API 连续故障时，熔断可以保护工作流线程和上游服务。

### 16.7 缓存穿透、击穿和雪崩

- 穿透：请求不存在的课程，可做短期空值缓存；
- 击穿：热点课程缓存失效，大量请求同时回源，可加互斥锁；
- 雪崩：大量缓存同时过期，可增加随机 TTL 和限流。

### 16.8 Cache Aside

典型流程：

```text
读缓存 → 命中则返回
       → 未命中则执行计算 → 写缓存 → 返回
```

更新时通常先更新真实数据，再删除缓存；本项目还需要版本化键，避免 Rubric 更新后读取旧结果。

### 16.9 为什么缓存不能只用 course_id

同一课程可能更换教学目标、原始对话、模型、Prompt 或 Rubric。只用 course_id 会造成脏读。缓存键必须包含输入 Hash 和各组件版本。

### 16.10 乐观锁与并发写

多个知识点组并行评估后汇总到同一 run，可以使用版本号或 compare-and-swap 防止后写覆盖先写。冲突时重读状态并合并，而不是静默覆盖。

### 16.11 P50、P95 与平均耗时

- 平均值容易被少量极慢请求影响或掩盖；
- P50 代表典型用户体验；
- P95 代表尾延迟；
- 项目应分别报告冷启动、缓存命中、单模型和双模型路径。

### 16.12 可观测性三支柱

- Logs：错误、reason code、输入版本；
- Metrics：调用数、Token、延迟、缓存命中、阻断率；
- Traces：一节课经过哪些节点、在哪里降级、为什么输出当前等级。

### 16.13 为什么审计日志不能只存最终答案

只存最终答案无法回答：

- 使用了哪个 Rubric；
- 引用了哪些课堂轮次；
- 是否发生 Schema 修正；
- 是否命中缓存；
- 是否经过保守降级；
- 哪个模型和 Prompt 产生结果。

### 16.14 什么是灰度发布

新 Prompt、模型或 Rubric 先作用于固定小比例课程，与旧版本并行比较一致率、无效引用率、阻断率和耗时，异常时快速回滚。

### 16.15 为什么模型、Prompt、Rubric 要一起版本化

评价结果由三者共同决定。只记录模型名无法复现同一结果；任何一项变化都可能改变知识点映射、等级边界和引用选择。

## 17. 教育评价与业务理解八股

### 17.1 核心素养为什么难评

核心素养是跨知识、跨情境、长期发展的能力，不是一次答题结果。课堂自动评价只能观察其在当前知识点和教学活动中的外显行为。

### 17.2 形成性评价与总结性评价

- 形成性评价：关注学习过程，用于及时改进；
- 总结性评价：关注一个阶段后的最终结果；
- 本项目更接近形成性课堂评价，为教研和教师改进提供证据。

### 17.3 评价有效性

有效性不是一个单一数字，至少包括：

- 内容效度：Rubric 是否覆盖应评内容；
- 构念效度：观察行为是否真的代表目标素养；
- 标准关联效度：系统结果是否与专家或其他外部标准相关；
- 后果效度：评价是否产生合理教学改进，而不是误导教师。

### 17.4 评价信度

信度关注结果稳定性：

- 同一课堂重复评估是否一致；
- 不同模型是否一致；
- 不同专家是否一致；
- 不同时间或学科是否稳定。

缓存提高的是工程复现，不等于评价工具本身具有高教育测量信度。

### 17.5 为什么教师行为和学生行为都要看

教师设计了活动，不代表学生已经产生对应学习行为；只有学生反馈，没有教学行为又难以分析教学原因。因此 Rubric 同时包含教师动作和学生外显表现。

### 17.6 为什么互动越多不等于素养越高

互动次数只是表面指标。机械齐答、无效追问或与知识点无关的讨论不能证明高阶能力。系统关注互动是否体现目标知识、能力要素和学生主动建构。

### 17.7 为什么一节课不能评价长期素养

一节课的教学目标、证据和情境有限。系统输出应表述为“本节课在某知识点上的观察表现”，而不是“该教师长期迁移创新能力为 B”。

### 17.8 如何处理学科差异

三大维度可以作为共通框架，但具体观察点、行为锚定和典型证据需要学科专属设计。数学中的量感、物理中的科学推理、语文中的语言运用不能只换标签复用同一描述。

### 17.9 如何处理年级差异

同一知识点或素养在不同学段的行为要求不同。Rubric 需要携带年级/学段和版本信息，知识点映射也必须读取教学目标上下文。

### 17.10 如何处理方言和转写错误

- 保留 ASR 置信度；
- 对低置信度片段降低证据权重；
- 使用上下文纠错但保留原文；
- 关键证据抽样人工复核；
- 不让模型把模糊转写解释成确定事实。

### 17.11 没有视频证据有什么影响

对板书、动作、课堂组织和非语言反馈的评价会受限。因此系统必须明确证据来源是问答与互动文本，不能声称覆盖全部课堂质量。

### 17.12 教学建议为什么要关注实施成本

建议如果需要大量额外课时、设备或超出学生认知水平，即使理论上正确也不可用。Before→Problem→After→Why 可以继续扩展实施成本、可追问方式和期望学生证据。

## 18. 压力追问与答题边界

### 18.1 “你这不就是写了一套高级 Prompt 吗？”

回答重点：Prompt 只是语义执行层。项目的核心工程还包括教育评价建模、知识点案例聚合、版本化 Rubric、结构化数据契约、证据回查、trust_score 阻断、缓存、增量构建、降级和离线评测。任何一个 Prompt 都不能替代这些确定性机制。

### 18.2 “评分标准还是模型写的，怎么保证科学？”

初版确实由模型动态生成候选期望，主要用于验证方案；最终架构改为预构建、版本化 Rubric，并通过专家标注数据迭代。系统降低模型自由度，但评价体系的科学性最终仍需要教育专家持续校准，这是项目明确边界。

### 18.3 “为什么不直接微调一个分类模型？”

当前数据规模和学科差异下，直接训练统一分类器成本高、可解释性差，也难处理等级理由和教学建议。Rubric + LLM 可以快速适配学科并提供证据解释；当数据积累足够后，可以针对知识点映射或等级分类做专门微调。

### 18.4 “400 节数据够吗？”

它足以支持 Prompt/Rubric 的初步离线验证，但不足以证明跨地区、跨学科和长期泛化。项目把 100 节作为独立验证集，不把 85%+ 宣称为行业普适准确率；下一步需要扩大分布和多专家标注。

### 18.5 “85% 一致率是不是因为专家自己也不一致？”

教育评价确实存在专家分歧，因此更严格的做法是先测专家间一致率，再解释系统与专家的一致率。如果专家自身只有 88% 一致，系统 85% 的含义与专家 99% 一致时不同。项目后续会补充 weighted Kappa 和分歧样本仲裁。

### 18.6 “0% 幻觉率明显是夸大吧？”

我不会把它解释成整体零幻觉。准确口径是 28 次运行、178 条引用中没有伪造 evidence_id。对于引用语义有效性使用更严格指标，无效引用率控制在 2% 以内；判级正确性另用人工一致率衡量。

### 18.7 “既然无效引用率 <2%，为什么准确率只有 85%？”

两者衡量不同问题。引用有效说明结论有真实课堂依据，但相同证据仍可能在 B/A 边界上判断不同；85% 衡量最终 Rubric 判级与专家是否一致。

### 18.8 “40% 调用下降是因为用了缓存吗？”

核心 40% 口径应统计冷启动，主要来自预构建 Rubric 和知识点分组；缓存用于重复评估耗时优化，不能混入冷启动调用下降，否则 A/B 不公平。

### 18.9 “相同输入 <2s，不就是缓存返回吗？”

是的，所以我会明确它是缓存命中场景。工程价值在于同一课堂经常因规则、展示或人工复核被重复查看，复用结果能降低成本并提高复现性，但不能把它包装成冷启动推理速度。

### 18.10 “为什么不把整节课一次性交给长上下文模型？”

大窗口只解决硬容量，不解决注意力稀释、跨知识点证据污染和成本问题。按知识点组织上下文还提供了更自然的评价单元和审计边界。

### 18.11 “预构建所有学科 Rubric 成本不是很高吗？”

成本确实前移，但评价标准本来就应该由专家设计和复用。动态生成每次成本低在前期、风险高在运行期；预构建把不稳定工作变成一次专家建设和持续版本维护，更适合正式评价系统。

### 18.12 “LLM 只是在表里选，技术含量在哪里？”

真正难点是如何构造这张表、如何把课堂证据切分到正确知识点、如何定义等级边界、如何验证引用以及如何保证复现。把开放问题转成受约束决策本身就是系统设计价值。

### 18.13 “如果 Rubric 本身错了，模型再稳定也没用吧？”

是的。系统只能保证按照当前版本 Rubric 稳定执行，不能自动证明 Rubric 科学。为此需要专家审核、版本化、回归集、人工反馈和旧版本审计。

### 18.14 “为什么 trust_score 低于 0.9 就阻断？”

阈值来自项目验证集上的风险权衡，并体现教育评价的保守策略。它不是通用常数；如果误阻断过高，需要重新标定或拆分不同风险场景阈值。

### 18.15 “同一模型既理解证据又打分，会不会自证循环？”

项目不直接信任模型写回的 quote，而是按 evidence_id 回查原文并由代码完成多级匹配；最终判级还与专家验证集对比。进一步降低相关性偏差可以使用独立复核模型或规则 Judge。

### 18.16 “为什么不是多模型投票？”

多数投票不能解决共同偏差。双模型主要用于发现不稳定样本；冲突时采用仲裁、保守等级或人工复核，而不是简单少数服从多数。

### 18.17 “你的结果是否能用于教师绩效考核？”

当前不建议直接用于高风险绩效决策。数据缺少完整视觉证据，单节课也不能代表长期能力。更合理的定位是教研辅助和形成性反馈。

### 18.18 “这个项目最失败的一类样本是什么？”

可以回答：知识点证据稀疏、学生互动少、转写质量差或同一课堂多个知识点高度交叉时，案例聚合和等级边界最容易出错。这类样本推动了知识点分组、证据质量标记和保守阻断设计。

### 18.19 “你个人负责什么？”

统一回答模板：

```text
我主要负责从评价问题建模到核心工作流的设计与落地，重点包括三部分：第一，把新课标素养拆解为知识点—能力要素—四级行为 Rubric；第二，推动初版动态评价表演进为预构建 Rubric 和知识点分组评估，解决调用链和上下文问题；第三，设计 evidence_id、引文匹配、trust_score、缓存与降级机制，并基于人工标注数据迭代 Prompt 和评测。课程数据接入、教育专家标注和部分产品交互由团队协作，我负责接口约束、评估链路和端到端验证。
```

必须根据真实分工修改，不要把专家标注、产品或团队代码全部说成个人完成。

### 18.20 “项目有没有真正上线？”

如果处于离线验证或试运行，应准确回答“完成真实课堂数据多轮验证，具备进一步接入条件”，不要把试运行包装为大规模生产上线。重点讲清当前阶段、用户范围、数据闭环和下一步上线条件。

## 19. 数字口径防守卡

简历上的每个数字都要能够用“对象—分母—基线—条件—结论”五句话守住。

### 19.1 `3×3` 能力要素

**对象**：每个知识点涉及的目标素养。  
**定义**：3 个能力维度，每维 3 个观察点，共 9 个观察位置。  
**作用**：把抽象素养拆成可观察、可绑定课堂证据的评价单元。  
**不是**：3 个模型、9 次调用或 9 个素养。  
**追问准备**：能够举出“周长—量感—学习理解—观察点1”的完整例子。

### 19.2 `C/B/A/S` 四级

**对象**：每一个观察点的行为水平。  
**定义**：达标、良好、优秀、卓越。  
**核心差异**：从教师主导与学生模仿，逐渐过渡到学生主动建构和自主探究。  
**不是**：考试成绩或教师长期绩效。  
**追问准备**：能够解释 B 和 A 的关键证据差异。

### 19.3 每组 `≤3` 个知识点

**对象**：一次结构化 LLM 评估调用的知识点数量。  
**基线问题**：多知识点完整输入导致上下文膨胀和注意力分散。  
**选择依据**：项目 Token 预算与稳定性工作点。  
**边界**：不是永远恰好 3 个，短案例可以合并，长案例应进一步拆分。  
**追问准备**：解释为什么不暴力截断、如何处理证据重叠。

### 19.4 LLM 调用量降低约 `40%`

**比较对象**：初版动态 Rubric 链路与最终预构建 Rubric + 分组链路。  
**统计条件**：同一批课程、同一模型、冷启动、不计缓存命中。  
**主要来源**：取消运行时 Rubric 生成、合并知识点组评估、复用确定性中间结果。  
**公式**：`(A组平均调用数-B组平均调用数)/A组平均调用数`。  
**边界**：不是 Token 或费用一定下降 40%，三者需要分别统计。

### 19.5 `trust_score <0.9` 自动阻断

**对象**：证据完整性与匹配质量。  
**输入**：ID、quote、上下文、角色时间、语义支持和必要证据覆盖。  
**决策**：低于 0.9 时不能进入正式输出。  
**边界**：trust_score 不是判级正确概率。  
**追问准备**：阈值需要在验证集上重新标定，能解释误阻断和漏放。

### 19.6 无效引用率 `<2%`

**分子**：无法通过 ID、原文、上下文或语义支持检查的引用。  
**分母**：系统生成的全部引用。  
**统计目标**：衡量证据引用质量。  
**不是**：整体判级错误率或全部幻觉率。  
**追问准备**：能够举出“ID 真实但语义不支持”的例子。

### 19.7 `28` 次运行、`178` 条引用、伪造 ID 为 `0`

**样本范围**：方案二实际跑通记录。  
**统计对象**：模型是否生成输入中不存在的 evidence_id。  
**结果**：178 条引用未发现伪造 ID。  
**边界**：样本量有限，只证明 ID 白名单机制在这批运行中有效。  
**不要说**：系统实现 0% 综合幻觉率。

### 19.8 `400` 节人工标注课程

**数据构成**：300 节开发集 + 100 节独立验证集。  
**开发集用途**：迭代 Prompt、Rubric、证据规则和错误处理。  
**验证集用途**：最终一次或受控次数评估。  
**边界**：不是 400 条简单文本，也不等于完成模型 SFT。  
**追问准备**：标注单位、专家来源、分歧处理、数据隔离。

### 19.9 一致率 `85%+`

**对象**：验证集上的系统评价与专家标准。  
**推荐统计单元**：知识点×素养×观察点评价单元。  
**匹配要求**：观察点和等级完全匹配。  
**边界**：不是所有教学建议 85% 完全一致。  
**追问准备**：能够说明剩余不一致主要来自边界等级、证据稀疏和案例聚合。

### 19.10 关键维度准确率 `90%+`

**对象**：每节课专家指定的核心素养主目标或关键观察点。  
**为什么更高**：主目标证据更集中、Rubric 更明确。  
**边界**：不要把“关键维度”临时改成表现最好的维度；其定义必须在评测前固定。  
**追问准备**：能够给出关键维度选择规则。

### 19.11 相同输入重评 `2-5min → <2s`

**基线**：完整冷启动执行。  
**优化场景**：输入、模型、Prompt、Rubric 和证据版本一致，命中缓存。  
**优化机制**：design_targets 缓存、LLM 响应缓存、SHA-256 增量判断。  
**边界**：不是所有首次评估都小于 2 秒。  
**追问准备**：缓存键、TTL、失效和脏数据处理。

### 19.12 证据层构建 `~10s → <1s`

**对象**：课堂证据解析与构建。  
**条件**：原始数据 SHA-256 未变化。  
**机制**：跳过无变化内容的重复解析。  
**边界**：输入变化时仍需执行增量或完整重建。

### 19.13 `164` 项测试通过

**对象**：项目关键规则、结构化输出、证据和流程路径。  
**价值**：说明工作流不仅靠手工 Demo。  
**边界**：测试通过不等于教育评价科学性已经被证明。  
**追问准备**：至少能说出 Schema、引文、分组、缓存和降级五类测试。

### 19.14 数字审计总表

| 数字 | 一句话口径 | 最容易踩的坑 |
| --- | --- | --- |
| 3×3×4 | 9个观察点，每点4级行为标准 | 说成9个素养或12级 |
| ≤3 | 单次评估最多3个知识点 | 说成固定分组算法 |
| -40% | 冷启动LLM调用量下降 | 把缓存收益混进去 |
| 0.9 | 证据可信度阻断阈值 | 说成90%判级概率 |
| <2% | 严格口径无效引用率 | 说成全部幻觉率 |
| 0/178 | 伪造evidence_id为0 | 扩大到所有语义错误 |
| 400 | 300开发+100验证课程 | 说成模型训练数据 |
| 85%+ | 系统与专家评价一致率 | 不知道统计单元 |
| 90%+ | 预先定义的关键维度准确率 | 事后挑最好维度 |
| <2s | 相同输入缓存命中 | 说成冷启动延迟 |

## 21. 面试前一页速记

### 项目三个业务问题

1. 传统听评课依赖专家经验，评价口径不统一；
2. 课堂评价结论缺少原始问答证据；
3. 素养抽象且长期，LLM 直接评分容易标准漂移。

### 核心理论

```text
知识是能力的载体
能力是素养的外显
知识点 × 能力要素 → 可观察课堂行为
```

### 最终架构

```text
课程数据
→ 教学目标/知识点
→ 素养映射
→ 知识点案例聚合
→ 预构建3×3×4 Rubric
→ 每组≤3知识点结构化评估
→ evidence_id与5级引文匹配
→ trust_score阻断
→ 三层建议、缓存与审计
```

### 四个核心价值

1. 把抽象教育评价转成可计算 Rubric；
2. 把开放式评分转成受约束判级；
3. 把评价结论绑定课堂原始证据；
4. 把一次性 Demo 做成可复现、有降级的工作流。

### 架构演进

```text
初版：运行时生成评价框架
问题：调用长、上下文大、标准波动
最终：预构建Rubric + 知识点分组 + 证据后处理
结果：LLM调用降低约40%
```

### 核心参数

- 3 个能力维度；
- 每维 3 个观察点；
- 每点 C/B/A/S 四级；
- 每组最多 3 个知识点；
- trust_score 阈值 0.9；
- LLM 缓存 TTL 24 小时；
- API 临时失败重试最多 2 次。

### 核心结果

- 400 节人工标注课程：300 开发 + 100 验证；
- 与人工标准一致率 85%+；
- 关键维度准确率 90%+；
- LLM 调用量降低约 40%；
- 无效引用率 <2%；
- 28 次运行、178 条引用中无伪造 evidence_id；
- 相同输入重评 2-5min → <2s；
- 无变化证据构建 ~10s → <1s；
- 164 项测试通过。

### 最关键案例

```text
三年级数学“周长”
→ 映射量感
→ 读取学习理解Rubric
→ 聚合教师引导、学生列举和同桌讨论证据
→ 匹配B级良好
→ 5条evidence_id通过校验
→ 建议学生自主归纳并迁移到不规则图形
```

### 三条原则

- 教学目标说明“应该教什么”，课堂证据说明“实际发生什么”；
- 引用存在不等于引用支持结论；
- 缓存保证工程复现，专家 Rubric 和验证集保证评价尺度。

### 最后一句总结

> 项目价值不在于让大模型写一段更漂亮的评课意见，而在于把主观课堂评价重构为“有统一参照、有原始证据、有确定性校验、有量化评测”的受约束决策系统。

## 23. 最终答题边界

### 可以坚定表达

- 项目核心不是自由评分，而是 Rubric 约束与证据判级；
- 初版到最终方案体现了稳定性、上下文和成本之间的架构权衡；
- evidence_id、Schema、trust_score 和审计是可执行约束；
- 缓存、增量构建和降级说明项目具备工程完整性；
- 400 节数据和独立验证集为 Prompt/Rubric 迭代提供了量化反馈。

### 需要带限定词

- “0% 幻觉”限定为 178 条引用中无伪造 evidence_id；
- “<2s”限定为相同输入缓存命中；
- “85%+”限定为当前验证集和既定统计单元；
- “90%+”限定为预先定义的关键维度；
- “40%”限定为最终方案相对初版的冷启动 LLM 调用量；
- “可上线”限定为已完成真实数据验证并具备进一步接入条件。

### 不应宣称

- 系统已经彻底杜绝所有幻觉；
- 单节课可以准确评价教师长期素养；
- 缓存命中速度就是首次评估速度；
- 400 节数据已经证明跨地区、跨学科普适性；
- 预构建 Rubric 已经获得完整教育科学认证；
- 使用了实际项目中不存在的 Agent、知识图谱、微调或数据库组件。

### 最终提醒

> 好的项目包装不是把每个结果说到最大，而是让面试官连续追问架构、数据、指标和边界时，所有回答仍然属于同一个系统、同一组实验和同一套事实。

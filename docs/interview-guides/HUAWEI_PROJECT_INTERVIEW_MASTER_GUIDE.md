# 华为网络产品智能故障诊断：项目面试总复习手册

> 使用口径：本文依据当前简历中的华为项目表述、SMK 与显式故障诊断项目截图及已有讨论整理。内容分为三类：**已确认事实**、**需要核实的数字**和**建议采用的答题框架**。正式面试前，应使用真实代码、运行日志、评测表和团队分工逐项校准；没有记录支撑的指标不能从“理论估算”升级为“实测结果”。

## 0. 如何使用这份文档

这不是普通项目说明，而是一份面向 AI 应用工程师、Agent 工程师、Java/后端工程师和智能运维方向的项目答辩底稿。建议按以下顺序复习：

1. 先背熟华为整体经历的 30 秒介绍，以及两个子项目各自的 30 秒介绍；
2. 再掌握“为什么需要两套系统”，明确静默断言故障和显式报错故障的证据差异；
3. 深入 SMK 的 10 阶段流水线、质量门控、运行时变更归因、调用链回溯和根因搜索；
4. 深入显式故障引擎的三级渐进诊断、grep 与 CodeGraph 协同、知识演进闭环和 RCA 强引用；
5. 最后用高频题、压力追问、数字口径卡和当前简历逐句答辩做三层追问演练。

面试中的总主线始终是：

> 网络产品测试故障不是同一种证据条件：一类只有断言结果不一致，缺少错误码和异常堆栈；另一类已经暴露错误码、栈帧或设备特征。我的工作不是用一条万能 Prompt 处理所有问题，而是从 0 到 1 构建两套证据驱动的诊断系统：前者通过运行时证据、近期变更和双向调用链逐步收敛根因，后者利用强锚点做三级渐进诊断；两者都把结论绑定真实代码证据并保留可复核轨迹。

### 0.1 标记说明

| 标记 | 含义 | 面试使用方式 |
| --- | --- | --- |
| 已确认 | 已进入当前简历或由用户明确说明 | 可以稳定表达，但仍要能解释实现 |
| 待核实 | 不同版本材料存在冲突，或缺少统计定义 | 面试前核对原始记录；未核对时不用精确数字 |
| 建议口径 | 为帮助表达而整理的方法论 | 可以使用，但不能冒充项目中不存在的模块 |
| 示例 | 用于练习讲解的虚拟故障过程 | 必须替换为本人真实案例后再说“实际案例” |

### 0.2 项目记忆钩子

只记两句话：

> **SMK：弱证据故障，用运行时范围和近期变更做消噪，再沿调用图双向逼近根因。**

> **显式故障：强锚点故障，先查错误码和栈帧，再匹配设备特征，最后才进入跨仓深度 RCA。**

### 0.3 面试时不要混淆的六组概念

| 容易混淆 | 正确区分 |
| --- | --- |
| 断言失败与“完全没有错误” | 测试结果明确失败，但通常没有可直接定位业务代码的错误码或异常堆栈 |
| 10 阶段流水线与 10 个子 Agent | 流水线是逻辑阶段；是否严格一阶段对应一个 Agent，应以真实实现为准 |
| AST/正则与候选减少 | AST/正则负责从 diff 中抽取方法；真正的范围收敛来自运行时仓库、近期 MR 和调用链等证据交集 |
| caller 与 callee | caller 是“谁调用我”，callee 是“我调用谁”；双向搜索分别回答上游入口和下游影响 |
| 路径覆盖与根因命中率 | 路径覆盖描述可探索的图范围；命中率描述真实根因是否进入候选，不能互换 |
| CodeGraph 能力与个人贡献 | CodeGraph/tree-sitter 若为平台已有能力，应说“采用并编排”，不能说成自己从零实现图引擎 |

## 1. 项目定位

### 1.1 华为经历的一句话定位

针对网络产品测试中的断言类静默故障与显式报错故障，作为 Owner 从 0 到 1 构建两套代码级根因诊断系统：SMK 侧以 Agent 流水线组织运行时证据、近期 MR 与跨仓调用链，显式故障侧以错误码/栈帧和设备特征为锚点进行渐进式 RCA，统一输出可复核、可审计的代码证据链。

### 1.2 华为经历 30 秒介绍

```text
我在华为主要做网络产品测试故障的智能根因诊断，分别覆盖两种证据条件。第一套是 SMK 断言类故障定位：这类问题测试结果不一致，但通常没有明确错误码和异常堆栈。我从 0 到 1 设计了 10 阶段 Agent 流水线，把测试日志、运行时 JAR、近期 MR、跨仓调用链和根因推断串起来，并用 Dispatcher、manifest 状态机和质量门控保证断点续跑，将单故障平均定位耗时从人工约 12 小时降到 2～3 小时。第二套面向已有错误码或异常栈的显式故障，采用“强锚点检索—设备特征匹配—深度 RCA”三级诊断，并结合 grep 与 CodeGraph 完成跨仓、跨语言追踪，最终结论都绑定真实代码、路径和行号。
```

### 1.3 华为经历两分钟介绍

```text
这段实习解决的是网络产品测试中的代码级故障定位问题。我先把故障按证据强弱分成两类，而不是强行用同一套流程。

第一类是 SMK 断言类静默故障。测试会表现为期望值和实际值不一致，但业务链路通常没有直接抛出可用的错误码或异常堆栈。传统方式需要工程师人工翻测试日志、定位请求线程、查运行时 JAR、比对近期 MR，再跨多个代码仓追调用链，平均约 12 小时。作为 Owner，我从 0 到 1 构建了 10 阶段定位流水线，通过 Dispatcher 和 manifest 状态机调度各阶段，所有阶段都有前置依赖和产物合法性校验，异常中断后可以从最近完成节点继续。证据侧先从日志识别相关请求和线程，再由运行时 JAR 映射实际代码仓，对近期 MR 做方法级变更归因，最后结合 JACG caller/callee 双向回溯、接口多态补全和四维交集搜索收敛根因候选。整个推理只基于可回查证据，过程写入 exploration_log，单故障定位耗时降到 2～3 小时。

第二类是显式故障，输入里已经有错误码、异常栈或稳定的设备特征。我设计三级渐进诊断：优先用错误码和栈帧做高精度锚点检索；不满足多证据一致性时，再做设备特征匹配；前两级无法解释时才进入深度 RCA。深度阶段由 grep 负责高召回地寻找文本锚点、配置和特殊字符串，CodeGraph 负责沿结构化调用关系扩展 caller/callee 和跨语言链路。为了避免一次性诊断结果无法复用，我还设计了人工核验后再按 Schema 入库的知识闭环，并要求 RCA 报告严格区分直接原因与根本原因，引用真实代码片段、文件路径和行号。

两个项目的共同价值是把依赖专家经验的人工排查，重构为证据驱动、可恢复、可复核的诊断工作流；差异在于 SMK 需要从弱证据中逐层收敛，显式故障则应该优先利用强锚点，避免一开始就做昂贵的全量代码分析。
```

### 1.4 五分钟介绍结构

五分钟介绍按以下顺序讲：

1. 网络产品故障定位为什么慢，以及两类故障的证据差异；
2. 先讲 SMK：10 阶段流水线和人工约 12h → 2～3h；
3. 用一张证据漏斗解释“日志 → 运行时仓库 → 近期变更 → 调用链 → 根因”；
4. 讲质量门控、状态持久化和可审计推理，证明系统不是一次性脚本；
5. 再讲显式故障：三级渐进诊断以及 grep + CodeGraph 分工；
6. 讲知识演进闭环和 RCA 强引用；
7. 最后总结两套系统如何覆盖不同证据条件，并主动说明当前指标和能力边界。

### 1.5 项目最准确的技术标签

推荐使用：

- Agentic Workflow / Multi-stage Diagnostic Workflow；
- Evidence-driven Root Cause Analysis；
- Static Call Graph Analysis；
- Change Impact Analysis；
- Program Analysis；
- Human-in-the-loop Knowledge Evolution；
- Reproducible / Auditable Diagnosis；
- AIOps / Intelligent Troubleshooting。

谨慎使用：

- “全自动修复”：当前材料支持自动定位与诊断，不支持自动修改并上线；
- “100% 根因定位”：没有对应评测；
- “解决反射和动态代理”：静态图无法完整还原所有运行时动态行为，更准确是补全或缓解；
- “知识库自动学习”：必须强调人工确认后入库；
- “理论覆盖率提升到 30%～50%”：这是能力边界估算，不是实测结果。

## 2. 为什么需要两套诊断系统

### 2.1 两类故障的本质差异

| 维度 | SMK 断言类故障 | 显式故障 |
| --- | --- | --- |
| 表面现象 | 期望值与实际值不一致 | 明确错误码、异常堆栈或稳定特征 |
| 初始证据 | 弱、分散、噪声大 | 强锚点较多 |
| 主要难点 | 找到相关线程、运行时范围、近期变化和隐含调用路径 | 判断强锚点是否真能解释当前设备与故障 |
| 搜索策略 | 从运行时证据和变更集合逐层收敛 | 从强锚点开始，证据不足再逐级扩大 |
| 主要程序分析 | JAR—仓库映射、MR 方法、JACG 双向调用链、交集增强 | grep 文本搜索、CodeGraph 结构推理、跨语言追踪 |
| 终止条件 | 候选根因具备完整可回查证据链 | 某一级证据达到一致性门槛并可定位代码位置 |
| 典型输出 | 根因候选、证据路径、RCA 报告、exploration_log | 直接原因、根本原因、代码强引用、诊断模式摘要 |

### 2.2 为什么不能只保留一个项目

两个项目不是重复堆砌，含金量分别体现在：

- SMK 展示复杂工作流编排、低信噪比证据消噪、Java 静态分析和搜索算法；
- 显式故障引擎展示分层路由、跨语言代码检索、知识闭环和结果工程化；
- 两者共同形成“弱证据逆向收敛 + 强证据渐进诊断”的完整故障诊断方法论。

简历中 SMK 用三条展开，显式故障用两条概括是合理的：SMK 是主项目，负责展示深度；显式故障负责扩大问题覆盖面和形成体系感。

### 2.3 统一故障路由

建议在白板上这样画：

```text
故障输入
  │
  ├─ 有稳定错误码 / 可用异常栈 / 明确设备特征
  │      └─ 显式故障三级渐进诊断
  │
  └─ 只有断言不一致 / 业务结果异常 / 缺少强锚点
         └─ SMK 10阶段证据收敛流水线

两条链路最终统一输出：
根因候选 + 真实代码证据 + 路径/行号 + 推理轨迹 + RCA报告
```

### 2.4 统一设计原则

1. **先利用确定性证据，再使用推理能力**：日志、JAR、MR、调用图和代码片段优先；
2. **先缩小空间，再让模型判断**：不把整个组织代码仓直接塞给 LLM；
3. **事实与假设分层**：候选排序可以包含启发式，但最终结论必须回到可核验事实；
4. **强锚点优先，昂贵分析后置**：显式故障不必一开始就全量 CodeGraph；
5. **每步可恢复、可复现**：状态和产物持久化，不依赖一次连续会话；
6. **新知识必须人工确认**：防止错误诊断污染知识库。

### 2.5 系统边界

- 系统定位的是代码级根因候选，不等同于自动完成修复、回归和发布；
- 静态调用图无法完整解析反射目标、动态代理对象和所有运行时多态；
- MR 关联是一种高价值先验，不代表“最近改动一定有罪”；
- 没有真实代码引用、日志或调用链支撑时，LLM 的解释不能升级为最终根因；
- CodeGraph、JACG 等平台或开源能力要与个人设计工作明确分开；
- 诊断结果的最终确认仍可能需要模块 Owner、复现环境或回归验证。

## 3. 总体架构

```text
测试平台 / 一线工程师
        │
        ├─ SMK：测试日志、请求信息、断言差异、时间范围
        └─ 显式：错误码、异常栈、设备号、日志、问题描述
        ▼
Input Validator + Fault Router
        ▼
Dispatcher / Diagnostic Orchestrator
        │
        ├──────────────── SMK 弱证据链 ────────────────┐
        │  日志解析 → 服务日志 → 运行时JAR → 代码仓     │
        │  → 近期MR → 入口 → 调用图 → 双向交集 → RCA   │
        │                                               │
        └────────────── 显式强锚点链 ───────────────────┤
           错误码/栈帧 → 设备特征 → grep + CodeGraph   │
           → 深度RCA → 人工确认 → 约束入库             │
                                                        ▼
Evidence Store / manifest / exploration_log
        ▼
RCA Report：直接原因、根本原因、代码片段、路径、行号、调用链
```

### 3.1 共同组件

| 组件 | 作用 |
| --- | --- |
| Input Validator | 校验日志、时间范围、设备信息、仓库配置和输入文件 |
| Dispatcher | 根据阶段依赖和 manifest 状态派发任务 |
| Manifest Store | 持久化 pending/running/done/failed 和产物路径 |
| Evidence Store | 保存日志片段、JAR、仓库、MR、方法和调用链证据 |
| Program Analysis Tools | JACG、CodeGraph、AST/文本解析、grep |
| Evidence Ranker | 根据相关性、变更、距离和多源一致性排序候选 |
| RCA Generator | 只基于已收集证据生成报告，不凭空补代码 |
| Audit Trace | 保存每一步输入、规则、输出和失败原因 |

### 3.2 为什么是“工作流 + Agent”，不是开放式 Agent

主链路的阶段、依赖和质量门是确定的，只有局部搜索、候选选择和根因解释需要推理能力。因此最准确的描述是：

> 以确定性工作流承载依赖、状态和安全边界，以子 Agent 执行需要语义理解或假设生成的阶段。

如果面试官问“为什么不直接 ReAct”，回答：开放式 ReAct 很难保证跨小时任务的恢复、产物完整性、停止条件和可审计性；本项目更适合显式状态机。

## 4. 核心数据结构与证据契约

本节是建议答题模型，不要求实际字段名完全一致。面试时应替换为真实 Schema。

### 4.1 FaultCase

```json
{
  "case_id": "CASE-001",
  "fault_type": "assertion_silent | explicit",
  "occurred_at": "...",
  "device_id": "...",
  "request_id": "...",
  "test_log": "...",
  "error_code": null,
  "stack_trace": null,
  "workspace": "..."
}
```

### 4.2 ManifestStage

```json
{
  "stage": "mr_method_extraction",
  "status": "pending | running | done | failed",
  "attempt": 1,
  "inputs": ["runtime_repos.json", "mr_list.json"],
  "outputs": ["changed_methods.json"],
  "schema_version": "v1",
  "started_at": "...",
  "finished_at": "...",
  "error": null
}
```

关键点：`done` 不能只表示进程退出码为 0，还必须表示输出存在、格式合法、关键字段完整。

### 4.3 EvidenceItem

建议至少包含：

- `evidence_id`；
- 来源类型：test_log / service_log / jar / mr / diff / call_graph / code；
- 来源位置：文件、仓库、commit、方法、行号；
- 与候选根因的关系：supports / contradicts / contextual；
- 生成方式和工具版本；
- 原始内容 hash；
- 时间戳和可信等级。

### 4.4 ChangedMethod

```text
repository + commit/MR + file_path + class_name
+ fully_qualified_method + signature + diff_hunk + changed_lines
```

全限定方法名用于跨仓和调用图对齐。只保存短方法名容易把不同包、不同重载混在一起。

### 4.5 CallPath

```text
entry_method → ... → candidate_method
direction: caller | callee | bidirectional
edge_type: direct | interface | configured-polymorphism | api-anchor | stack-anchor
evidence: graph record / source snippet / mapping config
```

### 4.6 RCAResult

建议字段：

- 故障摘要；
- 直接原因；
- 根本原因；
- 受影响服务/模块；
- 关键调用路径；
- 真实代码片段、文件路径和行号；
- 证据清单和反证；
- 修复建议与验证建议；
- 未确认假设；
- `exploration_log` 或 trace ID。

## 5. SMK 断言类故障自动定位 Agent

### 5.1 业务背景

SMK 测试失败表现为期望结果和实际结果不一致。它“有失败结果”，但通常缺少能直接跳到业务代码的错误码或异常堆栈。人工排查通常要完成：

1. 从海量自动化测试日志中找到当前请求；
2. 追到服务端相关日志和线程；
3. 判断运行时实际加载了哪些 JAR；
4. 映射到对应代码仓并查看近期 MR；
5. 找到协议/API 入口；
6. 跨仓追调用链；
7. 比较变更、日志和调用路径，形成根因假设；
8. 回到代码验证并撰写 RCA。

难点不是“看懂一段日志”，而是把分散在日志、制品、仓库、MR 和调用关系中的异构证据对齐到同一故障。

### 5.2 项目目标

- 自动完成重复、耗时的证据收集和范围缩小；
- 将代码搜索从组织级仓库范围收敛到运行时相关方法；
- 在缺少强锚点时仍能生成可核验的根因候选；
- 阶段失败可诊断、可恢复，不因一个子任务失败而全链路重跑；
- 最终报告可复现，不依赖 LLM 随机生成一套故事。

### 5.3 SMK 30 秒介绍

```text
SMK 处理的是测试断言不一致但缺少明确错误码和异常堆栈的静默故障。我从 0 到 1 设计了 10 阶段 Agent 流水线，把日志解析、服务日志采集、运行时 JAR 到代码仓映射、近期 MR 方法提取、入口解析、JACG 调用链追踪、双向交集和根因推断串起来。编排层使用 Dispatcher 与 manifest 状态机，每一阶段都做前置依赖和产物合法性校验并支持断点续跑。最终将单故障平均定位耗时从人工约 12 小时降到 2～3 小时，根因推理过程通过 exploration_log 可复现、可审计。
```

## 6. SMK 十阶段端到端流程

```text
1 日志解析
→ 2 服务端日志采集
→ 3 代码仓拉取
→ 4 MR变更提取
→ 5 入口解析
→ 6 调用链追踪
→ 7 证据准备
→ 8 双向搜索
→ 9 根因推断
→ 10 报告输出
```

### 6.1 日志解析

目标：从自动化测试日志中抽取请求标识、时间范围、断言期望/实际值、接口信息、设备信息和可能相关线程。

关键设计：

- 不使用固定时间窗口粗暴截取全部日志；
- 根据 request ID、线程关系、调用先后和业务标识做相关性分类；
- 可将线程分为 MAIN、RELATED、MAYBE、UNRELATED；
- 原始日志和过滤后日志都保留，防止消噪不可逆。

待核实案例：某次请求日志从 `201,278` 行压缩到 `618` 行。这个数字只能作为具体案例，不宜说成所有故障的平均值；早期材料曾出现 `608` 行，面试前必须以真实产物统一。

### 6.2 服务端日志采集

根据测试侧提取的设备、服务、请求和时间信息，通过 SSH 或内部日志接口拉取对应运行日志，并记录：

- 机器/容器与服务实例；
- 日志文件和时间范围；
- 拉取命令、返回码与文件 hash；
- 缺失或轮转情况。

这一步的价值是把“测试侧看到的结果错误”与“服务端实际执行轨迹”连接起来。

### 6.3 代码仓拉取

不是默认拉取所有仓库，而是根据运行时 JAR、服务清单和接口归属生成候选仓库集合。仓库拉取需要固定分支、commit 或 MR 时间点，避免分析时工作区漂移。

### 6.4 MR 变更提取

以故障发生时间为锚点，获取约定窗口内合入的 MR；现有材料使用“故障前 3 天”口径。对每个 MR 提取：

- 仓库与 MR/commit；
- 变更文件；
- diff hunk；
- 变更方法的全限定名和签名；
- 变更行范围。

三天窗口是工程先验，不是因果证明。窗口过短会漏掉滞后暴露问题，过长会显著增加噪声；更好的设计是允许按发布批次、部署时间和故障类型配置。

### 6.5 入口解析

将测试接口或协议请求映射为 Java 入口方法。已有材料涉及：

- OpenAPI YAML；
- RESTCONF RPC；
- RESTCONF DATA；
- YANG 命名到 Java 实现的转换；
- URL / RPC 名称 /资源路径到 Controller 或服务入口的映射。

入口解析决定调用图从哪里开始。如果入口错了，后续图搜索再准确也会在错误子图里工作。

### 6.6 调用链追踪

通过 JACG 构建 Java 调用图并写入 H2 嵌入式数据库，沿 caller 和 callee 两个方向搜索：

- callee：从请求入口向下看可能执行了哪些方法；
- caller：从近期变更方法向上看是否能回到请求入口；
- 双向交汇：减少单向遍历的噪声与漏召回。

### 6.7 证据准备

把日志、MR、入口和调用路径整理为结构化上下文。已有材料出现“9 维证据上下文”和“10 因子嫌疑排序”两种说法，建议区分为：

- 10 因子：候选方法排序所用的特征；
- 9 维上下文：提供给根因推断的证据类别。

如果真实实现中两者实际是同一组信号，应统一说“多维证据”，不要制造两个看似不同的创新点。

### 6.8 双向搜索

从请求入口向下搜索 callee，同时从 MR 变更方法向上搜索 caller，在接口等价、API 映射和可用异常线索等维度做交集增强。详细设计见第 9 节。

### 6.9 根因推断

根因推断遵循“观察事实优先于统计相关性”：

1. 先列出已证实事实；
2. 再生成候选假设；
3. 对每个假设列支持证据和反证；
4. 规则阶段完成确定性评分；
5. LLM 只在已收敛候选上做解释与归纳；
6. 无法闭环时保留不确定性，不强行输出唯一根因。

### 6.10 报告输出

报告应回答：

- 故障现象是什么；
- 哪条请求和运行时路径与故障相关；
- 哪个近期变更进入了实际调用路径；
- 直接原因与根本原因分别是什么；
- 证据对应哪个仓库、文件、方法和行号；
- 有什么反证和未确认点；
- 建议如何修复和回归验证。

## 7. Dispatcher、manifest 与质量门控

### 7.1 为什么不能写成一个长脚本

这条链路跨日志服务、代码仓、MR 平台、JAR、静态分析和模型调用，运行时间长、外部依赖多。一个长脚本的问题是：

- 任一阶段失败可能从头重跑；
- 难以判断产物是缺失、损坏还是空结果；
- 阶段耦合，替换工具或并行执行困难；
- 无法精确重放某一步；
- 很难审计某个结论使用了哪一版输入。

### 7.2 五阶段协议

```text
前置条件检查
→ 状态标记 running
→ 子Agent/工具派发
→ 输出合法性校验
→ 状态标记 done
```

失败时记录 `failed`、错误类型、重试次数和已有产物，不把失败阶段误标为完成。

### 7.3 质量门控检查什么

| 门控 | 示例 |
| --- | --- |
| 前置依赖 | MR 提取必须等运行时仓库集合和时间范围就绪 |
| 文件存在性 | 输出文件真实存在且非临时半成品 |
| JSON 合法性 | 可解析、Schema 版本匹配 |
| 关键字段完整性 | 方法必须有仓库、文件、全限定名和变更范围 |
| 语义合法性 | `done` 但候选仓库为空时，要区分真实空结果和采集失败 |
| 版本一致性 | JAR、代码仓和 MR 时间点属于同一次分析快照 |

### 7.4 状态转移

```text
pending → running → done
              └──→ failed → pending（满足可重试条件）
```

关键约束：

- `done` 是终态，除非输入版本发生变化；
- 重新执行前检查幂等键；
- 依赖产物 hash 变化时，下游阶段必须失效重算；
- `running` 超过租约时间需要由恢复逻辑判断是否成为僵尸任务。

### 7.5 断点续跑如何工作

1. 启动时读取 manifest；
2. 校验已完成阶段的产物和输入 hash；
3. 找到第一个未完成或已失效阶段；
4. 从该阶段继续；
5. 已完成且输入未变化的阶段直接复用。

断点续跑的价值不仅是省时间，更是让长链路具备生产级可恢复性。

### 7.6 并行化边界

适合并行：

- 多服务日志拉取；
- 多 JAR/仓库映射；
- 多仓 MR 与 diff 提取；
- 独立仓库的调用图准备。

必须等待依赖：

- 运行时仓库集合未确定前，不能最终确认 MR 交集；
- 入口未解析前，无法完成入口到候选方法的路径判断；
- 证据未闭环前，不能生成最终 RCA。

## 8. 运行时变更归因与证据消噪

### 8.1 证据漏斗

```text
组织级代码空间
  ↓ 运行时JAR/服务映射
本次故障可能执行的代码仓
  ↓ 故障时间与近期MR
时间相关变更
  ↓ diff方法抽取
方法级变更集合
  ↓ 入口与调用图
路径相关候选
  ↓ 日志、语义与多维证据
根因候选
```

每一层都回答一个不同问题：

- JAR：本次运行可能加载了什么；
- MR：最近什么发生了变化；
- 方法抽取：变化具体落在哪里；
- 调用图：请求是否可能经过这些变化；
- 日志和代码：哪个变化能解释当前现象。

### 8.2 运行时 JAR 为什么比仓库列表更有价值

组织拥有某仓库，不等于当前环境加载了它。运行时 JAR 把代码搜索空间约束到实际部署制品，能够排除大量“理论相关但本次未运行”的仓库。

映射通常需要处理：

- JAR 名称与仓库名不一致；
- 一个仓库产出多个 JAR；
- 一个服务加载多个仓库制品；
- 版本后缀、snapshot 和 shaded JAR；
- 内部模块与公共依赖。

### 8.3 AST + 正则到底做什么

准确口径：

> 在已经筛选出的 MR diff 中，把文件级变化转成方法级变化，并生成可与调用图对齐的全限定方法标识。

它不直接解释“为什么 1,178 个候选会降到 156 个”。候选减少来自前置仓库交集、方法级归因和后续路径过滤的共同作用。

建议实现解释：

- Java 优先使用 `javalang` AST，识别类、内部类、方法、构造器和签名；
- Kotlin 或 AST 解析失败场景使用文本/正则作为降级；
- 正则只用于候选召回，再结合文件、类、行号和调用图校验；
- 对宏、生成代码、匿名类和复杂语法保留 `parse_status`，不要静默丢失。

不要说“正则精确解析 Java/Kotlin”。正则适合兜底召回，不适合证明完整语法正确性。

### 8.4 为什么需要全限定方法名

`save()`、`build()`、`process()` 在多个包和类中都会出现。全限定名至少包含包、类、方法和必要签名，可以：

- 与 JACG 节点稳定对齐；
- 区分重载；
- 跨仓去重；
- 把 diff 精确绑定到调用路径。

### 8.5 三组数字如何正确解释

已有材料存在三组范围数字：

1. `200+` 代码仓 → `12` 个相关仓；
2. `45` 个近期 MR 仓 → 与运行时仓库交集后 `8` 个；
3. `1,178` 个 MR 候选方法 → `156` 个方法。

它们可能描述不同层级，也可能来自不同故障样本。一个可能但必须核实的解释是：

```text
组织代码空间 200+ 仓
→ 运行时制品映射 12 仓

同一时间窗口内有 MR 的 45 仓
∩ 运行时 12 仓
→ 8 个交集仓

交集仓内 MR diff 抽取 1,178 个变更方法
→ 结合入口/调用路径等证据保留 156 个候选
```

在原始数据未核对前，不要把这条链当成确定事实。当前简历已经改用“方法级变更归因链路”，这是更稳健的高层表述。

### 8.6 为什么“近期 MR”不是根因结论

最近变更只提高先验概率，不能证明因果。至少还要满足：

- 变更进入当前部署版本；
- 所属代码被本次运行加载；
- 调用路径与故障请求相关；
- 变更语义能够解释断言差异；
- 没有更强的反证。

## 9. JACG 调用图与四维双向搜索

### 9.1 为什么选 JACG + H2

JACG 用于从 Java 字节码构建方法调用关系，H2 作为嵌入式存储保存调用边和查询结果。项目场景下的优势是：

- 基于实际 JAR 分析，比只看源码目录更接近部署制品；
- H2 嵌入式、部署依赖轻，已有材料口径是“仅需 JDK8”；
- caller/callee 查询适合程序化批处理；
- 结果可以持久化，便于重复搜索和审计。

需要主动说明：JACG 是调用图工具，不是由本人从零实现的字节码分析框架；个人价值在于运行时范围约束、图查询策略、接口补全、交集算法和诊断编排。

### 9.2 caller 与 callee

假设 `A → B → C`：

- 对 B 来说，A 是 caller；
- 对 B 来说，C 是 callee；
- 从入口 A 向下找 C 是 callee 搜索；
- 从变更 C 向上找入口 A 是 caller 回溯。

双向搜索的好处：单向从入口向下可能展开巨大子图；单向从 MR 向上也可能到达大量公共调用者。两边同时约束，交汇点更有辨识度。

### 9.3 接口多态为什么导致断链

源码中调用的是接口 `Service.query()`，运行时实际执行 `ServiceImpl.query()`。如果调用图只保留静态声明，入口路径和实现方法可能无法直接相连。

已有材料中的三层补全机制：

1. `_ITF` 接口调用记录；
2. 接口—实现或多态配置；
3. BFS 按优先级扩展实现节点。

这是一种候选补全，不等于完整还原运行时分派。补全后仍要用运行时 JAR、Spring 配置、日志或代码证据验证。

### 9.4 AOP、动态代理与反射的边界

- Spring AOP 常通过代理对象插入切面，静态图可能只看到代理或接口；
- JDK 动态代理和 CGLIB 会改变实际接收者；
- 反射通过字符串或运行时 Class 对象选择目标；
- 静态分析通常只能过近似，存在漏边和伪边。

建议答法：

> 我没有宣称静态图能完全解决动态语义，而是用接口记录、配置、API 锚点和可用运行时证据补全候选路径，再通过多源交集降低误报。

### 9.5 四维交集

根据现有材料可解释为：

| 维度 | 含义 | 价值 |
| --- | --- | --- |
| D1 精确方法 | 全限定方法或签名直接匹配 | 精度最高 |
| D2 接口等价 | 接口声明与实现方法等价扩展 | 缓解多态断链 |
| D3 API 锚定 | RequestMapping、RPC、RESTCONF 等入口映射 | 从业务接口连接到代码入口 |
| D4 异常线索交叉 | 可用异常栈或服务日志栈与路径交叉 | 有栈时提供强证据 |

注意：SMK “通常没有异常堆栈”，不是任何服务日志都绝对不可能出现异常。D4 应作为可选证据维度；不能把它说成每个 SMK 样本都具备。

### 9.6 双向搜索的抽象算法

设：

- `E`：请求入口集合；
- `M`：近期 MR 变更方法集合；
- `Down(E)`：从入口向下的 callee 可达集合；
- `Up(M)`：从变更向上的 caller 可达集合；
- `Expand(M)`：接口等价、API 映射等补全集合。

基础候选：

```text
C1 = Down(E) ∩ M
```

增强候选：

```text
C2 = Down(E) ∩ Up(Expand(M))
```

再结合日志相关性、路径距离、变更时间、接口匹配和代码语义做排序。真实实现可能不是严格集合公式，但白板上这样解释能清晰展示思路。

### 9.7 多维嫌疑排序

候选排序可以包含以下类型特征；只有真实使用的特征才能说成项目实现：

- 是否属于运行时 JAR 对应仓库；
- 是否在故障时间窗口的 MR 中；
- 与入口的最短路径距离；
- caller/callee 两侧是否同时可达；
- 是否命中接口等价或 API 锚点；
- 日志关键词或请求标识相关度；
- 变更行是否涉及断言字段、返回值或状态转换；
- 是否存在异常或错误线索；
- 多源证据是否一致；
- 是否存在反证。

如果排序第一阶段是规则加权，应该明确说“确定性启发式排序”，不要模糊成训练过的机器学习模型。

### 9.8 “命中率提升约 40%”如何防守

当前简历使用：相较“请求调用链 ∩ MR 方法”的单向交集基线，根因候选命中率提升约 40%。面试前必须确认：

- 样本量是多少；
- 根因金标如何得到；
- 命中是 Top-1、Top-5、Top-K 还是候选集合包含；
- 基线是否只做 D1 单向精确交集；
- 40% 是相对提升还是 40 个百分点；
- 是否在相同 MR 窗口、入口和代码版本上比较。

推荐公式：

```text
Hit@K = Top-K候选中包含人工确认根因的故障数 / 有金标的故障总数
Relative Gain = (Hit_new - Hit_base) / Hit_base
```

如果缺少完整评测记录，面试时降级为：

> 在内部故障回放中，相比仅做入口调用链与 MR 方法精确交集，加入 caller 回溯和接口/API 等价扩展后，更多已确认根因能够进入候选集合；简历中的约 40% 需要以当时评测表的 Hit@K 口径为准。

绝不能把“理论路径范围从 5%～15% 扩展到 30%～50%”说成实测命中率提升 30%。前者是能力边界估算，后者还混淆了百分点和相对百分比。

## 10. 根因推断、exploration_log 与审计

### 10.1 为什么不能让 LLM 直接读全部材料

- 代码和日志上下文远超稳定窗口；
- 大量无关 MR 会形成强烈近期偏见；
- LLM 容易把相关性写成因果；
- 直接生成无法证明路径真实存在；
- 同一问题重复运行可能给出不同故事。

因此先由确定性工具做检索、映射、交集和排序，再让模型在小规模候选上完成语义解释。

### 10.2 侦探式推理框架

```text
Observation：日志、制品、代码和图上的已知事实
→ Hypothesis：能够解释现象的候选原因
→ Prediction：如果假设成立，还应看到什么证据
→ Verification：回查代码、路径和日志
→ Elimination：记录反证并淘汰候选
→ Conclusion：输出最小充分根因或保留不确定性
```

“观察优先于统计相关性”的意思是：MR 越近、关键词越像只能提高候选优先级；最终结论必须由实际路径和代码语义支撑。

### 10.3 Phase 1 规则评分

若真实实现采用规则加权，可解释为：第一阶段只使用明确特征做确定性评分，例如运行时命中、路径可达、接口一致、日志对应和变更时间；LLM 不修改规则分数，只负责解释高排名候选和提出验证动作。

### 10.4 exploration_log 应记录什么

- 本轮问题或待验证假设；
- 使用的工具和参数；
- 输入产物 ID 与版本；
- 返回的新证据；
- 候选分数变化；
- 支持证据和反证；
- 淘汰原因；
- 下一步动作；
- 最终停止原因。

不要记录或对外暴露不受控的长篇私有 CoT。可审计的是结构化决策轨迹、规则命中和证据变化。

### 10.5 如何避免“最近 MR 背锅”

- 保留“无近期变更根因”的候选通道；
- 要求 MR 方法实际进入请求相关路径；
- 检查变更是否进入当前部署制品；
- 对候选建立反事实问题：若回退该变更，现象是否应消失；
- 输出未确认项和替代假设；
- 最终通过复现、回滚或定向测试确认因果。

## 11. 显式故障智能诊断引擎

### 11.1 业务背景

这类故障已经给出错误码、异常堆栈、设备号或稳定特殊字符串，初始证据明显强于 SMK。传统人工排查仍可能面临：

- 错误码只映射到表层模块，没有解释根本原因；
- 栈帧停留在公共框架或跨语言边界；
- 同一错误码在不同设备/版本下含义不同；
- 故障跨多个代码仓和服务；
- 排查经验只留在个人脑中，下一次重复劳动。

### 11.2 项目目标

- 用最便宜、最强的证据优先完成诊断；
- 只有前一级证据不足时才扩大搜索范围；
- 将文本锚点与结构化调用链结合；
- 报告必须落到真实服务、模块、代码和行号；
- 经人工确认的新知识可以结构化复用。

### 11.3 30 秒介绍

```text
显式故障诊断引擎面向已经具备错误码、异常堆栈或设备特征的故障。我从 0 到 1 设计了“错误码/栈帧锚点检索→设备特征匹配→深度 RCA”三级渐进链路，以多证据一致性作为是否结束当前层或进入下一层的门槛。深度 RCA 中 grep 负责高召回地定位文本锚点和配置，CodeGraph 负责沿 caller/callee 做跨仓、跨语言结构推理。诊断结果强制区分直接原因和根本原因，并绑定真实代码片段、文件路径和行号；未收录错误码或设备特征只有经人工确认后才按 Schema 入库，形成可控的知识演进闭环。
```

## 12. 三级渐进诊断

```text
Level 1：错误码 / 栈帧锚点检索
   │ 证据足够 → 输出并复核
   ▼ 不足
Level 2：设备特征 / 特殊字符串匹配
   │ 证据足够 → 输出并复核
   ▼ 不足
Level 3：grep + CodeGraph 深度RCA
   ▼
真实代码强引用 + 人工确认 + 可复用模式
```

### 12.1 Level 1：错误码与栈帧锚点

输入可能包括：

- 外部错误码，如固定格式十六进制码；
- 异常类型；
- 首个业务栈帧；
- 文件、类、方法；
- 日志中的明确错误消息。

检索不只看“错误码是否出现”，还要检查：

- 版本是否一致；
- 设备/产品线是否适用；
- 栈帧是否来自业务代码而非公共框架；
- 知识项是否有已确认来源；
- 当前日志是否满足该错误的必要条件。

### 12.2 Level 2：设备特征匹配

当错误码未收录或含义过宽时，使用设备号、驱动名、板卡类型、特殊字符串、配置项和日志指纹匹配特定故障模式。

设备特征不能只做单关键词命中。更可靠的做法是组合：

- 产品/设备身份；
- 特殊字符串；
- 日志上下文；
- 版本或配置；
- 已知根因的适用条件。

材料中提到“多证据一致性作为层级门槛”。若实际实现有“两项命中”或其他阈值，面试前核对配置；未核实时只说“达到配置化一致性门槛”。

### 12.3 Level 3：深度 RCA

前两级不能形成完整解释时，才进入跨仓代码分析：

1. grep 在错误文本、栈帧、配置、协议字段和代码中找锚点；
2. CodeGraph 从锚点扩展 caller/callee、跨文件和跨仓关系；
3. 再用 grep 回查具体路径上的参数、配置和条件分支；
4. 必要时沿 JNI/CGO 等边界连接跨语言调用；
5. 汇总直接原因、根本原因和证据链；
6. 不满足强引用约束时保持待确认。

### 12.4 为什么要渐进，而不是一步到位

- 错误码和栈帧是高精度、低成本锚点；
- 设备特征能快速复用已知模式；
- 全量图搜索成本更高、噪声更大；
- 分层有利于统计每一级的解决率和失败原因；
- 知识库命中仍需证据门，避免过期经验直接误导。

## 13. grep 与 CodeGraph 协同

### 13.1 两者分别擅长什么

| 工具 | 擅长 | 不擅长 |
| --- | --- | --- |
| grep/文本搜索 | 精确字符串、错误码、配置、日志文本、动态拼接线索，高召回、快速 | 不理解真实调用关系，跨重命名和别名能力弱 |
| CodeGraph | caller/callee、符号关系、结构化路径、跨文件/跨仓影响分析 | 错误消息、运行时字符串和部分动态配置可能建不进图 |

### 13.2 四拍协同模式

```text
grep 找锚点
→ CodeGraph 展开结构路径
→ grep 回到路径节点查配置/分支/字符串
→ CodeGraph 评估上游来源与下游影响
```

这不是简单把两个工具都调用一次，而是让文本证据和结构证据交替缩小搜索空间。

### 13.3 为什么 grep 仍然必要

程序图通常无法完整表示：

- 配置文件；
- 日志模板；
- 反射字符串；
- 错误码表；
- 运行时拼接内容；
- 生成代码之外的文档映射。

grep 的优势是“只要文本存在就可能找到”，缺点是语义关系弱。因此它适合作为锚点召回器，不适合单独证明根因。

### 13.4 CodeGraph 的个人贡献边界

如果 CodeGraph 是团队或平台已有工具，推荐表述：

> 我负责设计故障诊断链路、输入锚点构造、grep 与 CodeGraph 的协同策略、跨仓路径裁剪和报告证据约束；CodeGraph 的底层 tree-sitter 图构建能力由平台提供。

除非确实开发过底层 parser、索引和图查询引擎，否则不要说“我实现了 CodeGraph”。

### 13.5 跨语言调用如何解释

跨语言追踪不是“一个图天然理解所有语言”，通常需要边界适配：

- Java ↔ C/C++：JNI 方法声明、native 实现和注册关系；
- Go ↔ C：CGO 声明和生成桥接；
- RPC：接口定义、服务名、客户端 stub 和服务端 handler；
- 配置/协议：方法名、路由和资源标识映射。

CodeGraph 负责语言内结构关系，边界映射负责把不同子图连接起来。若项目只覆盖部分边界，应明确覆盖范围。

## 14. 知识演进闭环与 RCA 报告

### 14.1 为什么不能让系统自动写知识库

一次诊断可能仍含假设。如果自动入库，错误知识会被后续请求反复命中并放大。因此闭环必须是：

```text
发现未收录错误码/设备特征
→ 生成候选诊断与证据
→ 人工确认根因
→ Schema与格式校验
→ 版本化入库
→ 同类故障复用
→ 失效/纠错反馈
```

这叫 Human-in-the-loop knowledge evolution，比“自动学习、越用越准”更准确。

### 14.2 知识项建议字段

已有材料涉及 `error_codes.md` 和 `special_team_st.md` 等知识文件。面试时可以抽象为：

- 错误码或特征 key；
- 适用产品、设备和版本；
- 触发条件和排除条件；
- 直接原因与根本原因；
- 关键日志/栈帧模式；
- 代码位置和调用路径；
- 修复与验证方式；
- 来源案例、确认人、确认时间；
- 状态：active / deprecated；
- Schema 版本。

如果实际文件字段不同，应以真实格式为准。

### 14.3 如何避免知识库污染

- 人工确认是入库硬条件；
- 错误码、设备范围和版本必须完整；
- 同一 key 冲突时不覆盖，进入人工仲裁；
- 写入前做 Schema 和格式校验；
- 知识项带来源案例和代码引用；
- 支持失效、回滚和审计；
- 新版本先灰度回放历史案例。

### 14.4 直接原因与根本原因

示例：

- 直接原因：空指针导致当前接口返回失败；
- 根本原因：设备类型映射缺失，使上游构造了空对象，而防御性校验也未覆盖该分支。

只写“发生空指针”是复述异常，不是完成 RCA。根本原因要解释为什么系统进入了该错误状态，以及为什么现有机制没有提前阻断。

### 14.5 RCA 强引用约束

每个核心结论至少应绑定：

- 真实仓库与 commit/MR；
- 文件路径；
- 方法或符号；
- 行号范围；
- 真实代码片段；
- 上下游调用关系；
- 对应日志、错误码或栈帧。

禁止伪代码的原因：伪代码只能说明“可能这样”，不能证明真实代码“确实这样”。

### 14.6 八段式 RCA 模板

如果项目实际采用八段式报告，可按以下结构解释；标题必须与真实模板对齐：

1. 故障摘要；
2. 输入与环境；
3. 错误码/日志/栈帧证据；
4. 调用链与影响路径；
5. 直接原因；
6. 根本原因；
7. 修复建议与验证方案；
8. 未确认项、引用与审计信息。

### 14.7 诊断模式摘要

每次分析后生成的“诊断模式摘要”不是再写一份长报告，而是提炼可复用结构：

```text
触发锚点 + 适用条件 + 关键路径 + 验证动作
+ 典型根因 + 排除条件 + 修复/回归方式
```

它的目标是让一线工程师下次遇到同类故障时快速复用，而不是依赖原分析者记忆。

## 15. 两个完整案例模板

以下案例用于练习系统讲解，不应冒充真实线上故障。面试前请各替换为一个本人真实负责并能展开 15 分钟的案例。

### 15.1 SMK 断言类故障案例模板

#### 故障现象

```text
自动化用例期望返回状态 A，实际返回状态 B；测试侧只有断言失败，未提供明确业务错误码或异常栈。
```

#### 诊断过程

1. 日志解析得到请求 ID、时间范围、接口和断言差异；
2. 线程相关性分析保留 MAIN/RELATED 日志，去除并发噪声；
3. 拉取服务端日志并确认实际处理服务；
4. 从运行时 JAR 映射到相关仓库；
5. 获取故障前约定窗口内的 MR，并抽取变更方法；
6. 从 OpenAPI/RESTCONF 解析请求入口；
7. JACG 从入口向下搜索，从变更方法向上回溯；
8. 接口等价和 API 锚点补全断裂路径；
9. 候选方法同时满足运行时、变更、路径和日志证据；
10. 回查真实代码，解释状态 B 如何产生，并输出 RCA。

#### 面试时必须补充的真实细节

- 实际断言字段是什么；
- 请求入口如何确定；
- 最终根因在哪个仓库、类和方法；
- 哪个 MR 改了什么；
- 调用链在哪一步曾断裂；
- 你写了哪段核心逻辑；
- 修复后如何验证。

#### 这个案例体现什么

- 弱证据条件下的系统化收敛；
- 运行时制品与源码变更对齐；
- 双向调用图比单向交集更稳；
- 结论可以回查而不是 LLM 猜测。

### 15.2 显式故障案例模板

#### 故障现象

```text
设备执行操作时返回错误码 E，并在服务日志中出现异常栈 S；栈顶停留在公共层，无法直接判断具体业务模块。
```

#### 诊断过程

1. Level 1 检索错误码和首个业务栈帧；
2. 检查知识项的设备、版本和触发条件，发现证据不完整；
3. Level 2 使用设备型号和特殊字符串补充匹配；
4. 仍无法解释根本原因，进入 Level 3；
5. grep 找到错误字符串、配置项和相关 handler；
6. CodeGraph 向上寻找入口、向下寻找受影响模块；
7. 跨 JNI/CGO/RPC 边界连接另一个语言仓库；
8. 回查真实分支，区分直接异常与根本配置/状态问题；
9. 报告绑定代码片段、路径、行号和调用链；
10. 人工确认后，将新错误模式按 Schema 入库并生成诊断模式摘要。

#### 面试时必须补充的真实细节

- 实际错误码或异常类型；
- 为什么 Level 1 没有直接结束；
- 设备特征是什么；
- grep 找到了什么，CodeGraph 又补了什么；
- 跨语言边界如何建立；
- 直接原因和根本原因分别是什么；
- 新知识由谁确认、如何入库。

## 16. 评测体系与指标设计

### 16.1 当前可以稳定使用的结果

- 已确认：SMK 单故障平均定位耗时由人工约 `12h` 降至 `2～3h`；
- 当前简历使用、但必须核实统计表：根因候选命中率较单向基线提升约 `40%`；
- 显式故障项目暂无已确认准确率、耗时或覆盖率数字，不应自行补造。

### 16.2 12h → 2～3h 怎么测

必须先定义“定位结束”：建议以“得到经模块 Owner 可复核的代码级根因候选和证据报告”为终点，不包含修复开发、代码评审、发布和完整回归。

推荐统计：

```text
T_manual = 人工开始排查到形成可复核根因的时长
T_system = 提交故障输入到生成可复核RCA的端到端时长
```

需要说明：

- 样本是否为同一批历史故障回放；
- 是否包含等待外部系统时间；
- 人工基线由哪些角色完成；
- 取平均、中位数还是区间；
- 失败样本是否计入。

`12h → 2～3h` 对应约 4～6 倍提速。简历使用耗时更直观，面试中再补倍数即可。

### 16.3 根因候选命中率

推荐定义：

```text
Hit@K = 人工确认根因出现在系统Top-K候选中的故障数 / 有确认根因的故障总数
```

必须固定 K。候选集合包含根因与 Top-1 排在根因位置是完全不同的难度。

### 16.4 应补齐的离线评测集

建议按故障案例而不是日志行构建评测集，并记录：

- 故障类型：SMK / 显式；
- 是否有错误码、栈、设备特征；
- 涉及仓库数和语言；
- 人工确认根因；
- 真实入口和关键路径；
- 关键变更；
- 每一阶段的预期产物；
- 人工排查耗时；
- 系统结果和失败类型。

### 16.5 分层指标

#### 日志与运行时证据

- 请求/线程召回率；
- 日志压缩率；
- 关键日志保留率；
- JAR—仓库映射准确率；
- 制品版本一致率。

#### MR 与方法抽取

- 相关 MR Recall@K；
- 方法抽取 Precision/Recall；
- AST 解析成功率；
- fallback 触发率；
- 全限定名与调用图节点对齐率。

#### 调用图与搜索

- 真实路径覆盖率；
- 平均候选数；
- Hit@1/5/10；
- 平均最短路径长度；
- 接口/动态场景单独命中率；
- 无路径和伪路径比例。

#### 根因与报告

- 根因候选命中率；
- 代码引用有效率；
- 直接/根本原因区分准确率；
- 人工采纳率；
- 平均人工复核时长；
- 不充分证据下的保守输出率。

#### 工程指标

- 端到端 P50/P95；
- 各阶段成功率和重试率；
- 断点恢复成功率；
- 重跑节省时长；
- 外部依赖失败率；
- 单案例资源消耗。

### 16.6 A/B 基线

SMK 可以设计：

| 方案 | 描述 |
| --- | --- |
| Baseline A | 人工排查 |
| Baseline B | 请求入口调用链与 MR 方法做 D1 单向精确交集 |
| Full | 运行时过滤 + caller/callee 双向回溯 + D1-D4 扩展 + 多维排序 |

显式故障可以设计：

| 方案 | 描述 |
| --- | --- |
| Baseline A | 仅错误码知识库检索 |
| Baseline B | grep 全仓文本搜索 |
| Full | 三级渐进路由 + grep/CodeGraph 协同 + 多证据门 + 强引用 |

### 16.7 消融实验

建议分别去掉：

- 运行时 JAR 仓库约束；
- 线程相关性分析；
- caller 回溯；
- 接口等价 D2；
- API 锚定 D3；
- 可用异常线索 D4；
- 多维排序；
- 显式故障设备特征层；
- CodeGraph，仅保留 grep；
- 人工确认入库门。

观察候选规模、Hit@K、耗时和错误知识率变化。消融结果必须来自真实实验，不能根据主观感受填写数字。

### 16.8 如何保证评测可信

- 同一批故障、同一代码/JAR/MR 快照；
- 根因由真实修复或模块 Owner 确认；
- 基线与完整方案使用同一入口和时间窗口；
- 报告样本量和失败案例；
- 同时报告准确性与候选规模，防止靠扩大集合提高命中；
- 按接口多态、跨仓、跨语言等难例分层；
- 保存每个案例的 trace，支持回放。

## 17. 工程化、稳定性与安全

### 17.1 幂等

建议幂等键包含：

```text
case_id + input_hash + jar_version + repository_commit
+ mr_window + analyzer_version + rule_version
```

相同输入重复执行应复用已验证产物；任何依赖版本变化都需要使下游缓存失效。

### 17.2 超时与重试

- 网络拉取和只读查询可做有限重试；
- 代码仓拉取前检查已有 commit；
- 模型结构化输出失败最多受控重试；
- 非幂等写入，如知识库更新，不自动盲重试；
- 总 deadline 向下传递，避免上游结束后后台仍长期运行。

### 17.3 失败降级

| 失败 | 处理 |
| --- | --- |
| 测试日志缺失关键 ID | 使用时间、接口和设备弱匹配，并标记低可信 |
| 服务日志拉取失败 | 保留测试侧证据，停止宣称运行时路径已验证 |
| JAR 无法映射仓库 | 扩展到服务归属仓，但提高噪声提示 |
| AST 解析失败 | 文本/正则 fallback，并标记待校验 |
| JACG 建图失败 | 退化到源码/CodeGraph/文本搜索，不伪造路径 |
| 动态调用无法解析 | 输出断点和所需运行时证据 |
| CodeGraph 无路径 | grep 回查配置、反射和跨语言边界 |
| 知识项冲突 | 不自动覆盖，转人工仲裁 |
| LLM 不可用 | 仍输出确定性候选和证据包，报告解释延后 |

### 17.4 可观测性

每个阶段记录：

- trace/case/stage ID；
- 输入和工具版本；
- 开始/结束时间；
- 状态、重试和错误类型；
- 候选规模变化；
- 产物路径和 hash；
- 外部调用耗时；
- 最终候选与人工反馈。

### 17.5 数据与代码安全

- 代码仓和日志按最小权限访问；
- 报告输出避免泄露密钥、token 和设备敏感信息；
- LLM 输入若经过外部模型，必须符合公司数据策略；
- 工具只读优先，知识入库需审批；
- 报告引用受权限控制，不能把内部代码暴露到无权限环境。

## 18. 项目高频面试问题与标准回答

### Q1：为什么要分成两套系统？

因为两类故障的初始证据不同。SMK 缺少强锚点，需要从日志、运行时制品、近期变更和调用图逐层收敛；显式故障已经有错误码或栈，应该先利用高精度证据，失败后再扩大搜索。统一流程会让强证据场景成本过高，也会让弱证据场景过早下结论。

### Q2：SMK 为什么叫“静默故障”？

不是没有任何失败，而是测试断言明确失败，但业务链路通常没有可直接定位根因的错误码或异常堆栈。可观察的是输出不一致，根因需要从间接证据反推。

### Q3：为什么需要 10 阶段？会不会过度设计？

阶段对应真实依赖：日志、服务端证据、制品、源码、MR、入口、调用图、候选证据、推断和报告。拆分后每步可以独立校验、重试、复用和审计。重点不是数字 10，而是把跨系统长任务变成可恢复工作流。

### Q4：10 阶段是不是 10 个 Agent？

逻辑阶段确定，但是否每阶段都是独立 Agent 要按真实实现回答。更稳妥的说法是“10 阶段流水线，由 Dispatcher 统一编排子 Agent 和确定性工具”。

### Q5：为什么用 manifest，不直接用数据库任务表？

manifest 是面向单案例的可移植状态与产物清单，便于本地重放和断点续跑。规模扩大时可以把调度状态放数据库，但产物版本、hash 和依赖关系仍需要 manifest 类契约。

### Q6：`done` 如何避免假完成？

进程成功只是条件之一；还要校验输出存在、JSON/Schema 合法、关键字段完整、输入版本一致和语义不异常，之后才能标记 done。

### Q7：断点续跑怎么保证不使用脏数据？

阶段记录输入 hash、工具版本和依赖产物版本。恢复时逐项校验；上游输入变化会使下游失效重算，而不是只根据状态字段跳过。

### Q8：日志为什么不能用固定时间窗？

并发系统中同一时间窗混有大量无关线程，时间接近不等于因果相关。请求 ID、线程传递、业务标识和调用关系比单纯时间更可靠。

### Q9：201,278 → 618 行会不会丢关键日志？

压缩率不是唯一指标，还必须测关键日志保留率。原始日志始终保留；MAYBE 类可以作为补充召回，后续发现路径缺失时回退扩大。该数字是单案例，且 618/608 口径需要先核实。

### Q10：为什么用故障前三天的 MR？

这是减少搜索空间的工程先验，假设新故障更可能与近期变更有关。它不是固定真理，应该根据部署批次、版本和故障暴露周期配置，并保留非近期变更通道。

### Q11：AST 与正则为什么同时使用？

AST 对 Java 结构解析更准确，能稳定识别类和方法；正则用于 Kotlin、解析失败或不完整 diff 的降级召回。正则结果必须带低可信标记并通过其他证据校验。

### Q12：AST+正则为什么能把 1,178 降到 156？

严格说不能单独归因。它们负责把 diff 转成方法集合；候选减少来自运行时仓库、MR 时间、方法级定位和调用路径等多层过滤。面试时应纠正这个因果关系。

### Q13：为什么分析 JAR，不直接分析源码？

JAR 代表当前环境实际部署的制品，能约束真实运行范围；源码仓可能包含未部署分支和无关模块。最终仍需回到源码解释，但入口范围由运行时制品确定更可靠。

### Q14：JACG 是什么？

JACG 是 Java 方法调用图分析工具，可从字节码生成 caller/callee 关系。本项目用它建立跨 JAR 的方法图，并通过 H2 保存和查询；核心工作是围绕业务入口、近期变更和接口多态设计搜索与交集策略。

### Q15：静态调用图为什么会有漏边和伪边？

动态代理、反射、运行时多态和配置驱动调用难以静态确定；为了保证召回，静态分析又可能连接多个潜在实现，形成伪边。因此要结合运行时 JAR、配置、日志和 API 锚点验证。

### Q16：BFS 为什么适合调用链搜索？

BFS 按路径长度逐层扩展，容易优先找到较短解释路径，并能设置深度和节点预算。大型调用图中还需 visited 去重、方向限制、包/仓过滤和优先级队列控制爆炸。

### Q17：caller/callee 双向搜索比单向好在哪里？

入口向下能约束请求实际影响范围，变更向上能验证候选是否能回到入口。两侧交汇可同时降低入口子图过大和公共方法调用者过多带来的噪声。

### Q18：四维交集是什么？

D1 是全限定方法精确匹配，D2 是接口与实现等价，D3 是 RequestMapping/RPC 等 API 锚点，D4 是存在时使用异常栈或服务日志线索交叉。它们从严格到宽松扩展候选，同时保留证据类型。

### Q19：D3 为什么可能贡献最大？

业务请求与 Java 方法之间经常隔着协议和框架映射，直接方法名不一致；API 锚点把 URL、RPC 或资源路径连接到入口方法，因此可能补回大量本来断开的路径。`+15～25%` 若只是案例估算，不应当作统一实测结果。

### Q20：你真的解决了反射和动态代理吗？

没有完整解决。准确说法是：针对静态调用图的能力边界，通过接口记录、配置、API 锚点和运行时证据补全候选，并显式记录无法解析的动态断点。

### Q21：根因候选命中率 40% 怎么算？

应按有人工确认根因的故障集计算 Hit@K，并与相同条件的单向精确交集基线比较。还要说明 K、样本量以及是相对提升还是百分点；这些无法说明时就不能给出精确口径。

### Q22：为什么不直接让大模型读日志和代码？

上下文过大、噪声高、跨仓路径无法仅靠文本证明，而且模型容易把近期 MR 相关性写成因果。系统先用确定性程序分析收敛，再让模型解释候选。

### Q23：LLM 在 SMK 中负责什么？

负责在结构化证据上生成和比较根因假设、解释代码语义并生成报告；不负责伪造调用边、跳过质量门或把无证据候选升级为确定根因。

### Q24：exploration_log 为什么重要？

它记录每次假设、工具调用、证据变化、候选淘汰和停止原因，使诊断可以重放、调试和审计，也便于区分规则错误、工具错误和模型判断错误。

### Q25：显式故障为什么还需要深度 RCA？

错误码和栈帧常只说明表层失败位置，可能停在公共层，或同一码对应多个条件。只有当锚点与设备、版本和代码路径形成一致证据时，才能解释根本原因。

### Q26：三级链路的晋级条件是什么？

当前层不能形成满足适用范围、日志/栈和代码位置一致性的解释时进入下一层。具体几项证据或阈值应读取实际配置，不应临场编造“二选三”。

### Q27：grep 和 CodeGraph 为什么不是重复？

grep 找文本锚点、配置和运行时字符串，CodeGraph 展开结构化符号和调用关系。一个高召回地找“在哪里出现”，另一个回答“上下游如何连接”。

### Q28：跨语言调用链怎么做？

各语言内部由语法/符号图解析，JNI、CGO、RPC 或协议映射作为边界连接。跨语言能力取决于已实现的边界适配，不应宣称任意语言天然互通。

### Q29：为什么知识入库必须人工确认？

错误诊断自动入库会污染知识库并在后续请求中放大。人工确认、Schema 校验、适用范围和版本化共同保证知识质量。

### Q30：“越用越准”怎么证明？

没有连续评测就不要这么说。更准确是“提高已确认同类故障的复用率并减少重复深度分析”。后续可统计 L1/L2 命中率、人工确认率和平均诊断耗时随知识库增长的变化。

### Q31：直接原因和根本原因有什么区别？

直接原因解释本次失败由哪个异常或错误状态触发；根本原因解释该错误状态为什么产生、为什么没有被更早发现或阻断。

### Q32：为什么强制真实代码、路径和行号？

它们把自然语言解释变成可以被工程师当场回查的证据，并能发现模型编造代码。行号会随版本变化，所以报告还应绑定 commit。

### Q33：两个项目中你个人负责什么？

推荐模板：

```text
我是两套诊断系统的 Owner，负责从问题分类、整体架构到核心链路落地。SMK 侧重点负责 10 阶段编排、manifest 质量门控、运行时变更归因、调用图双向搜索和根因推断；显式故障侧负责三级诊断策略、grep 与 CodeGraph 协同、知识入库约束和 RCA 报告规范。JACG、CodeGraph 等底层工具能力以及部分平台接口由已有平台或团队提供，我负责把它们编排成端到端可运行、可复核的诊断系统。
```

必须根据真实分工删改。

### Q34：项目最大的技术难点是什么？

不是调用一个大模型，而是在证据不完整、代码跨仓且调用图存在动态断点的情况下，建立可执行的搜索空间收敛机制，并保证每一步产物和最终根因都可回查。

### Q35：如果重新做一次，会改什么？

第一，统一构建带真实根因和调用路径金标的离线回放集；第二，用运行时 trace 补足静态调用图动态边；第三，把规则排序升级为可解释 learning-to-rank，但保留硬证据门；第四，把知识条目从 Markdown 演进为版本化结构存储和自动回归。

## 19. 程序分析、Agent 与后端八股

### 19.1 静态分析与动态分析

- 静态分析不运行程序，通过源码或字节码推断结构和可能路径；
- 动态分析通过 trace、采样或插桩观察实际执行；
- 静态分析覆盖广但可能有伪边，动态分析路径真实但只覆盖被执行场景；
- 最理想是静态图负责召回，运行时证据负责裁剪和确认。

### 19.2 AST 是什么

抽象语法树把源码表示为类、方法、表达式和控制结构等节点，忽略空格等表面形式。相比正则，它更能正确处理嵌套和语法边界。

### 19.3 为什么 diff 比完整文件难解析

diff 可能只包含方法的一部分，缺少类头、import 或闭合括号，无法直接形成完整 AST。常见做法是解析变更后的完整文件，再用 diff 行号映射所属方法；若只能拿到片段，则使用启发式 fallback。

### 19.4 字节码调用图的基本原理

读取 class 文件中的方法和调用指令，构建“调用者—被调用者”边。`invokestatic`、`invokespecial` 相对明确；`invokevirtual`、`invokeinterface` 受运行时类型影响；反射调用通常需要额外分析。

### 19.5 CHA、RTA 与 Points-to Analysis

- CHA 根据类层次结构枚举可能实现，快但伪边多；
- RTA 只考虑可能被实例化的类型，较精确；
- Points-to 分析推断变量可能指向的对象集合，更精确但成本更高；
- 面试中只解释原理，不要说项目使用了没有实现的算法。

### 19.6 BFS 与 DFS

- BFS 逐层搜索，适合找最短调用路径；
- DFS 内存可能更低，适合深入遍历，但容易先走入长支路；
- 大图中需要 visited、深度限制、节点预算和包级过滤；
- 加权路径可使用 Dijkstra 或优先队列式 best-first search。

### 19.7 Precision、Recall 与候选规模

扩大接口和动态候选会提高 Recall，但也会降低 Precision。诊断系统不能只追求根因“在集合里”，还要控制候选规模和人工复核成本。

### 19.8 Top-K 与 MRR

- Hit/Recall@K：真实根因是否进入 Top-K；
- MRR：真实根因首次出现排名的倒数均值；
- Top-1 反映直接可用性，Top-K 反映辅助诊断能力。

### 19.9 状态机的关键要素

状态、事件、转移条件、动作和终止状态。本项目中 manifest 保存状态，Dispatcher 触发动作，质量门决定转移。

### 19.10 幂等与可重入

- 幂等：重复执行产生相同最终效果；
- 可重入：任务中断后能够再次进入并安全继续；
- 断点续跑需要两者共同支持。

### 19.11 Checkpoint 与缓存的区别

Checkpoint 保存一次长任务的执行状态和中间产物；缓存按 key 复用历史计算结果。Checkpoint 关注恢复，缓存关注性能，两者可能共享存储但语义不同。

### 19.12 JSON Schema 的作用

定义字段类型、必填项、枚举和嵌套结构，使不同 Agent 和工具通过稳定契约通信。Schema 合法不等于语义正确，还要做业务校验。

### 19.13 重试与退避

网络瞬时错误适合指数退避加 jitter；输入错误和 Schema 业务错误不应盲目重试；非幂等写操作必须防重。

### 19.14 可观测性三支柱

Logs、Metrics、Traces。本项目尤其依赖 Trace，因为一次 RCA 跨越多个阶段和外部系统，需要还原候选如何收敛。

### 19.15 什么是 RCA

Root Cause Analysis 不只是找最后抛错位置，而是从现象、直接原因、系统性根因到修复与验证形成闭环。

### 19.16 什么是 Change Impact Analysis

分析代码变更可能影响哪些调用路径、模块和业务行为。本项目反向使用同一思想：从故障请求与近期变更两端寻找交集。

### 19.17 什么是 Human-in-the-loop

系统自动生成候选和证据，人类负责高风险确认或知识准入。人的角色不是弥补一个 Prompt，而是明确的质量控制节点。

### 19.18 为什么规则和 LLM 要分工

规则适合确定性状态、依赖和格式；LLM 适合日志/代码语义理解和假设生成。让模型负责状态转移会不稳定，让规则独自理解复杂语义又不灵活。

## 20. 压力追问与答题边界

### 20.1 “这不就是一堆脚本串起来吗？”

回答重点：脚本只完成单点自动化；项目的核心是跨系统数据契约、状态与质量门、运行时证据到方法级变更的对齐、双向图搜索、候选排序和可审计 RCA。任何阶段失败都能恢复和定位，而不是一次性顺序执行。

### 20.2 “最近三天 MR 凭什么是根因？”

它只是先验，不是结论。只有 MR 进入当前制品、位于请求路径且代码语义能解释现象时才提高根因可信度；系统还保留非近期变更和配置问题的候选。

### 20.3 “你用 LLM 猜根因，靠谱吗？”

LLM 不创造调用边和代码事实。确定性工具先形成证据包，模型只能在真实候选上解释并提出验证；最终报告必须引用仓库、commit、方法、代码和日志。

### 20.4 “静态图断了，你后面的结论还可靠吗？”

路径断裂本身会被记录。系统通过接口/API/配置补全候选，但不能证明的动态边不会包装成确定事实；必要时要求运行时 trace 或人工确认。

### 20.5 “40% 是不是拍脑袋？”

如果无法展示样本、Hit@K 和基线，确实不能守住。因此面试前必须找到评测表；找不到就把表述降级为“在内部回放中显著提高已确认根因进入候选的比例”，不再坚持精确数字。

### 20.6 “200+→12 和 45→8 到底哪个是真的？”

先解释它们可能是不同集合：组织仓库、近期有 MR 的仓库和运行时仓库；再展示实际案例产物。如果无法证明属于同一案例，就明确它们来自不同样本，不串成单一漏斗。

### 20.7 “CodeGraph 是你写的吗？”

如实回答底层能力来源。个人贡献是诊断流程、锚点构造、图查询策略、跨仓裁剪和报告约束；不要把平台工具包装成个人底层研发。

### 20.8 “知识自学习不就是往 Markdown 里追加一行吗？”

价值不在写文件，而在知识准入：必须有人确认、Schema 校验、适用范围、版本、来源、冲突处理和回归验证。没有这些，追加越快污染越快。

### 20.9 “有错误码还需要 AI 吗？”

错误码只提供锚点，未必解释不同设备、版本和跨仓路径。确定性命中足够时系统快速结束；只有歧义或未知模式才使用更深的语义和图分析，AI 不应为了存在而存在。

### 20.10 “为什么不用动态链路追踪替代 JACG？”

动态 trace 路径真实，但需要可复现环境、插桩和触发故障，且只覆盖本次执行；静态图可离线覆盖更多可能路径。更好的方案是两者融合，而不是相互替代。

### 20.11 “定位 2～3 小时还算自动化吗？”

链路涉及多仓拉取、JAR 分析、调用图和跨系统 I/O，目标不是毫秒响应，而是把约 12 小时的专家人工排查缩短并释放人工。还应展示各阶段耗时，继续优化可并行的 I/O 和图索引复用。

### 20.12 “Owner、0→1 怎么证明？”

回答具体决策和交付物：问题分类、阶段划分、manifest 协议、搜索基线、交集扩展、失败恢复、报告约束和评测设计；同时明确哪些工具和接口来自团队。Ownership 体现在关键设计决策和端到端结果，不是声称所有代码都一个人写。

### 20.13 “项目真正上线了吗？”

按照真实阶段回答：研发验证、内部试用、生产接入或规模化使用。没有证据时不要说大规模上线；可以说“完成真实故障回放/内部使用验证并具备进一步接入条件”。

### 20.14 “项目最失败的一类样本是什么？”

建议选一个真实难例：动态代理/反射导致图断裂、运行时版本与仓库不一致、日志缺请求标识、错误码知识过期或跨语言边界缺映射。说明它如何推动接口补全、版本校验或强引用设计。

## 21. 数字口径防守卡

每个数字都要能用“对象—分母—基线—条件—边界”五句话守住。

### 21.1 `10` 阶段

**对象**：SMK 端到端诊断逻辑阶段。  
**内容**：日志、服务日志、代码仓、MR、入口、调用链、证据、双向搜索、推断、报告。  
**价值**：明确依赖、门控和恢复边界。  
**边界**：不必声称严格等于 10 个独立进程或 10 个 LLM。  
**追问准备**：能画出全链路并说明每阶段输入输出。

### 21.2 `pending/running/done/failed`

**对象**：manifest 阶段状态。  
**完成定义**：产物存在、合法且版本一致后才 done。  
**失败处理**：记录错误与重试信息。  
**边界**：状态机本身不自动保证幂等，需要输入 hash 和写入协议。  
**追问准备**：恢复、僵尸 running、上游变化的处理。

### 21.3 人工约 `12h → 2～3h`

**对象**：从开始排查到形成可复核代码级根因的端到端耗时。  
**基线**：传统人工翻日志、查 MR 和追调用链。  
**结果**：约 4～6 倍提速。  
**边界**：不包含后续修复上线，需说明样本和统计方式。  
**追问准备**：各阶段耗时和失败案例是否计入。

### 21.4 故障前 `3天` MR

**对象**：近期变更候选窗口。  
**作用**：降低 MR 搜索空间。  
**依据**：项目工程经验或部署节奏。  
**边界**：不是通用常数，不证明因果。  
**追问准备**：窗口过长/过短和配置化方案。

### 21.5 `201,278 → 618` 行

**对象**：一个请求案例的日志过滤结果。  
**机制**：线程/请求相关性分类而非固定时间窗。  
**价值**：显著降低人工阅读和后续处理噪声。  
**边界**：单案例；618 与早期 608 冲突，必须核实。  
**追问准备**：关键日志保留率和回退机制。

### 21.6 `200+ → 12` 仓

**对象**：可能是组织级仓库到运行时相关仓库。  
**机制**：JAR/服务映射。  
**边界**：与 45→8 是否同一案例待核实。  
**追问准备**：JAR—仓库映射表如何生成和版本化。

### 21.7 `45 → 8` 仓

**对象**：可能是时间窗内有 MR 的仓库与运行时仓库取交集。  
**边界**：必须明确集合定义和故障样本。  
**不要说**：AST 把 45 个仓库解析成 8 个。  
**追问准备**：交集为空时怎么办。

### 21.8 `1,178 → 156` 方法

**对象**：MR 变更方法到路径相关候选方法。  
**机制**：方法抽取只是前提，收敛来自仓库、入口、调用链和证据过滤。  
**边界**：需要确认 156 是交集前还是搜索后。  
**追问准备**：全限定方法、重载、Kotlin fallback。

### 21.9 AST `90%～95%`、正则 `75%～85%`

**对象**：若为抽样评测，应是方法抽取准确率或成功率。  
**边界**：必须说明样本、指标和语言；不能把解析成功率当准确率。  
**建议**：未找到评测记录时不主动报。  
**追问准备**：错误类型和 fallback。

### 21.10 根因候选命中率 `+40%`

**对象**：相较 D1 单向交集基线的 Hit@K。  
**必须确认**：K、样本量、相对提升还是百分点。  
**边界**：不能由理论路径覆盖推导。  
**追问准备**：公式、基线、消融和候选规模。

### 21.11 `5%～15% → 30%～50%`

**对象**：早期讨论中的能力边界或理论路径覆盖估算。  
**结论**：不是当前简历实测指标。  
**使用方式**：原则上不在面试中主动使用。  
**不要说**：提升 30%；中点 10→40 是 30 个百分点，不是相对 30%。

### 21.12 数字审计总表

| 数字 | 当前状态 | 推荐处理 |
| --- | --- | --- |
| 10 阶段 | 已确认 | 可稳定使用 |
| 12h→2～3h | 已进入简历 | 补样本与终点定义 |
| 3 天 | 已有材料 | 解释为可配置先验 |
| 201,278→618 | 待核实 | 仅作为案例，统一 608/618 |
| 200+→12 | 待核实 | 当前简历不主动写 |
| 45→8 | 待核实 | 先明确集合定义 |
| 1,178→156 | 待核实 | 先明确过滤阶段 |
| AST/正则精度 | 待核实 | 无评测表不报 |
| +40% Hit@K | 高风险 | 找评测表；否则降级措辞 |
| 5～15→30～50 | 理论估算 | 不作为成果 |

## 23. 面试前一页速记

### 两类故障

```text
SMK：断言不一致，无明确错误码/栈 → 弱证据收敛
显式：有错误码/栈/设备特征 → 强锚点渐进诊断
```

### SMK 十阶段

```text
日志解析 → 服务日志 → 代码仓 → MR方法
→ 入口 → 调用链 → 证据 → 双向搜索
→ 根因推断 → RCA报告
```

### SMK 三个核心价值

1. Dispatcher + manifest + 质量门控，让长链路可恢复；
2. 运行时 JAR → 仓库 → MR → 方法，让变更归因落到方法级；
3. JACG 双向回溯 + 四维交集，让弱证据也能收敛到代码根因。

### 显式故障三级链路

```text
错误码/栈帧锚点
→ 设备特征匹配
→ grep + CodeGraph 深度RCA
```

### 显式故障三个核心价值

1. 强证据优先，避免不必要的全量分析；
2. 文本召回与结构推理互补，支持跨仓/跨语言；
3. 人工确认后入库，报告强引用并沉淀复用模式。

### 三条原则

- MR 相关性不是根因因果；
- 静态图候选不是运行时事实；
- LLM 解释不能替代真实代码证据。

### 核心结果

- SMK：人工约 12h → 2～3h；
- SMK：当前简历写根因候选命中率较单向基线约 +40%，必须补齐 Hit@K 口径；
- 显式故障：暂无确认量化指标，不自行编造。

### 最关键白板图

```text
运行时JAR限定仓库
      ∩
故障窗口近期MR方法
      ∩
入口向下callee路径
      ∩
变更向上caller路径
      ↓
日志/接口/代码语义验证
      ↓
可复核根因候选
```

### 最后一句总结

> 这段项目的核心价值不在于让大模型替工程师读日志，而在于把不同证据条件下的故障排查重构为“先确定性收敛搜索空间、再基于真实代码解释根因、全过程可恢复可审计”的诊断系统。

## 25. 最终答题边界

### 可以坚定表达

- 两类故障初始证据不同，因此采用不同诊断策略；
- SMK 是 10 阶段、质量门控、可断点续跑的 Agentic Workflow；
- 运行时制品、近期变更和调用图共同形成方法级归因链路；
- 双向调用图和接口/API 扩展用于缓解单向搜索漏召回；
- 显式故障采用强锚点优先的三级渐进诊断；
- grep 文本召回与 CodeGraph 结构推理是互补关系；
- 新知识经人工确认后再入库；
- RCA 绑定真实代码证据并区分直接原因与根本原因。

### 需要带限定词

- “12h→2～3h”限定为当前样本口径下形成可复核根因的诊断耗时；
- “+40%”限定为相对单向交集基线的根因候选 Hit@K，并需核实 K 和统计表；
- “跨语言”限定为已经适配的 JNI/CGO/RPC 等边界；
- “突破反射/多态”限定为候选补全与多证据验证，不是完整运行时还原；
- “知识自学习”限定为人工确认后的知识演进；
- “Owner、0→1”限定为本人真实设计、开发和交付范围。

### 不应宣称

- 静态分析可以 100% 还原运行时调用链；
- 最近 MR 一定是根因；
- 理论路径覆盖就是实测根因命中率；
- 5%～15% 到 30%～50% 等于“提升 30%”；
- AST 或正则本身将仓库/方法候选减少 87%；
- CodeGraph 或 JACG 底层引擎全部由本人实现，除非事实如此；
- 知识库完全自动学习且必然越用越准；
- 系统已自动完成修复、发布和回归；
- 无指标记录时为显式故障项目补造准确率或耗时。

### 面试前必须补齐的六项材料

1. 一个 SMK 真实故障案例的输入、根因、MR、调用路径和修复验证；
2. 一个显式故障真实案例的错误码/栈、设备特征、跨仓路径和入库结果；
3. `12h→2～3h` 的样本量与统计终点；
4. `+40%` 的 Hit@K 定义、K、基线、样本和原始评测表；
5. 200+→12、45→8、1,178→156、201,278→618 的集合定义和所属案例；
6. 个人代码、平台工具和团队协作的明确边界。

### 最终提醒

> 好的项目封装不是把所有数字都写到最大，而是让面试官从业务问题、数据流、程序分析、评测口径到个人贡献连续追问时，两个项目仍然属于同一套真实、完整且可核验的工程事实。

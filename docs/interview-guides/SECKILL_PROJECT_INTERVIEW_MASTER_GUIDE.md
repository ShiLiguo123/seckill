## 1. 项目定位与面试介绍

### 1.1 一句话定位

这是一个面向瞬时流量洪峰和热点库存竞争的分布式秒杀系统：入口通过OpenResty、动态黑名单和下单许可做多级控流，核心使用Guava/Redis多级缓存与Redis Lua分桶预扣，订单和库存通过RocketMQ事务消息、7天幂等标记及错误消息补偿实现最终一致性，数据层使用ShardingSphere按用户、商品维度分片。

### 1.2 30秒介绍

```text
项目主要解决秒杀场景中的瞬时流量洪峰、单热点库存竞争和跨服务一致性问题。我把交易链路拆成入口准入、许可控量、异步受理、缓存预扣、事务落库和失败补偿六个阶段。入口使用OpenResty按IP和用户Token限速，并用Lua完成1秒防重、15秒动态黑名单和接口防绕过校验；订单服务按可售库存的1.5倍生成下单许可，通过Lua原子领取后将任务写入RocketMQ。实际扣库存采用userId哈希分桶加Lua原子预扣，订单本地事务提交后再异步扣减数据库库存；失败时通过错误消息删除用户/商品两套订单记录并幂等恢复缓存库存。最后使用ShardingSphere将订单和库存按核心查询维度分片。
```

### 1.3 两分钟介绍

```text
这个项目面向高并发商品抢购。业务上有三个核心矛盾：第一，访问量远大于库存量，不能让所有请求都进入Java服务、Redis核心Key和数据库；第二，库存判断和扣减如果不是原子的会超卖，即使使用单Key Lua，在极端热点下也会出现单Key串行瓶颈；第三，缓存库存、订单数据和数据库库存分布在不同服务里，不能用一个本地事务直接覆盖完整链路。

流量层我设计了“网关准入—许可控量—MQ削峰”三级链路。OpenResty根据IP、用户和Access Token限速，Lua根据用户Token做1秒防重和15秒黑名单，同时校验前序页面下发的x-st-token，阻止绕过商品详情直接调用下单接口。进入订单服务后，系统根据可售库存乘1.5初始化下单许可，许可由Redis Lua原子领取；领取成功后只提交一个订单任务到RocketMQ，接口先返回可轮询的taskId，避免请求线程同步等待完整交易。

库存层不是直接让所有用户竞争同一个Key，而是把库存拆成多个桶，使用abs(userId.hashCode()) % bucketCount将用户稳定路由到固定桶。Lua一次完成桶存在性、维护状态、校准状态、库存充足性检查和扣减，解决判断与扣减竞态；库存重编排支持总量和增量两种模式，并在编排期间暂停扣减。

一致性层采用RocketMQ事务消息。缓存预扣成功后发送事务半消息，订单服务在本地事务中按userId和goodsId写入两份查询模型，并写入order_tx:{txNo}的7天事务标记；事务提交后，库存服务消费消息并扣减数据库库存，通过stock_tx:{txNo}和分布式锁保证幂等。数据库扣减失败时发送错误消息，订单服务删除两份订单记录、清理taskId映射，并通过check_execute.lua保证缓存库存只补偿一次。

项目最有价值的地方不是使用了多少中间件，而是明确了每一层的边界：许可只控制流量，Redis Lua库存才保证预扣正确；事务消息只连接本地事务和消息投递，最终一致性仍依赖消费幂等、错误消息和逆向补偿。
```

### 1.4 五分钟介绍结构

五分钟介绍按以下顺序展开：

1. 三个业务难点：流量远大于库存、热点Key竞争、跨服务一致性；
2. 一条完整链路：OpenResty → 许可池 → 订单任务MQ → 分桶Lua → 事务消息 → 数据库库存；
3. 四个重点：流量治理、多级缓存、库存分桶、事务补偿；
4. 用一次“库存落库失败”的案例讲清逆向补偿；
5. 最后说明压测口径、项目边界和下一步优化。

## 2. 业务目标、系统约束与不变量

### 2.1 输入和输出

典型输入包括：

- 用户身份与Access Token；
- 活动ID、商品ID、购买数量和商品版本号；
- 预约状态、活动时间、商品上下架状态和限购规则；
- 同步或异步提交模式；
- 数据库、分布式锁、普通Lua或分桶库存扣减策略。

异步模式的首次输出不是订单ID，而是订单任务ID。客户端随后轮询任务结果：仍返回taskId表示处理中，返回orderId表示订单已创建。

### 2.2 四个核心系统目标

1. **保护系统**：把重复、无权限和超过库存量级的请求挡在核心链路之外；
2. **库存正确**：任意并发交错下，缓存预扣不能出现负库存；
3. **最终一致**：成功订单最终对应数据库库存扣减，扣库失败最终回滚订单和缓存预扣；
4. **可扩展**：减少单热点Key和单库单表瓶颈，支持服务与数据水平扩展。

### 2.3 必须守住的业务不变量

```text
I1：任一库存桶 availableStock >= 0
I2：同一个orderTaskId只允许被受理一次
I3：同一个txNo的订单本地事务最多产生一次有效结果
I4：同一个txNo的数据库库存最多扣减一次
I5：同一个txNo的缓存库存最多补偿一次
I6：最终状态只能是“订单存在且库存已落库”或“订单回滚且缓存库存已恢复”
```

这些不变量分别由Lua原子脚本、taskId幂等键、`order_tx`、`stock_tx`和补偿Lua标记守住。

### 2.4 系统不承诺什么

- 不因为使用微服务就宣称绝对高可用；
- 不因为使用Redis Lua就宣称任何环境下永久“0超卖”；
- 不把MQ受理QPS等同于订单最终落库TPS；
- 不把缓存库存看成最终账本，最终库存仍以数据库落库结果为准；
- 不把RocketMQ事务消息描述成跨服务强一致事务。

## 3. 总体架构

```text
客户端
  │ access-token / x-st-token / 下单参数
  ▼
OpenResty
  ├─ IP / User / Access-Token 限速
  ├─ 1秒防重 + 15秒动态黑名单
  └─ 接口编排Token校验
  ▼
Spring Cloud Gateway
  ├─ JWT解析与userId透传
  └─ Sentinel网关流控
  ▼
Order Service
  ├─ 风控 / 商品状态 / 活动时间 / 限购 / 预约校验
  ├─ taskId幂等
  ├─ 库存×1.5许可池
  └─ Lua领取许可
  ▼
RocketMQ：topic_order_msg（异步受理与削峰）
  ▼
OrderTaskConsumer
  ▼
Bucket PlaceOrder
  ├─ userId哈希选桶
  └─ Redis Lua原子预扣
  ▼
RocketMQ事务消息：topic_bucket_tx_msg
  ├─ 订单本地事务：user_order + goods_order
  ├─ order_tx:{txNo} 7天标记
  └─ Broker提交后投递
  ▼
Stock Service
  ├─ stock_tx:{txNo}消费幂等
  └─ MySQL库存桶扣减
        │失败
        ▼
topic_error_msg
  ▼
Order Service补偿
  ├─ 删除两套订单记录
  ├─ 清理taskId映射
  └─ Lua幂等恢复Redis分桶库存
```

### 3.1 为什么分成两类RocketMQ消息

| 消息 | 目的 | 是否事务消息 | 核心边界 |
| --- | --- | --- | --- |
| `topic_order_msg` | 接口异步受理和削峰 | 否 | 把HTTP请求与实际下单执行解耦 |
| `topic_bucket_tx_msg` | 连接订单本地事务与库存消费 | 是 | 订单事务成功后才允许库存服务消费 |
| `topic_error_msg` | 逆向补偿 | 否 | 库存落库失败后回滚订单和缓存库存 |

把前两者混成“RocketMQ异步下单”会丢失技术深度。第一条解决吞吐和线程占用，第二条解决本地事务与消息投递的原子关系。

### 3.2 三种Token必须区分

| 名称 | 载体 | 作用 |
| --- | --- | --- |
| JWT Access Token | 请求头 `access-token` | 登录认证和解析userId |
| 接口编排Token | 请求头 `x-st-token` | 防止跳过前序页面直接调用下单接口 |
| 下单许可 | Redis `order:token:{goodsId}` | 控制进入异步下单链路的请求数量 |

接口编排Token属于访问路径校验；下单许可属于流量预算；二者都不是库存正确性的最终边界。

## 5. 端到端下单流程

### 5.1 网关准入

1. Nginx按照IP、用户和Access Token建立限流区，源码默认速率为`1r/s`；
2. 下单接口执行`submit_access.lua`；
3. 根据Access Token的MD5检查动态黑名单；
4. 同一Token在1秒窗口内出现第二次请求时，进入15秒黑名单；
5. 校验`x-st-token == md5(access_token + "4")`，防止绕过商品详情直接下单；
6. Spring Cloud Gateway解析JWT，将可信userId写入下游请求头。

### 5.2 业务前置校验

`SeckillBaseSubmitOrderServiceImpl.checkSeckillOrder`依次检查：

- userId和命令是否为空；
- 模拟风控策略是否通过；
- 商品是否存在；
- 是否处于秒杀时间范围；
- 商品是否已发布且未下架；
- 购买数量是否超过限购；
- 当前库存视图是否足够；
- 用户是否满足预约条件。

这些校验是快速拒绝和业务合法性检查，不代替最终库存原子扣减。

### 5.3 生成taskId并做幂等

异步模式使用`MD5(userId + "_" + goodsId)`生成taskId。同一用户对同一商品得到相同任务ID，再通过`check_execute.lua`执行“存在则拒绝，不存在则SETEX”的原子防重，TTL为24小时。

价值：

- 防止客户端重试产生多个下单任务；
- taskId可作为异步状态查询句柄；
- 不依赖前端自己生成随机幂等键。

限制：

- 当前粒度是“用户+商品”，同一用户在TTL内无法产生第二个合法任务；
- 如果业务允许多次购买，应加入活动ID、请求批次或业务幂等键；
- MD5在这里用于稳定标识，不用于密码学安全。

### 5.4 获取下单许可

许可读取顺序：

```text
Guava本地缓存
  ↓ miss
Redis order:token:{goodsId}
  ↓ miss
Redisson分布式锁
  ↓
Dubbo读取可售库存
  ↓
ceil(availableStock × 1.5)
  ↓
写入Redis和本地缓存
```

领取时执行`take_order_token.lua`：许可大于0则`INCRBY -1`并返回成功；Key不存在时刷新许可，最多重试3次。若订单任务消息发送失败，则执行`recover_order_token.lua`恢复许可并删除task幂等键。

### 5.5 为什么许可乘1.5

许可不是库存，而是进入核心链路的流量预算。若严格按库存1:1生成，用户校验失败、MQ发送失败、订单异常等情况会造成许可损耗，可能出现库存仍有但没有许可的“少卖”。适度超配允许一定失败流量通过，而最终库存仍由Lua预扣控制，因此不会因为许可超配直接超卖。

1.5不是通用常数，应根据以下数据调节：

- 前置校验失败率；
- 任务消息发送失败率；
- 订单事务失败率；
- 库存售罄后的无效任务成本；
- 少卖损失与系统负载之间的业务权衡。

### 5.6 异步受理与结果轮询

许可领取成功后，把`SeckillOrderTask`发送到`topic_order_msg`，HTTP接口立即返回taskId。`OrderTaskConsumerListener`消费任务并执行实际下单；获得订单ID后写入`order:task:id:{taskId}`，客户端轮询时从taskId切换为orderId。

这实现的是“受理异步化”，不是订单完成语义。面试中必须区分：

- 接口返回成功：任务已被系统接受；
- 查询得到orderId：订单本地事务已完成；
- 库存服务落库成功：跨服务链路最终完成。

## 6. 多级流量治理详细设计

### 6.1 为什么把限流前移到OpenResty

如果所有请求都进入Spring线程池再判断是否合法，会消耗连接、线程、反序列化、GC和日志资源。OpenResty在事件驱动网关层执行Lua，可以在进入Java服务前完成高频轻量判断。

### 6.2 限流、黑名单和许可的职责差异

| 机制 | 控制对象 | 时间尺度 | 解决问题 |
| --- | --- | --- | --- |
| Nginx限速 | IP/User/Token | 秒级 | 单主体访问频率过高 |
| 动态黑名单 | User Token | 15秒 | 高频重复刷接口 |
| 接口编排Token | 访问路径 | 单次请求 | 绕过前序页面直调下单 |
| Sentinel/本地限流 | Route/方法/线程池 | 服务运行期 | 保护Java服务和线程资源 |
| 下单许可 | 商品维度 | 活动库存周期 | 进入核心交易链路的总量 |

### 6.3 当前网关实现的工程边界

源码中的黑名单使用`lua_shared_dict`，共享范围是同一OpenResty实例的worker进程，不会自动在多个网关节点之间同步。生产多节点部署有三种选择：

1. 接受节点级近似限流，通过负载均衡放大总体阈值；
2. 使用一致性哈希让同一用户尽量落到固定节点；
3. 将全局黑名单放入Redis，同时保留本地缓存减少远程访问。

默认`1r/s`和“1秒内第二次请求拉黑”适合演示防刷机制，生产需要根据正常用户双击、网络重试和前端重发行为重新标定，避免误杀。

### 6.4 限流算法八股映射

- Nginx `limit_req`近似漏桶式平滑控制，`burst`允许有限突发；
- Guava `RateLimiter`基于令牌/平滑发放思想，适合单实例方法级QPS控制；
- 固定窗口实现简单但边界处可能出现两倍突发；
- 滑动窗口精度更高但状态和计算成本更大；
- 令牌桶允许一定突发，漏桶强调稳定出流。

## 7. Guava + Redis多级缓存

### 7.1 缓存结构

项目使用：

- Guava本地缓存：初始容量15、并发级别5、写后10秒过期；
- Redis分布式缓存：活动和商品业务对象通常5分钟过期；
- MySQL：最终数据源。

典型读取链路：

```text
Local Cache → Redis → Distributed Lock → Double Check → DB → Redis → Local
```

### 7.2 为什么需要本地缓存

本地缓存没有网络RTT，适合极热点、读多写少的数据。代价是每个实例都有副本，会存在短暂不一致，因此本地TTL较短，并通过版本号和领域事件降低旧数据窗口。

### 7.3 `SeckillBusinessCache`为什么不仅保存data

缓存对象还保存：

- `exist`：数据是否真实存在；
- `version`：客户端/本地缓存与分布式缓存的新旧比较；
- `retryLater`：热点回源竞争失败时快速返回，而不是继续阻塞。

`notExist()`相当于空值缓存，可降低不存在ID持续穿透数据库；`retryLater()`是一种过载反馈，不应被误认为“数据不存在”。

### 7.4 分布式锁 + Double Check

Redis miss后只有拿到Redisson锁的线程回源数据库。拿锁后再次检查Redis，是因为等待锁期间前一个线程可能已经完成回填。没有Double Check，后续排队线程仍会重复查询数据库。

活动缓存示例使用等待1秒、租约5秒；商品缓存示例使用等待2秒、租约5秒。未拿到锁的请求直接返回`retryLater`，这是有意识的快速失败：高峰期宁可让少量用户重试，也不让大量线程堆积。

### 7.5 缓存三大问题在项目中的对应

| 问题 | 含义 | 项目机制 |
| --- | --- | --- |
| 穿透 | 查询永不存在的数据 | `notExist`空对象缓存 |
| 击穿 | 单个热点Key失效并发回源 | Redisson锁 + Double Check + 快速失败 |
| 雪崩 | 大量Key同时失效 | 多级缓存、限流；生产还应增加随机TTL和批量预热 |

### 7.6 一致性边界

两级缓存不能提供瞬时强一致。项目通过短本地TTL、版本号和领域事件降低不一致窗口。对活动描述、商品详情可接受短暂最终一致；对库存扣减不能只依赖本地缓存，必须落到Redis原子脚本和数据库账本。

## 8. 防超卖方案的演进

项目保留四种下单策略，通过`place.order.type`切换：

| 方案 | 正确性方式 | 并发问题 | 适用价值 |
| --- | --- | --- | --- |
| DB | SQL条件更新/数据库锁 | 数据库成为热点 | 作为最直接基线 |
| Lock | Redisson分布式锁串行扣减 | 锁竞争和网络开销 | 便于理解分布式互斥 |
| Lua | Redis单Key判断+扣减原子化 | 单热点Key串行 | 高并发正确性主流方案 |
| Bucket | 多Key分桶 + 每桶Lua | 库存碎片、编排复杂 | 进一步拆散单Key热点 |

### 8.1 为什么Redis的GET后DECR不安全

两个线程可能同时读到库存1，都判断可扣，随后各自减1，最终库存为-1。问题不在Redis单命令是否原子，而在“判断+扣减”是两个命令，中间存在并发交错窗口。

### 8.2 Lua为什么能保证原子性

Redis在执行Lua脚本期间不会穿插执行其他命令，因此库存读取、比较和`INCRBY -quantity`构成一个原子操作。脚本还用返回码区分：

- `-1`：库存桶不存在；
- `-2`：库存维护/挂起；
- `-3`：库存校准中；
- `-4`：库存不足；
- `1`：扣减成功；
- `-10`：未命中预期分支。

### 8.3 Lua的限制

- 脚本执行期间阻塞Redis事件循环，不能写长逻辑；
- Redis Cluster中多个Key必须位于同一hash slot，生产需要Hash Tag设计；
- 脚本原子性只覆盖Redis，不能同时原子提交MySQL和RocketMQ；
- Redis故障恢复后仍要依赖数据库账本与对账机制。

## 9. 库存分桶设计

### 9.1 为什么单Key Lua仍可能成为瓶颈

Lua解决正确性，但同一商品所有请求仍串行访问一个Redis Key。极热点商品可能把单Key、单分片和单核事件循环打满。分桶将一个逻辑库存拆成多个物理Key，使请求分散到多个桶；在Redis Cluster中还可以进一步路由到不同slot和节点。

### 9.2 用户如何选桶

```text
bucketSerialNo = abs(userId.hashCode()) % bucketCount
```

稳定哈希的好处：

- 同一用户重复请求稳定落到同一桶，行为可预测；
- 分散随机争抢，减少单Key竞争；
- 不需要每次扫描所有桶。

### 9.3 分桶Lua执行什么

`decrement_bucket_stock.lua`接收三个Key：

1. 目标库存桶Key；
2. 库存编排挂起Key；
3. 库存校准Key。

脚本先检查桶是否存在，再检查是否处于编排/校准状态，然后判断库存是否足够并原子扣减。

### 9.4 库存如何分配到多个桶

编排服务先计算平均库存和余数：前`bucketCount-1`个桶分配平均值，最后一个桶接收余数；如果可售库存与总库存计算产生额外差值，再从前面的桶逐个补1，保证各桶之和等于逻辑总量。

### 9.5 总量模式和增量模式

- **总量模式**：传入值表示新的总库存，先计算已售数量，再得到新的可用库存；
- **增量模式**：传入值表示在当前库存上增加或减少的数量；
- 两种模式都不能让新总量小于已经售出的数量。

### 9.6 重编排为什么要暂停扣减

若一边重新计算桶数量和库存分布，一边继续扣减，可能发生库存丢失或重复分配。因此编排流程先获取商品维度锁并暂停桶服务，完成数据库和Redis更新后再恢复。

### 9.7 分桶的代价：库存碎片

如果某个桶售罄而其他桶仍有库存，固定路由到售罄桶的用户会收到库存不足，造成逻辑总库存未售完。可选优化包括：

1. 当前桶不足时随机探测1至2个备用桶；
2. 维护有库存桶的位图或集合；
3. 后台低频做桶间再平衡；
4. 小库存商品不启用分桶；
5. 根据热点程度动态调整桶数。

备用探测不能无限扫描，否则高峰期会放大Redis访问。

## 10. RocketMQ事务消息与最终一致性

### 10.1 事务消息解决什么

事务消息解决的是“订单本地事务”和“消息是否可被下游消费”之间的原子关系：

```text
发送半消息
  ↓
执行订单本地事务
  ├─ 成功：COMMIT，Broker投递给库存服务
  ├─ 失败：ROLLBACK，Broker删除半消息
  └─ 状态不明：Broker回查本地事务
```

它不直接把订单库和库存库放进同一个ACID事务。

### 10.2 订单本地事务

`OrderTxMessageListener.executeLocalTransaction`解析`TxMessage`并调用`saveOrderInTransaction`：

1. 检查`order_tx:{txNo}`是否已存在；
2. 使用txNo作为订单ID构造订单；
3. 分别写入`seckill_user_order`和`seckill_goods_order`；
4. 成功后写入7天`order_tx:{txNo}`事务标记；
5. 返回COMMIT。

Broker回查时只检查该标记：存在返回COMMIT，不存在返回UNKNOWN。

### 10.3 为什么订单要双写

系统有两类核心查询：

- 用户查看自己的订单：按userId路由；
- 运营或商品维度查看订单：按goodsId路由。

如果只保存一张按userId分片的表，按goodsId查询可能广播所有分片。因此项目用两套物理查询模型换取两类单分片查询，代价是写放大、事务和补偿更复杂。

### 10.4 库存消费幂等

RocketMQ默认至少一次投递，消费者可能重复收到消息。库存服务使用两层保护：

1. `stock_tx:{txNo}_lock`分布式锁，防止并发重复处理；
2. `stock_tx:{txNo}` 7天标记，防止串行重复处理。

成功扣减数据库库存后写标记；重复消息发现标记直接返回成功。

### 10.5 库存扣减失败后的补偿

库存服务失败时发送`topic_error_msg`。订单服务收到后：

1. 确认`order_tx:{txNo}`存在，避免对未提交订单补偿；
2. 删除用户维度订单；
3. 删除商品维度订单；
4. 清理taskId与orderId映射；
5. 通过`check_execute.lua`抢占补偿执行权；
6. 调用`increment_bucket_stock.lua`恢复Redis预扣库存。

### 10.6 为什么补偿也要幂等

错误消息也可能重复投递。如果每次都恢复库存，会出现“库存越补越多”。`check_execute.lua`使用`GET + SETEX`原子判断，首次返回1并设置7天标记，后续返回0，因此缓存库存最多补偿一次。

### 10.7 事务状态表

| 阶段 | 订单 | Redis库存 | DB库存 | 处理 |
| --- | --- | --- | --- | --- |
| 初始 | 无 | 未扣 | 未扣 | 等待请求 |
| 预扣成功 | 无 | 已扣 | 未扣 | 发送事务消息 |
| 订单事务成功 | 有 | 已扣 | 未扣 | 提交消息 |
| 库存落库成功 | 有 | 已扣 | 已扣 | 最终成功 |
| 订单事务失败 | 无 | 应恢复 | 未扣 | 本地异常路径恢复 |
| 库存落库失败 | 先有后删 | 先扣后补 | 未扣/已回滚 | 错误消息逆向补偿 |

### 10.8 仍然可能出现的极端窗口

任何最终一致性方案都需要考虑补偿消息也失败：

- 库存服务扣减失败，但错误消息发送失败；
- 订单删除成功，但Redis库存恢复失败；
- 两张订单表只删除一张；
- 7天标记过期后旧消息再次投递；
- Redis与数据库同时故障。

生产补强方案：

- 错误消息发送使用重试和死信队列；
- 失败事件先写本地Outbox，再异步投递；
- 定时对账扫描“有订单无库存事务”和“有库存事务无订单”；
- 补偿失败进入人工/自动修复表；
- 幂等记录可落数据库并设置更长保留期。

## 11. ShardingSphere分库分表

### 11.1 订单分片

订单服务配置3个数据源，每类订单表各3张：

```text
seckill_user_order:
  DB = userId % 3
  Table = userId % 3

seckill_goods_order:
  DB = goodsId % 3
  Table = goodsId % 3
```

### 11.2 库存桶分片

库存服务配置2个数据源、每库3张表：

```text
DB = goodsId % 2
Table = goodsId % 3
```

同一商品的所有桶落到同一物理表，便于按goodsId读取和编排；不同商品分散到不同库表。

### 11.3 为什么分片键要来自查询模式

分库分表不是为了展示用了ShardingSphere，而是为了避免核心查询广播：用户订单按userId查，商品订单按goodsId查，库存按goodsId管理，因此分别选择这些字段作为分片键。

### 11.4 分片带来的问题

- 非分片键查询可能广播路由；
- 跨库分页和排序成本高；
- 双写订单增加存储和补偿复杂度；
- 扩容需要数据迁移和双写切换；
- 跨分片事务能力取决于ShardingSphere事务模式，不能把普通`@Transactional`自动等同于强一致分布式事务。

### 11.5 扩容方案

若从3库扩到6库，直接修改取模会导致大量旧数据路由变化。常见方案包括：

- 使用逻辑分片表和路由映射表；
- 先双写新旧集群，再迁移历史数据；
- 按时间或业务批次新增分片；
- 使用一致性哈希减少迁移，但范围查询和负载均衡更复杂。

## 13. 四个完整面试案例

### 13.1 正常异步下单成功

```text
用户请求
→ OpenResty校验通过
→ 业务校验通过
→ taskId首次写入
→ 领取许可成功
→ topic_order_msg发送成功并返回taskId
→ 消费者按userId选桶并Lua预扣
→ RocketMQ事务半消息
→ 订单双写成功并COMMIT
→ 库存服务DB扣减成功并写stock_tx
→ 客户端轮询获得orderId
```

回答重点：接口快速返回的是taskId，最终交易成功要看库存落库与状态收敛。

### 13.2 用户重复点击

同一用户、同一商品生成相同taskId。`check_execute.lua`发现24小时Key已存在，直接返回重复提交，不继续领取许可和写MQ。

价值：重复请求不会演变成重复消息、重复订单和重复扣库存。

### 13.3 数据库库存扣减失败

订单本地事务已经提交，但库存服务更新数据库失败：

1. 库存服务发送错误消息；
2. 订单服务确认本地事务标记存在；
3. 删除user_order和goods_order；
4. 清理任务结果；
5. 抢占补偿幂等标记；
6. 恢复对应Redis库存桶。

这个案例最能体现项目的一致性闭环。

### 13.4 库存正在重编排

Lua发现挂起或校准Key，分别返回`-2/-3`，当前请求快速失败而不是使用不稳定库存。编排完成后恢复桶服务。

回答重点：维护窗口内选择可用性让位于正确性，避免边改库存结构边售卖。

## 14. 压测、A/B和指标口径

### 14.1 当前可确认的测试资产

仓库包含JMeter脚本，其中完整链路和防超卖场景配置过1000线程。但线程数只是负载配置，不等于QPS；`ThroughputController`参数也不是实际测量结果。

### 14.2 正确的A/B矩阵

在相同硬件、库存、数据和压测脚本下比较：

| 组别 | 提交方式 | 库存策略 | 目的 |
| --- | --- | --- | --- |
| A | 同步 | DB | 数据库基线 |
| B | 同步 | Redisson Lock | 验证分布式互斥代价 |
| C | 同步 | 单Key Lua | 验证原子脚本收益 |
| D | 异步 | 单Key Lua | 验证MQ削峰收益 |
| E | 异步 | Bucket + Lua | 验证分桶对热点竞争的收益 |

### 14.3 必须报告的指标

- 接口受理QPS，而不是模糊的“系统QPS”；
- 订单最终落库TPS；
- P50、P95、P99延迟；
- HTTP和业务错误率；
- 初始库存、成功订单数、数据库扣减数、Redis剩余库存；
- 超卖数和少卖数；
- MQ积压量与积压消化时间；
- Redis CPU、命令耗时和热点Key；
- MySQL CPU、锁等待、慢SQL和连接池占用。

### 14.4 防超卖结果怎么验证

若初始库存为`S`，成功订单总量为`O`，数据库已扣数量为`D`，Redis逻辑剩余库存为`R`：

```text
超卖：O > S 或 D > S
理想收敛：O = D = S - R
少卖：压测结束且无在途消息时，R > 0但没有新的合法请求能够成功
```

不能只看Redis没有负数，还要核对订单、数据库库存和在途消息。

### 14.5 “2万+QPS”如何正确表述

只有具备以下记录时才能写入简历：

```text
硬件/实例数：________
压测端与服务端是否分机：________
线程数：________
预热/持续时间：________
目标接口：下单受理 / 订单创建 / 完整落库
稳定QPS与峰值QPS：________
P95/P99：________
错误率：________
```

### 15.1 部署拓扑

```text
Load Balancer
  ├─ OpenResty × N
  └─ Spring Cloud Gateway × N
        ├─ Activity/Goods Service × N
        ├─ Order Service × N

RocketMQ：订单任务、事务消息、错误消息
MySQL + ShardingSphere：订单与库存分片
```

### 15.2 关键监控

- 网关：各限流规则命中数、黑名单数量、误杀率；
- 订单：许可剩余量、任务提交成功率、重复提交数；
- MQ：发送失败率、消费失败率、重试次数、积压深度；
- Redis：Lua耗时、热点Key、CPU、连接数和慢命令；
- 库存：预扣成功率、DB落库成功率、补偿次数和补偿失败数；
- 数据库：锁等待、慢SQL、分片路由和双写失败；
- 端到端：受理QPS、落库TPS、P95/P99和账务不一致数。

### 15.3 降级策略

| 故障 | 建议处理 |
| --- | --- |
| Redis不可用 | 停止秒杀下单，避免绕过预扣直接打DB |
| RocketMQ不可用 | 任务发送失败，归还许可并清除task幂等键 |
| 商品/预约RPC超时 | 快速失败，不继续进入扣库存 |
| 库存DB失败 | 错误消息补偿；发送失败进入Outbox/告警 |
| 本地缓存失效 | 回退Redis；Redis miss时单线程回源 |
| 分桶重编排 | 返回维护/校准状态，稍后重试 |
| 单个服务过载 | Sentinel/本地限流快速失败 |

### 15.4 为什么秒杀场景宁可快速失败

排队并不创造库存。请求量远大于库存时，让所有请求等待只会占用线程、连接和内存，并把故障传播到下游。快速失败可以保持系统整体可用，并给客户端明确的售罄或稍后重试结果。

## 16. 设计缺陷、技术债与改进方向

面试中能主动指出边界，比把项目说成完美系统更可信。

### 16.1 黑名单是节点本地状态

改进：Redis全局黑名单+本地短缓存，或一致性哈希固定用户节点；阈值基于误杀率和攻击样本调节。

### 16.2 接口编排Token可预测

当前`md5(access_token + 固定数字)`主要用于演示防绕过，不能替代真正防重放。生产应使用服务端密钥HMAC，绑定用户、商品、活动、过期时间和nonce，并校验一次性使用。

### 16.3 taskId粒度过粗

当前用户+商品在24小时内唯一。生产根据购买规则加入活动ID、购买批次或客户端幂等键，并将状态机持久化。

### 16.4 Redis幂等标记不是永久账本

7天后旧消息若再次出现，理论上可能重复处理。生产使用数据库唯一键、消费日志表或更长保留策略，并保证消息最大重试生命周期小于幂等记录TTL。

### 16.5 补偿消息可能丢失

改进：本地事务Outbox、发送确认、重试/死信队列、补偿任务表和定时对账。

### 16.6 分桶存在库存碎片

改进：有限备用桶探测、有库存桶索引、热点动态分桶和后台再平衡，并通过少卖率验证收益。

### 16.7 双写订单有写放大

可选替代：保留一份主订单，另一查询维度通过异步索引或Elasticsearch构建读模型；需要在查询实时性和写链路复杂度之间权衡。

### 16.8 配置与运行事实要分开

仓库中的部分ShardingSphere和Nacos配置以注释模板存在。正式答辩前应保留实际生效的Nacos配置、启动日志和分片SQL路由证据，避免把“设计过”说成“线上运行过”。

## 17. 高频项目问题与标准回答

### Q1：为什么既要限流又要下单许可？

限流控制单个主体或单位时间速率，防止某个用户或IP打满系统；许可控制商品维度进入核心链路的总量，使请求规模与库存量级相关。二者维度不同，不能互相替代。

### Q2：为什么许可是库存的1.5倍？

许可是流量预算，不是库存。1:1会因为校验失败和消息失败造成许可损耗，导致库存未售完。1.5倍是给失败流量留冗余，最终仍由库存Lua兜底。该倍数应根据失败率和系统承载能力压测确定。

### Q3：许可超配会不会超卖？

不会直接导致超卖，因为许可只决定能否进入下单队列，实际库存必须通过分桶Lua的原子判断和扣减。超配过大只会增加售罄后的无效任务和MQ压力。

### Q4：为什么要先MQ削峰，再发送一次事务消息？

第一条普通消息把HTTP受理和实际下单解耦；第二条事务消息保证订单本地事务成功后，库存服务才看到消息。一个解决流量和线程占用，一个解决本地事务与消息投递的关系。

### Q5：Lua为什么不会超卖？

库存读取、比较和扣减在同一个脚本中，Redis执行脚本期间不会插入其他命令，因此不存在两个请求都读到同一份库存后分别扣减的竞态。

### Q6：既然Lua正确，为什么还要分桶？

Lua解决原子性，分桶解决单Key竞争。所有请求访问同一个Key仍受单个Redis分片和事件循环限制；分桶把流量拆到多个Key，但增加库存碎片和编排成本。

### Q7：分桶会不会少卖？

会有碎片风险。固定路由桶售罄时其他桶可能还有库存。可以有限探测备用桶或维护有库存桶索引，但不能无限扫描。是否启用分桶要看热点程度和可接受少卖率。

### Q8：为什么按userId哈希而不是随机选桶？

稳定路由让同一用户重复请求落到固定桶，便于限购、幂等和问题追踪；随机路由均衡性可能更好，但重复请求会跨桶放大竞争和排查复杂度。

### Q9：RocketMQ事务消息等于分布式事务吗？

它实现可靠消息最终一致性的一部分，保证本地事务与消息提交关联；订单库和库存库并不是一个强一致ACID事务，仍要依赖消费幂等、失败消息、逆向补偿和对账。

### Q10：Broker回查为什么查Redis标记？

订单本地事务成功后写`order_tx:{txNo}`。Broker不知道本地事务状态时，通过该标记决定COMMIT或UNKNOWN。生产可把事务日志落数据库，避免Redis丢失影响回查判断。

### Q11：库存消息重复消费怎么办？

先抢`stock_tx:{txNo}`对应分布式锁，再检查7天幂等标记；标记存在直接返回，只有首次处理执行数据库扣减。

### Q12：补偿消息重复消费怎么办？

恢复库存前执行`check_execute.lua`，首次设置带TTL标记并获得执行权，后续重复消息看到标记后不再补偿。

### Q13：如果错误消息也发送失败呢？

仅靠当前同步发送不够。生产要使用Outbox、重试、死信队列和定时对账，让失败事件可持久化、可重放、可告警。

### Q14：为什么订单保存两张表？

分别服务按用户和按商品查询，避免非分片键广播。属于CQRS式读模型思想，但写放大和一致性成本更高。

### Q15：Guava本地缓存和Redis如何保持一致？

项目通过短TTL、版本号和领域事件降低不一致窗口，不提供瞬时强一致。库存写操作不依赖本地缓存做最终判断。

### Q16：为什么拿不到缓存重建锁就快速失败？

热点失效时只有一个线程回源即可，其余线程等待会占用连接和线程并形成堆积。返回`retryLater`让上游稍后重试，是过载保护。

### Q17：Double Check检查什么？

线程等待分布式锁期间，前一个线程可能已从数据库回填Redis。拿锁后再检查一次，存在就直接返回，避免重复回源。

### Q18：为什么不能只依赖数据库条件更新？

数据库条件更新能保证正确，但秒杀洪峰全部进入数据库会造成热点行锁、连接池和事务日志压力。Redis预扣把绝大多数竞争前移，数据库处理有限成功流量。

### Q19：异步下单如何告诉用户结果？

首次返回taskId，消费者创建订单后写taskId→orderId映射，客户端有限次数轮询。生产还可以使用WebSocket、SSE或消息通知，但仍需任务状态持久化。

### Q20：为什么P95比平均延迟更重要？

平均值可能掩盖MQ积压、锁等待和缓存回源造成的慢请求。P95/P99更能体现高峰期尾延迟；异步接口还应分别测受理延迟和最终完成延迟。

### Q21：你个人负责什么？

必须按真实情况回答。如果基于开源工程完成复现和二次优化，可使用：

```text
我基于公开秒杀工程完成了源码级复现和链路梳理，重点负责流量治理、异步下单、库存分桶和事务补偿链路的部署验证与优化；我能从入口Lua、许可池、分桶脚本一直讲到事务回查、消费幂等和错误补偿。原工程已有的通用模块我不会描述成个人原创，我重点强调自己实际修改、压测和验证的部分。
```

若确实独立新增了模块，再明确指出具体类、提交记录、前后基线和测试结果。

### Q22：项目最大的技术难点是什么？

不是调用Redis和RocketMQ，而是划清三层正确性边界：入口许可只控流，Redis Lua保证缓存预扣，事务消息+幂等+补偿保证跨服务状态最终收敛；任何一层都不能替代另外两层。

### Q23：如果重新做一次会改什么？

优先补齐Outbox和对账平台，将幂等日志持久化；然后做动态库存分桶和少卖率评测；最后建立统一压测报告，把入口QPS、订单TPS、MQ积压和账务一致性放在同一条Trace中。

## 18. Redis与缓存八股

### 18.1 Redis为什么快

- 核心命令主要在内存操作；
- 单线程执行命令避免大量锁竞争；
- I/O多路复用处理连接；
- 高效数据结构和紧凑编码；
- Redis 6之后网络I/O可多线程，但命令执行仍保持有序语义。

### 18.2 Redis单线程为什么还有并发安全问题

单条命令原子，不代表多条命令组成的业务操作原子。`GET库存 → Java判断 → DECR`之间可以穿插其他请求，因此需要Lua、事务或锁。

### 18.3 Lua和Redis事务的区别

Redis事务通过MULTI/EXEC顺序执行命令，但不提供传统数据库回滚；WATCH可以实现乐观锁。Lua可以把读取、条件判断和修改写在一个脚本中，更适合库存条件扣减。

### 18.4 Redisson锁的看门狗

不指定leaseTime时，Redisson可使用Watchdog续期；显式指定租约时通常不会自动无限续期。项目缓存重建使用5秒租约，要求数据库回源和回填在租约内完成，否则可能锁提前释放。

### 18.5 Redis持久化

- RDB：定期快照，恢复快但可能丢失最近数据；
- AOF：记录写命令，数据更完整但文件更大；
- 混合持久化结合二者。

库存缓存不是最终账本，即使Redis开启持久化，也要依赖MySQL和对账恢复。

### 18.6 Redis Cluster与Lua多Key

集群模式下脚本涉及的多个Key必须在同一slot。可用`{goodsId}`作为Hash Tag，例如`stock:{1001}:bucket:2`、`stock:{1001}:suspend`，确保同一商品相关Key同槽。

### 18.7 热Key怎么发现和处理

通过`--hotkeys`、代理层统计、命令监控和业务埋点发现；处理方式包括本地缓存、Key拆分、读副本、请求合并、限流和分桶。库存写热点不能简单读副本，必须保证写入顺序和一致性。

## 19. RocketMQ八股

### 19.1 RocketMQ核心角色

- Producer：发送消息；
- Broker：存储并投递消息；
- NameServer：路由发现；
- Consumer Group：负载均衡和消费进度；
- Topic/MessageQueue：消息分类与并行分区。

### 19.2 至少一次、至多一次、恰好一次

RocketMQ工程上通常提供至少一次投递，因此消费端必须幂等。端到端Exactly Once需要业务唯一键、幂等记录和事务共同保证，不能只靠MQ配置。

### 19.3 顺序消息

同一MessageQueue内可以保持顺序，生产者需要按业务Key选择队列，消费者按序处理。秒杀项目的库存幂等不依赖全局顺序；如果同一订单存在创建、支付、取消事件，应按orderId路由到同一队列。

### 19.4 消息积压怎么处理

- 先确认生产突增还是消费变慢；
- 扩容消费者，但并发上限受MessageQueue数量限制；
- 优化慢SQL、锁和外部RPC；
- 临时将积压消息转储到新Topic并行处理；
- 对售罄商品快速跳过无效任务。

### 19.5 事务消息回查

Producer本地事务结果不明确时，Broker回调`checkLocalTransaction`。回查必须幂等、快速，并依赖可靠本地事务日志。长期UNKNOWN会反复回查，最终按Broker策略处理。

### 19.6 普通消息、延迟消息和事务消息

- 普通消息：异步解耦和削峰；
- 延迟消息：到期后投递，适合订单超时检查；
- 事务消息：本地事务与消息提交关联。

当前源码没有完整15分钟未支付自动关单链路，因此面试时不要把延迟关单作为已实现核心功能。

## 20. MySQL、事务与分片八股

### 20.1 ACID

- Atomicity：事务内操作全部成功或全部回滚；
- Consistency：事务前后满足业务约束；
- Isolation：并发事务互不产生不允许的干扰；
- Durability：提交结果持久保存。

### 20.2 MVCC

InnoDB通过隐藏版本字段、Undo Log和Read View实现快照读，减少读写冲突。当前读或加锁读仍会访问最新版本并可能加锁。

### 20.3 隔离级别

- Read Uncommitted：可能脏读；
- Read Committed：避免脏读，但可能不可重复读；
- Repeatable Read：InnoDB默认，配合Next-Key Lock降低幻读；
- Serializable：最强但并发最低。

### 20.4 乐观锁扣库存

典型SQL：

```sql
UPDATE stock
SET available_stock = available_stock - :quantity
WHERE goods_id = :goodsId
  AND available_stock >= :quantity;
```

根据影响行数判断成功，能避免数据库层超卖，但极热点行会有锁竞争，所以项目在前面增加Redis预扣。

### 20.5 分库分表后分页

跨分片分页可能需要各分片取`offset+limit`再归并，深分页成本高。可基于时间/ID游标翻页，或将查询模型同步到搜索系统。

### 20.6 唯一键与幂等

最可靠的订单防重之一是数据库唯一约束，例如`(activity_id, goods_id, user_id)`。Redis幂等用于前置快速判断，数据库唯一键作为最终防线，两者结合更稳。

## 21. Spring、Dubbo与并发八股

### 21.1 `@Transactional`失效场景

- 同类内部自调用绕过代理；
- 方法不是可代理的public方法；
- 异常被捕获未继续抛出；
- 抛出受检异常但未配置rollbackFor；
- 使用了不受同一事务管理器控制的数据源；
- 异步线程不继承原线程事务。

项目事务监听器和订单保存使用`rollbackFor = Exception.class`，但跨服务和跨物理库仍不能靠一个本地注解自动获得全局事务。

### 21.2 Spring AOP如何实现

基于JDK动态代理或CGLIB生成代理对象，在方法调用前后插入事务、限流等逻辑。项目的注解式RateLimiter就是AOP拦截器。

### 21.3 Dubbo调用流程

消费者通过注册中心获得Provider地址，代理对象进行序列化、网络传输、负载均衡和超时重试。秒杀写接口要谨慎重试：若调用不是幂等，超时重试可能产生重复操作。

### 21.4 Nacos作用

注册中心负责服务实例发现，配置中心负责动态配置。两者都使用Nacos不代表职责相同；配置变更还需要灰度、校验和回滚。

### 21.5 Sentinel与普通限流器区别

Sentinel提供按资源的流控、熔断降级、热点参数和控制台规则；Guava RateLimiter是单实例内的轻量限速组件。网关、服务和方法级保护可以组合，但要避免多层阈值互相冲突。

### 21.6 线程池参数

核心参数包括corePoolSize、maximumPoolSize、queue、keepAliveTime、ThreadFactory和RejectPolicy。秒杀场景不应使用无界队列，否则高峰期会把请求变成内存中的长期积压。

### 21.7 `volatile`与synchronized

`volatile`保证可见性和一定有序性，不保证复合操作原子；synchronized同时提供互斥、可见性和可重入。分布式场景中的JVM锁不能保护其他实例，需要Redis锁、数据库锁或业务幂等。

### 22.1 “这不就是一个开源课程项目吗？”

### 22.2 “2万QPS怎么测的？”

如果没有硬件、持续时间、P95、错误率和接口范围，就直接承认当前没有完整报告，不继续使用该数字。不要用“线程数很多”或“JMeter显示过峰值”搪塞。

### 22.3 “为什么不用Redis Stream或Kafka？”

项目需要RocketMQ事务消息把订单本地事务与消息提交关联，RocketMQ在事务消息、消费重试和Java生态上适合该链路。普通异步任务用Kafka也可行，但需要另行设计本地事务与可靠投递。

### 22.4 “Redis宕机后预扣库存丢了怎么办？”

Redis不是最终账本。恢复时以数据库库存、成功订单和事务日志重建缓存；重建期间暂停下单，并通过对账处理在途事务。不能仅依赖RDB/AOF声称绝不会丢。

### 22.5 “订单已经返回成功，库存却失败了怎么办？”

异步受理接口返回taskId不代表交易完成。库存失败后订单会进入补偿删除，客户端查询仍应得到失败状态。生产应维护明确任务状态，而不只是taskId/orderId二态。

### 22.6 “你这算强一致还是最终一致？”

Redis预扣内部是原子一致的；订单本地事务内部满足ACID；订单与库存跨服务通过可靠消息和补偿最终收敛，因此整体是最终一致性。

### 22.7 “为什么不用Seata？”

Seata AT/XA可以降低部分事务编排成本，但跨服务强协调会增加锁、代理和全局事务开销。秒杀更适合把高并发链路异步化，以可靠消息、幂等和补偿换吞吐。若业务要求强一致且吞吐可接受，可评估Seata或TCC。

### 22.8 “分桶后Redis还是单机，有意义吗？”

单机上分桶可以分散Key级热点和便于后续扩展，但命令执行仍受单实例事件循环限制；真正获得节点级水平扩展需要Redis Cluster并设计Key slot。面试时不能把单机多Key夸成多节点吞吐线性提升。

### 22.9 “项目哪里最可能出事故？”

补偿链路。正向链路通常被充分测试，而错误消息发送失败、补偿重复、双写只回滚一半和幂等标记过期更容易造成账务不一致，因此生产必须有Outbox、死信和对账。

## 23. 面试前一页速记

### 三个问题

1. 请求量远大于库存量，核心链路不能承接全部流量；
2. 单热点库存存在并发竞态和单Key瓶颈；
3. 缓存库存、订单和数据库库存跨服务，无法由单一本地事务覆盖。

### 六段链路

```text
OpenResty准入
→ 库存×1.5许可
→ RocketMQ异步任务
→ userId哈希分桶 + Lua预扣
→ RocketMQ事务消息 + DB库存落库
→ 错误消息 + 幂等补偿
```

### 三种Token

- Access Token：认证；
- x-st-token：接口防绕过；
- 下单许可：商品级流量预算。

### 两类MQ

- 普通订单任务消息：削峰；
- 事务消息：订单本地事务成功后才投递库存消费。

### 四个关键参数

- OpenResty默认限速：1r/s；
- 重复请求窗口/黑名单：1秒/15秒；
- 下单许可：`ceil(库存×1.5)`；
- taskId TTL：24小时；事务/补偿标记：7天。

### 四个不变量

- Redis库存不为负；
- task只受理一次；
- DB库存只扣一次；
- 缓存库存只补偿一次。

### 分片规则

- 用户订单：userId → 3库×3表；
- 商品订单：goodsId → 3库×3表；
- 库存桶：goodsId → 2库×3表。

### 最关键案例

缓存分桶预扣成功 → 订单事务提交 → DB库存失败 → 错误消息 → 删除两份订单 → 清理任务映射 → Lua幂等恢复缓存库存。

### 最后一句总结

> 项目价值不在于“Redis+MQ+分库分表”的技术栈组合，而在于把流量预算、缓存预扣和跨服务最终一致性拆成三层边界，并为重复请求、重复消费和失败补偿分别设计幂等机制。
